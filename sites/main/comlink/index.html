Comlink, rebuilt for today's platform

Comlink lets you call a worker as if it were a local object. It was written when ports could carry a lot less than they can now, so I rebuilt it using what the platform has added since.

It is one file with no dependencies, hawser.js (a hawser is the rope that ties a ship to a port). The three demos below run it next to Comlink 4.4.2 on the same job so you can see where they differ.

Cancelling work and noticing a dead worker

Each picture is drawn by its own worker running the same code. Click either picture (or focus it and press Enter) to zoom in. Both follow.

What to try

Press Dive in fast. It asks for fourteen deeper pictures, one every 100 ms, like holding down a zoom key. On the left each new request cancels the one before, so the worker only draws what you are looking at. On the right every frame has to be finished in order, so the picture falls behind and the wasted time goes up.

Then crash them

Crash both workers calls terminate(), which is what a worker that ran out of memory looks like from outside. The left side notices within a second, starts another worker and redraws. The right side waits for ever until you press Restart both workers.

// the worker: an async generator, a band of rows per pull
async *rows(view, width, height, signal) {
  for (let y = 0; y < height && !signal.aborted; y += 12) {
    yield { y, pixels: transfer(band(view, width, height, y, y + 12)) };
  }
}

// the page
controller?.abort();                    // stop the picture we left
controller = new AbortController();
for await (const { y, pixels } of api.rows(view, W, H, controller.signal)) {
  ctx.putImageData(new ImageData(pixels, W), 0, y);
}

How it works. An AbortSignal cannot be cloned, so the one in the arguments is swapped for a token, and the worker gets a real signal of its own that aborts when yours does. The generator stays in the worker. The page holds a reference to it and each turn of the for await loop is one call to next(), so the worker only draws what was asked for.

A terminated worker sends nothing, so wrap(worker, { heartbeat: 300 }) pings it. After three unanswered beats every pending call rejects with LinkClosedError and closed(api) resolves, which is where this page starts the replacement. Comlink keeps its pending calls in a map that is never emptied.

Both frames are the same page on another origin. It counts the words in your note as you type. The red buttons inside are the widget trying to do more than it was asked to.

What to try

Type in the note and both counts follow. Then press the red buttons in each widget. Neither can call write(). But the Comlink widget's second button rewrites your note anyway, with code it sent across and ran inside this page, even though the page only exposed two harmless functions.

Then take the port back

Take back the Hawser widget's port aborts a signal. The widget's link closes, its loop over your edits ends, and it says so. With Comlink the only way to do that is to remove the frame.

// this page: expose the real object, say what may be reached
const revoke = new AbortController();
expose(note, offer(frame.contentWindow, widgetOrigin), {
  only: ["read", "changes"],
  signal: revoke.signal,
});

// the widget, on another origin
accept(hostOrigin, async (port) => {
  const note = wrap(port);
  for await (const text of note.changes()) count(text);
});

How it works. Comlink walks whatever path the caller sends. Every function has a constructor, which is Function, so new api.read.constructor("code") builds a function from the caller's text in the exposing page and hands back a proxy to it. Calling the proxy runs it. That doesn't matter when the other end is your own worker. It is a security hole when it is another origin.

Here a path may only touch an object's own properties and its class's methods. constructor, __proto__, call and bind are refused before anything is read. only then narrows what is left, and signal ties the link's life to something the page controls. offer() and accept() will not send or take a port without an exact origin.

Releasing a locked file when the link closes

A journal kept in a real fileFile handles open in the worker: 0

Opening the journal

    The file lives in this origin's private file system and is still there when you reload. A worker opens it with a sync access handle (an exclusive read/write lock on that file).

    What to try

    Add a line or two. Each one opens the file, writes, reads it back and lets go, and the count of open handles returns to zero. Now untick Let go of the file when done and add another. That handle is kept by mistake. Add one more and the browser refuses, because the file is locked.

    Then close the link

    Close the link fixes it. Everything the link was holding in the worker is disposed of, so the lock goes. The same happens if this tab is closed, or when the forgotten handle is garbage collected, although you can't know when that will be.

    // the worker
class Journal {
  #handle;
  append(line) { /* write and flush */ }
  [Symbol.dispose]() { this.#handle.close(); }
}
const api = { open: async (name) => give(new Journal(await lock(name))) };

// the page
{
  using journal = await api.open("journal.txt");
  await journal.append(line);
} // Journal[Symbol.dispose]() has run in the worker

    How it works. A class instance is passed by reference: the page gets a proxy and the worker keeps the object in a table with a count of how many times it has been sent. Disposing of the proxy, which is all using does at the end of a block, sends one small message. When the count reaches zero and the object was handed over with give(), its Symbol.dispose method is called.

    There are two fallbacks. A FinalizationRegistry sends the same message when a proxy is collected. And when a link ends for any reason both sides clear their tables, so nothing stays held for a page that has gone. Functions, objects and iterators all share the one port. Comlink gives each its own MessageChannel, with nothing tying their lifetimes together.

    Calling into a result before it arrives

    With Comlink, each step that returns an object costs a full trip there and back, and a new port. Here a call returns something you can keep calling into straight away. Everything queued in the same tick (before control returns to the browser's event loop) is sent as one message and the far side runs the steps in order against the real values. Between a page and its worker the saving is small. Across a slow hop, such as a relay or a connection to another device, it is one wait in place of three. This behaviour is covered by the unit test suite.

    // one message out, one port
const title = await api.open("ideas").latest().title();

// Comlink: three round trips, three ports
const notebook = await old.open("ideas");
const note = await notebook.latest();
const title = await note.title();

    Where this came from

    How Comlink works

    Comlink is about 650 lines. It works like this.

    1. wrap(port) returns a Proxy around an empty function. Reading a property does nothing but return another proxy that remembers the path so far.
    2. Calling it, awaiting it, assigning to it or using new posts one of six messages down the port: GET, SET, APPLY, CONSTRUCT, ENDPOINT or RELEASE, with the path and a random id.
    3. expose(object, port) listens on the other end, walks the path on the real object, does the thing, and posts the result back with the same id.
    4. Values go through structured clone. To send something by reference, such as a callback, you mark it with proxy(). Comlink then makes a new MessageChannel, exposes the value on one end, and transfers the other end in its place. Every proxied value is its own port.
    5. Extra types are handled by named transfer handlers, which is how thrown errors are flattened and rebuilt.
    worker.postMessage({ id: "4f1c…", type: "APPLY", path: ["math", "add"],
  argumentList: [{ type: "RAW", value: 1 }, { type: "RAW", value: 2 }] });
// and back
port.postMessage({ id: "4f1c…", type: "RAW", value: 3 });

    I think that design still holds up. The platform around it is what changed.

    What it still can't do

    • The result of a call is not a real Promise. It can be awaited, passed to Promise.all and given .then, but instanceof Promise is false, because it also has to be something you can keep calling into.
    • A chain only shares a message if it is written in one tick. Hold a result, wait, then call into it and it still works, by waiting for the answer first.
    • Garbage collection can happen at any time or never. Dispose of anything that has to be released on time yourself.
    • The heartbeat is a timer, and browsers slow timers in background tabs. It counts missed beats and not milliseconds, so a slow tab is not mistaken for a dead peer, but it will take longer to notice one.
    • Everything is asynchronous. A worker that never yields cannot answer a ping or hear an abort, so long jobs have to be cut into pieces, as the fractal is. A blocking call needs shared memory and a cross-origin isolated page, which is what the isolated room is for.
    • The automated suite runs in Chromium and Node (where MessageChannel behaves the same way); you can check the underlying primitives in other browsers in the lab.

    The whole API

    import { expose, wrap, connect, port, closed,
         share, give, transfer, offer, accept } from "/hawser.js";

expose(target, endpoint, { only, heartbeat, timeout, signal, onclose })
wrap(endpoint, { heartbeat, timeout, signal, onclose })
connect(target, endpoint)   // both directions: { remote, close, revoke, closed }
port(remote, { only, signal }) // a narrowed, revocable port to pass on
closed(remote)              // promise for why the link ended
share(object)               // send by reference
give(object)                // by reference, and theirs to dispose
transfer(buffer)            // move, do not copy
offer(window, origin)       // give a window a port, origin required
accept(origins, callback)   // take ports only from these origins

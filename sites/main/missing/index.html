What the web platform is missing

This is my list of things I want browser vendors to build or fix. All of it came out of building this site. For each item I say what is missing or broken, how I know, why I want it, and what people could build if it were there. Where I found a specification issue, a bug or a proposal, I link to it.

Where a gap can be tested, this page tests it in the browser you are reading it with and prints what happened. A red bar means the gap is there in your browser. A green bar means your browser already does it.

Why this matters to me

Today there are two ways to use someone else's code on my page.

I can load their library into my own origin. It then has everything my page has: the document, the storage, the cookies, and the network with my users' sign-in.

Or I can put their code in a frame on their own origin. It can then touch nothing of mine, which is what I want. But for many jobs I cannot pass it the data it needs, because the data is a type that does not cross from one origin to another.

Video is my example. I would like another origin to provide webcam filters, lenses and effects, so that I do not have to build them into my own site. Would I trust a video processing library to run inside my origin with access to everything on my site? No, I would not. I would trust it with frames. Frames go in, frames come out, and it has no other access to my site. That design needs a VideoFrame to cross origins, and it does not.

So the strict same-origin rule on these types does not keep third-party code away from the data. It pushes me to load that code into my own origin, which is the less safe choice, or to copy the pixels by a slower route. I think that rule is blocking designs that are both more secure and faster than what we do now.

Information security is hard, and some of these limits have reasons behind them. Where I know the reason I give it. I still think several of these types should move between origins, because moving them is what makes it possible to run third-party code safely.

It is the same shape as the AI router on this site, where a site gets a port to my model account and never sees the key. The other party gets the one thing it needs and nothing else.

1. Rich data cannot cross origins

A MessagePort, an ArrayBuffer, a stream and an ImageBitmap can all be sent to a frame on another origin. The types below cannot. They are the ones a media or file service on another origin would need.

Video frames and audio data cannot be sent to another origin

What is missing

A VideoFrame, an AudioData or an EncodedVideoChunk can be sent to a worker of the same page. Sent to a frame on another origin, it does not arrive. The call to postMessage succeeds, the receiver gets a messageerror event with nothing in it, and the sender is told nothing.

In your browser, now

Running: webcam effects from another origin, sent two ways

The frame in this demo is an effects service on another origin. It has no camera and cannot reach this page. This page sends it the same pictures two ways at the same time: as VideoFrame, which is what I want to use, and as ImageBitmap, which is what crosses origins today. Press Start. It uses a drawing unless you choose your camera.

The code is in effects-demo.js and effects.html.

How I know

  • The lab on this site sends 45 kinds of object to 13 places and records what happens. See the results.
  • In the Chromium this site was built with, the frame fails to arrive even when the other origin is on the same site and in the same process. So it is a rule about origins, and not a limit of sending between processes.
  • The shared browser tests expect it. This web-platform-test passes only if a frame can neither be copied nor moved to another origin.
  • The WebCodecs specification does not state the rule in its transfer steps. There is an issue asking for it to be written down: w3c/webcodecs #717, "Specify cross-agent-cluster structured cloning for various Web Codecs API objects".
  • The same failure has been reported against Electron: electron #47705.

Why I want it

A video frame is the unit of work for anything that processes video. It is a handle to pixels that are often already on the graphics card, and moving it copies nothing. If it cannot leave my origin, then code that works on video has to come into my origin.

What it would enable

  • Webcam filters, lenses, background blur and other effects provided by another origin. My page sends frames and gets frames back. The effects origin never has my camera, my page or my users' data.
  • Captions, translation and noise removal from AudioData, by a service that has no microphone permission of its own.
  • Plug-ins for a video editor that are given frames and nothing else.
  • A codec or a transcoder on another origin, taking encoded chunks in and giving frames back.

What you have to do today

Send an ImageBitmap, or copy the pixels into an ArrayBuffer and send that. Both work. In the demo above the bitmap route costs about a millisecond for each small picture in the Chromium this was built with, so at that size speed is not what is lost. What is lost is everything else a frame carries: the timestamp, the duration, the colour information and the pixel format. A frame from a camera or a decoder also has to be turned into a bitmap first, and a result that should go to an encoder has to be turned back.

In your browser, now

The video filter demo on this site sends each VideoFrame to a sandboxed frame. That works where the sandboxed frame shares a process with the page. In Chrome 160 on a Mac the lab recorded that the frame did not arrive there either.

In your browser, now, to a sandboxed frame

A camera or microphone track cannot be handed to anyone

What is missing

The specification says a MediaStreamTrack is transferable, to a worker or to a frame in the same agent cluster, which in practice means the same site. Chrome refuses to send one anywhere, a worker of the same page included. The specification does not allow another origin at all.

In your browser, now

How I know

  • The lab: refused with DataCloneError at every destination in Chromium 157 and Chrome 160.
  • The specification: Transferable MediaStreamTrack. The interface is marked Transferable, SameAgentCluster.

Why I want it

The only way to let a frame on another origin work with my camera today is allow="camera", which lets that frame open the camera itself. I want to open the camera in my page and hand over one track. The specification already describes the control I would want: the page that made the track stays in charge of the source, and when that page goes away the track ends.

What it would enable

  • A video call widget on another origin that is given one track and has no camera permission.
  • A recorder or a broadcaster on another origin that I can cut off by stopping my own track.
  • Processing a live track in a worker in Chrome. Safari is reported to have shipped that in version 18.

File handles, data channels and media sources stop at the origin boundary

What is missing

Each of these works inside one origin and fails to reach a frame on another.

TypeReaches another origin in your browserWhat it would enable if it did
FileSystemFileHandleAn editor on another origin that opens the one file I picked and saves it in place. It never sees the folder, and nothing is uploaded.
RTCDataChannelA plug-in in a frame with no network access that can talk on one connection I opened, until I close it.
MediaSourceHandleA player engine on another origin that feeds a video element in my page.
EncodedVideoChunkA decoder or a transcoder as a service on another origin.
ReadableStream, for comparisonThis one crosses, and it is what makes a transform on another origin possible.

Hover over an answer for the full result. The third column is to the right on a small screen.

How I know

  • The lab, in Chromium 157: none of the four reaches a frame on another origin, and all four work in a frame on the same origin.
  • For file handles the rule is written down. The File System Standard says a handle that arrives in a different origin must fail with DataCloneError.

Why I want it

Each of these is a narrow grant: one file, one connection, one video element. Handing over a narrow grant is how I would give a third party a job without giving it my origin. For a file, the choices today are to send a copy that cannot be saved back, or to load the editor's code into my own origin.

Chrome ends a frame's process when the frame draws on a canvas it was sent

What is broken

A canvas in my page can give its drawing surface away with transferControlToOffscreen(). Sent to a worker, that works. Sent to a frame that runs in another process, which is any frame on another site and any sandboxed frame in current Chrome, the frame is killed a moment after its first draw. Every other frame of that site in the tab goes with it.

In your browser This check is not run for you, because it can end frames from the other origin in this tab.

How I know

  • All three lab reports from Chrome 160 on a Mac record the receiver going silent for good after this one value.
  • I reproduced it in Chromium 157 with site isolation turned on for the frame. With the frame in the page's own process, it draws.
  • WebKit has a bug for the same case under its site isolation work: WebKit 325214. The Electron report above describes the frame crashing too.

Why I want it

A surface that another origin can paint and cannot read is a good way to embed a third party. It gets pixels on my page, and no access to the page.

What it would enable

  • Charts, maps, a game or a document viewer drawn by another origin straight into a canvas I lay out and style.
  • The video effects case, with the result painted directly and no frame sent back.

What you have to do today

Have the other origin send finished ImageBitmap frames and draw them yourself. The canvas demos on this site were changed to do that.

2. Failures nobody is told about

The sender is not told that a message could not be read

What is missing

When a value cannot be rebuilt where it lands, postMessage has already returned. The receiver gets a messageerror event that does not say what failed or which message it was. The sender gets nothing. The browser is not consistent about it either: for some types and destinations it throws at the sender, and for others it fails silently at the receiver.

In your browser, now: two values sent to the same frame on another origin

How I know

Most of the failed cells in the lab's results are of this kind. The guide has it running: a module sent to a shared worker disappears, and the sender waits for ever.

Why I want it

Every protocol on a port has to add acknowledgements and time limits to find out about a failure the browser already knows about. I did not find an open issue that asks for this.

What I am asking for

  • Throw at the sender when the browser can tell at send time that the destination cannot accept the type.
  • Put the name of the type that failed on the messageerror event.
  • Give the sending port an event when a message it sent could not be delivered.

Nothing says that the other end of a port has gone

What is missing

Close the tab, remove the frame or end the worker that holds the other end, and my port looks the same as before. No event fires, and posting into it throws nothing.

In your browser, now

How I know

  • The check above, and the heartbeat example in the guide.
  • This was asked for in 2016: whatwg/html #1766, "Add onclose event to MessagePort".
  • A close event was added to the HTML Standard in January 2024 by pull request #9933, with an explainer by Fergal Daly. Chromium built it, and Chromium 157 still has it behind the MessagePortCloseEvent flag.
  • Then whatwg/html #10201 pointed out that the event as written tells one side when the other side's port was garbage collected, which a page should not be able to observe. The issue was closed on 2 October 2026 by removing the event from the Standard. It is not in the current text.
  • Chrome's status page for the feature still says "Enabled by default". The check above shows what your browser does.

Why I want it

Without it, every library that makes calls over a port needs a heartbeat. A heartbeat is slow to notice, wakes background tabs, and gets it wrong when a tab is only throttled.

What I am asking for

The version that was discussed in that issue and not finished: an event the holder of a port opts in to, which fires when the other end calls close(), or its document or worker is destroyed, or its process crashes. It does not need to fire for garbage collection.

What it would enable

  • A call over a port that rejects at once when the other side dies.
  • A service that frees what it holds for a client as soon as the client is gone.
  • A shared worker that knows how many tabs it still has.

What you have to do today

Across origins, ping on a timer. Inside one origin, have the other side hold a Web Lock for life and queue for the same lock.

3. Ports as permissions

Holding a port is the permission to use it. That makes ports a good way to give another party a small, exact amount of access. These are the places where the model has holes.

There is no port that works in one direction

What is missing

Both ends of a MessageChannel can send and receive. There is no way to make an end that can only send or only receive, and anything can ride back along a port, another port included.

How I know

I had to build it: the one-way port on this site is two channels and a piece of code in the middle that copies messages forward and drops what comes back. It works only while the page running that code stays alive, and it has to post each copy with no transfer list, or a port could ride forward and become a way to answer.

Why I want it

A one-way link is the safe way to feed data to code I do not trust. If it has no way to send anything out, it does not matter what it reads.

What I am asking for

An option on MessageChannel, or a method on a port, that gives a send-only end and a receive-only end, enforced by the browser and still in force after the page that made it has gone. I did not find a proposal for this.

What it would enable

  • A sandboxed frame with no network access that is fed private data to display, and cannot send it anywhere.
  • A log or metrics sink that many parties can write to and none can read.

A readable stream can signal back to its writer

What is missing

Handing someone only the readable side of a stream looks like a one-way link, and it is not one. A stream asks its source for the next chunk when the reader takes one, so the writer can see the timing of every read, and a reader can send bits by choosing when to read.

How I know

Measured on this site: a sandboxed frame that held only a readable stream sent 16 bits to the writer by timing its reads, and all 16 were read correctly. It is running here.

What I am asking for

I am not sure this can be fixed without losing back-pressure, which is the reason to use a stream. At the least the Streams Standard and MDN should say that a transferred readable is not a one-way link. A real one-way port, above, would give people something to use instead.

A port does not say who is at the other end

What is missing

A message that arrives through window.postMessage carries the sender's origin. A message that arrives on a port carries none. A port can be passed on any number of times, and the receiver cannot find out which origin holds the other end now.

In your browser, now

Why I want it

Not knowing is correct for many uses, because the port is the permission. But a service that hands out ports cannot keep a record of who used one, and cannot refuse a party it would not have given a port to.

What I am asking for

An opt-in, set when the channel is made, that stamps each message with the origin of the context that posted it. I did not find an issue asking for this.

What it would enable

  • An audit log of which site used a delegated port, as the AI router needs for its usage counts.
  • A port that only works for the origin it was first given to.

A stream stops when the context it passed through goes away

What is broken

If A sends a stream to B and B sends it on to C, the data still travels through B. When B closes, C's reader stalls and gets no error.

How I know

It runs in the streams section of the guide. It is a known problem with an issue open since 2020: whatwg/streams #1063, "Transferable streams: the double transfer problem".

Why I want it

Introducing two parties and then leaving is the basic move with ports, and it works for a port. It should work for a stream.

What it would enable

A broker or a picker window that connects a producer to a consumer with a stream and then closes, which is what the hub on this site does with ports.

An AbortSignal cannot be sent

What is missing

An AbortSignal is how every modern API is cancelled, and it cannot be posted to a worker or a frame.

In your browser, now

How I know

The lab: refused everywhere. There is an open issue from 2021: whatwg/dom #948, "Allow postMessage-ing AbortSignal".

What it would enable

Cancelling work on another thread or another origin by passing the same signal I would pass to fetch. Today each library builds its own, as Hawser on this site does with a port.

4. Lifetime and reach

A service worker loses its ports when it is stopped

What is missing

The browser stops a service worker when it is idle. Every port it held is gone with it.

How I know

Mounting another site at a path and a tab that serves other tabs both rely on a service worker holding a port. Both have to make the worker ask the open pages for a new port each time it wakes.

What I am asking for

Ports that a service worker holds should survive a stop, and a message arriving on one should start the worker and be delivered, the way a message from a page does.

What it would enable

A service worker as a dependable router between the pages of a site and the other origins they have been introduced to.

There is nowhere for two sites to meet

What is missing

Two sites can pass a port only if one holds a reference to a window of the other: one it opened, its opener, or a frame. A hidden frame from a third origin used to work as a shared meeting point. Now its storage and its SharedWorker are separate for each top-level site, so it cannot be one.

How I know

The hub on this site has to be a visible popup window, with its registry kept on a server, for this reason.

Why I want it

The partitioning is there to stop tracking, and I am not asking for it to be undone. I am asking for a way through it that the person using the browser controls. I worked on Web Intents for the same reason.

What I am asking for

A picker drawn by the browser, like the one FedCM has for sign-in, that lets the person choose a site for a job and hands each side one end of a MessageChannel. The Storage Access API can already give a frame an unpartitioned shared worker after a prompt. That helps one site reach itself on other sites, and does not introduce two sites to each other.

What it would enable

  • "Edit this image with", "pay with" and "send to", with the person's own choice of site and no server in between.
  • A site calling the person's own AI model, or their own agent, through a port the browser handed over.

A page with shared memory cannot talk to a popup on another origin

What is missing

To get a SharedArrayBuffer a page has to be cross-origin isolated. The headers that do that also cut it off from any window on another origin that it opens, so it cannot hand that window a port.

How I know

The isolated room on this site shows what changes.

What I am asking for

Chrome has an answer on desktop since version 137: Document-Isolation-Policy, which isolates one document and leaves its popups reachable. I want it in Chrome on Android, and in Safari and Firefox.

What I am not asking for

  • Shared memory between origins. A SharedArrayBuffer and a compiled WebAssembly.Module stay inside one origin for reasons I accept.
  • Ports that can be saved to storage. A port is a live connection, and leaving it with a shared worker over a reload is enough.
  • Any of the cross-origin transfers above without both sides choosing it. The sender has to post the value and the receiver has to be listening.

How this list was made

Every item comes from something built on this site that did not work, or needed a workaround. The measurements are from the lab, in Chromium 157 while building and from Chrome 160 on a Mac in the reports people have sent. I have no results from Safari or Firefox yet. If you run the lab in one of them, the results are stored and this list gets more accurate.

If something here is wrong, already fixed, or already proposed somewhere I did not find, please open an issue. There is more background for all of it in Further reading, in the sections on how the standards changed and the specifications.

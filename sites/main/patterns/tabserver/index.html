Port patterns / More things a port can carry

Serve pages to other tabs from this tab

What you are looking at

A Service Worker can answer a fetch any way it likes, including by asking someone else. This page hands the worker a port. Every request under /patterns/served/ is sent up that port, and whatever you type on the left is the response. The page on the right is a real navigation to a real URL, and so is the new tab.

The code

// Service Worker
onfetch = (event) => event.respondWith(new Promise((resolve) => {
  const { port1, port2 } = new MessageChannel();
  port1.onmessage = (e) => resolve(new Response(e.data.body, { headers: e.data.headers }));
  tabPort.postMessage({ url: event.request.url }, [port2]);
}));

Using it

// a site editor in the browser. The files being edited live in this tab, in a Map called files
// the editor tab: offer() gives the worker a port, and answers what comes up it
const offer = () => {
  const channel = new MessageChannel();
  channel.port1.onmessage = (event) => {              // one request, and its reply port
    const path = new URL(event.data.url).pathname;
    const body = files.get(path) || "No such file in the editor";
    event.ports[0].postMessage({ body, headers: { "content-type": typeOf(path) } });
  };
  registration.active.postMessage({ serve: true }, [channel.port2]);
};
offer();

// the Service Worker: keep that port as tabPort
onmessage = (event) => { if (event.data.serve) tabPort = event.ports[0]; };

// the person presses Preview. This is a real navigation, answered by the editor tab
previewButton.onclick = () => window.open("/preview/index.html");

// The browser stops an idle Service Worker, and tabPort goes with it. When the worker
// wakes it posts "need-port" to its open tabs, and the editor hands over a new port.
navigator.serviceWorker.onmessage = (event) => { if (event.data === "need-port") offer(); };

Where you would use it

A real case. A site editor runs in the browser and keeps the files being edited in memory, in one tab. The person presses Preview, and a second tab opens at /preview/index.html. The Service Worker holds no files, so it sends each URL up tabPort and the editor tab answers with the text as it stands, saved or not. A style sheet or a link in the preview is one more request, answered the same way. The moment to plan for is a quiet spell: the browser stops the worker, tabPort is lost, and the editor has to hand over a new port before the next request can be answered.

How it works

A service worker sees every request in its scope and may answer however it likes. Here it answers by asking: it posts the URL down a port to a tab, with a reply port, and builds the response from what comes back.

The tab is now the origin server for those URLs. Other tabs, frames and even image tags get real responses at real addresses, written by JavaScript in a page you can see.

Service workers are stopped when idle and lose their variables, the port included. When this one wakes without a port it asks every open page for a new one, and waits briefly.

What each press of Next does in the demo at the top.

  2. Load the served page. The box on the right navigates to a real URL. The Service Worker forwards the request up the port to this tab, and this tab writes the response.

A website served out of this origin's private file system

The idea: Serving files from the Origin Private File System or from memory.

What you are looking at

This tab writes three files into the Origin Private File System: a page, a stylesheet and a picture. Then it serves them. The box on the right is a real navigation to a real URL. The service worker passes each request up a port to this tab, the tab opens the file, and the File itself goes back down the port as the response. No server has these files. Rewrite the stylesheet and reload, and the site changes.

The code

// this tab, for each request the service worker passes up
port.onmessage = async ({ data, ports: [reply] }) => {
  const name = new URL(data.url).pathname.split("/").pop() || "index.html";
  const file = await (await root.getFileHandle(name)).getFile();
  reply.postMessage({ body: file, headers: { "content-type": typeFor(name) } });
};

Step by step

What each press of Next does in this demo.

  1. Write three files to the private file system. A page, a stylesheet and a picture, written by this tab into storage only this origin can see.
  2. Load the site from them. Three requests reach the service worker. Each is answered by this tab, from a file.
  3. Rewrite the stylesheet and reload. This tab overwrites one file. The site is loaded again and looks different.

One tab holds the data, and the others fetch it with fetch()

The idea: Local-first apps where a tab holds the data and others fetch it.

What you are looking at

The notes exist in one place: an array in this tab's memory. The reader on the right is an ordinary page that calls fetch("notes.json"), as it would against any server. The request goes to the service worker, up a port to this tab, and the answer comes back as JSON. The reader does not know its server is a tab. Add a note here, fetch again there, and it has arrived.

The code

// the reader: nothing unusual
const notes = await (await fetch("notes.json")).json();

// this tab, which is the server
port.onmessage = ({ data, ports: [reply] }) =>
  reply.postMessage({ body: JSON.stringify(notes), headers: { "content-type": "application/json" } });

Step by step

What each press of Next does in this demo.

  1. Open a reader. A real page loads, and fetches the notes. This tab answers.
  2. Add a note in this tab. The note is added to an array in this tab, and nowhere else.
  3. Reader: fetch again. The reader asks again and gets the new note.

Things to try

  • Edit the HTML on the left and load the served page again.
  • Open the served page in a new tab, with any path you like. The tab on the left sees the path and answers.

Common mistakes

  • Requests fail once the serving tab closes.
  • A sandboxed frame with no origin is not controlled by your service worker.
  • What you serve runs as your origin.

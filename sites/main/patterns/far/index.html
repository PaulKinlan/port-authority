A port whose other end is on another device

What you are looking at

This page meets another device through a pairing code, the two connect directly with WebRTC, and each side wraps its end of that connection in a MessagePort. Then this page hands its port on. The counter at the end of the yellow cable is a sandboxed frame that was given a port and knows nothing more. Your phone is now pressing its buttons. The server carried a few messages so the two could find each other, and nothing since. The port carries more than text: bytes, other ports and streams can be posted into it, and each is rebuilt on the other device. See sending a photo as a stream and lending a port to another device.

The code

// this page shows a pairing code. onPort is given a real MessagePort
far({ code, host: true, onPort(port) {
  counterFrame.postMessage({ cmd: "port" }, "*", [port]);   // give it away like any other port
} });

// the other device, with the same code: ordinary port code
far({ code, onPort(port) {
  port.postMessage({ do: "add" });
  port.onmessage = ({ data }) => show(data.count);
} });

Using it

// a venue's front desk laptop, and a steward's phone at the door
// the laptop: code is six random characters, shown on screen as a QR code
const line = far({ code, host: true, onPort(port) {
  counterFrame.postMessage({ cmd: "port" }, "*", [port]);   // the counter gets the port that stands for the phone
} });

// the counter frame: it was given a port, and does not know a phone holds the other end
addEventListener("message", (e) => {
  if (e.source !== parent || e.data?.cmd !== "port") return;
  const port = e.ports[0];
  port.onmessage = ({ data }) => { if (data.do === "add") count++; port.postMessage({ count }); };
});

// the phone, with the code from the QR link: one press for each person who comes in
far({ code, onPort(port) {
  addButton.onclick = () => port.postMessage({ do: "add" });
  port.onmessage = ({ data }) => show(data.count);
}, onState(state) { if (state === "gone") show("The front desk hung up"); } });

// the laptop: the doors close
line.close();

Where you would use it

A real case. At a venue's door a steward counts people in on a phone, and the total shows on the front desk laptop. The laptop shows a pairing code as a QR code, the steward scans it, and the two devices connect directly. The laptop hands its port to the counter, which is a sandboxed frame that knows only that it was given a port. When the doors close the laptop calls close(), and the phone's onState reports gone. There is no relay, so this works only where the two devices can reach each other directly.

How it works

Two devices cannot pass a port, because neither has a reference to the other. A server can introduce them. Each opens a WebSocket to a meeting place named by a short code, and the server relays the few messages WebRTC needs to set up a direct data channel.

Each side then makes a local MessageChannel, joins one end to the data channel, and hands out the other. Code that holds that port cannot tell it from any other port.

This page gives its port to a sandboxed counter. The phone ends up talking to a frame that was given a port and nothing else, through a page that keeps no reference to either.

The browser will not move a port or a stream to another machine, so the code that joins the port to the data channel rebuilds them. When a message contains a MessagePort, the far side makes a new channel, hands out one end, and the two sides pass that port's messages along the same data channel under a number. A ReadableStream becomes a new stream on the far side that asks for one chunk at a time, so the source is read only as fast as the far side reads. A WritableStream works the same way in the other direction. Bytes travel as bytes, cut into frames of 15 kB.

All of it shares the one data channel. The file that does this is portwire.js. It needs only something that carries bytes in order, so the same code would put a port on a WebSocket.

Approve on your phone what you started on your laptop

The idea: Approving an action on one device that was started on another.

What you are looking at

This page is a checkout. Before it pays, it asks another device. The two are joined by a pairing code and a direct connection, and each holds a port. The question goes down the port, the other device shows Approve and Deny, and the answer comes back up it. Open the link on your phone to do it for real, or let a second page stand in for the phone.

The code

// laptop
const port = await far({ code, host: true });
port.postMessage({ ask: "Pay 20 to the florist?" });
port.onmessage = ({ data }) => data.answer === "approve" ? pay() : stop();

// phone
port.onmessage = ({ data }) => show(data.ask);
approveButton.onclick = () => port.postMessage({ answer: "approve" });

Step by step

What each press of Next does in this demo.

  1. Open a line to your phone. This page opens a meeting place and shows its code. The link is for your phone.
  2. Use a stand-in for the phone. A second page plays the phone, and the two connect directly.
  3. Pay 20 to the florist. The checkout stops and asks the other device.
  4. Other device: approve. The other device says yes, down its port. The checkout goes ahead.
  5. Pay 20 to the florist. A second payment asks again.
  6. Other device: deny. This time the answer is no, and nothing is paid.

An agent on one machine, using tools that live in a browser on another

The idea: Pairing an agent on one machine with tools in a browser on another.

What you are looking at

This page is a shop with a basket, and it offers three tools: read the basket, add tulips, and empty it. The agent runs somewhere else. The two are paired with a code and connect directly, and the agent's side holds a port. It is sent the list of tools and calls them by name. This page decides what each name does, and refuses any name it never offered. Here a second page stands in for the agent's machine, and its buttons stand in for the agent's choices.

The code

// this browser owns the tools
const tools = { readBasket: () => basket.join(", "), addTulips: () => { basket.push("tulips"); return "added"; } };
const port = await far({ code, host: true });
port.postMessage({ tools: Object.keys(tools) });
port.onmessage = ({ data }) =>
  port.postMessage(data.call in tools ? { result: tools[data.call]() } : { error: "no such tool" });

Step by step

What each press of Next does in this demo.

  1. Open a line for the agent. This page opens a meeting place and shows its code.
  2. Use a stand-in for the agent's machine. A second page plays the other machine. The two connect directly, and the tool list is sent.
  3. Agent: call addTulips. The call crosses to this browser, which runs its own tool.
  4. Agent: call readBasket. The agent reads what is in the basket.
  5. Agent: call deleteAccount. A name this page never offered. It is refused here.

Send a photo from your phone to this page as a stream

The idea: Sending a file from a phone to a laptop as a stream, with no upload to a server.

What you are looking at

The phone picks a picture and posts file.stream() into its port. A stream cannot be moved to another machine, so the port on this side hands over a new ReadableStream and feeds it with the bytes as they arrive over the direct connection. This page does not read it. It transfers the stream to a sandboxed viewer, which reads it chunk by chunk and draws the picture at the end. The phone's file is read only as fast as the viewer reads. No server sees any of it.

The code

// phone
const body = file.stream();
port.postMessage({ file: { name: file.name, size: file.size }, body }, [body]);

// this page: a stream arrived from another device. Pass it on unread.
port.onmessage = ({ data }) =>
  viewer.postMessage({ file: data.file, body: data.body }, "*", [data.body]);

// the viewer, a sandboxed frame
for await (const chunk of body) show(chunk);

Step by step

What each press of Next does in this demo.

  1. Open a line to your phone. This page opens a meeting place and shows a QR code. Scan it with a phone to be the other device.
  2. Use a stand-in for the phone. A second page plays the phone, and the two connect directly.
  3. Other device: send a sample picture. The other device posts a stream into its port. This page receives a stream and passes it to the viewer without reading it. The viewer draws the picture when the last byte arrives.
  4. Hang up. This page closes the connection.

Lend the other device a port to one thing, then take it back

The idea: Lending another device a port to one thing on this one, and taking it back without ending the connection.

What you are looking at

The connection between the two devices is one port. This page posts more ports into it. Each is a line to one sandboxed frame here: a lamp, and a counter. The phone receives each as a MessagePort of its own and uses it like any other. The lines pass through this page, so this page can close one. Take the lamp back and the phone's lamp button does nothing, while its counter port and the connection carry on. The phone was never given the page, only two ports.

The code

// this page: a line to the lamp that it can close
const toLamp = new MessageChannel(), toPhone = new MessageChannel();
lampFrame.postMessage({ cmd: "port" }, "*", [toLamp.port1]);
toPhone.port1.onmessage = (e) => toLamp.port2.postMessage(e.data);
toLamp.port2.onmessage = (e) => toPhone.port1.postMessage(e.data);

// a port, posted into the port that crosses devices
far.postMessage({ lent: "lamp", port: toPhone.port2 }, [toPhone.port2]);

// the phone
far.onmessage = ({ data }) => { data.port.postMessage({ do: "switch" }); };

// later, this page
toPhone.port1.close();

Step by step

What each press of Next does in this demo.

  1. Open a line to your phone. This page opens a meeting place and shows a QR code.
  2. Use a stand-in for the phone. A second page plays the phone, and the two connect directly.
  3. Lend the lamp. This page posts a port into the connection. The other device receives a port of its own that leads to the lamp.
  4. Lend the counter. A second port, to the counter. Both ride on the one connection.
  5. Other device: switch the lamp. The other device posts into its lamp port. The lamp frame here hears it and answers.
  6. Other device: add one. The same, on the counter's port.
  7. Take the lamp back. This page closes its end of the lamp's line.
  8. Other device: switch the lamp. The other device posts into its lamp port again. Nothing is on the other end.
  9. Other device: add one. The counter's port still works. Only one port was closed.

Common mistakes

  • A port or stream that crosses is a stand-in joined to the original. Its traffic passes through the page that opened the connection on each device. Close either page and everything riding on the connection ends.
  • A buffer is copied to the other device. Transferring it empties it on this side and saves nothing.
  • Blob, File, OffscreenCanvas, VideoFrame and shared memory do not cross. Send file.stream() for a file.
  • No browser tells a page when a port's other end has closed — the port close event was removed from the HTML standard in October 2026 — so a lent port that is closed on one device is not closed on the other. Posting into it does nothing. Send a message saying so.
  • There is no relay. Two networks that cannot reach each other directly will not connect.
  • The pairing code is the only secret. Anyone who has it while the line is open can join.

Measured

Chromium 157, between two pages on one computer: a 600 kB picture crosses as a stream and arrives whole, a port sent through the connection works on the far side, and closing one lent port leaves the others working. Not yet tested between two networks. Other browsers are being filled in from the lab's results.

Port patterns / The six basic patterns

Send a reply port with each request

What you are looking at

Instead of matching replies to requests with ids, make a new channel for each request and send one end along with it. The answer comes back on a port that only this request ever had. Answers can't get mixed up, and nobody else can answer in your place. The three boxes are frames in this page. This page gave each client its line to the service before the first press.

The code

function ask(service, question) {
  const { port1, port2 } = new MessageChannel();
  service.postMessage(question, [port2]);
  return new Promise((resolve) => (port1.onmessage = (e) => { resolve(e.data); port1.close(); }));
}

Using it

// a writing app. The service is a worker that checks spelling.
const service = new Worker("/spelling.js");

// two paragraphs are checked at the same time
const [intro, chapter] = await Promise.all([
  ask(service, { text: introText }),
  ask(service, { text: chapterText }),
]);
underline(introBox, intro);
underline(chapterBox, chapter);

// in spelling.js: answer on the port that came with the question
onmessage = async (e) => {
  const reply = e.ports[0];
  reply.postMessage(await mistakesIn(e.data.text));
};

// The short paragraph may be answered first. Each answer still reaches
// the ask() that sent its port. If the worker never answers, ask() waits
// for ever, so a real ask() also needs a timeout that closes port1.

Where you would use it

A real case. A writing app checks spelling in a worker. The page sends each paragraph as a question of its own while the person edits, so several questions are open at once. Each question carries its own reply port, so the result for a long chapter cannot land on the short introduction, whichever the worker finishes first. The worker keeps no list of who asked. It answers on the port that came with the question and forgets it.

How it works

Every question carries a new port, made for that one question. The service answers on it and forgets it. The answer can't be confused with any other, because that port is only used for this question.

This replaces the request id that most postMessage protocols use. There is no table of pending ids to keep, and a reply port can't be guessed or forged.

It also means the service does not need to know who is asking. It answers whoever holds the other end. A client can even hand its reply port to someone else, and the answer goes there.

Step by step

What each press of Next does in the demo at the top.

  1. Connect Client one. Client one gets a request channel to the service.
  2. Connect Client two. Client two gets its own request channel to the service.
  3. Client one asks. Client one sends a question along with a fresh reply port. The answer returns on that reply port, then it closes.
  4. Client two asks. Client two sends a question with its own reply port. Answers return on separate ports, so they can never be mixed up.

A long job that reports progress, and can be cancelled

The idea: Streaming answers: keep the reply port open and send progress on it until done. Cancelling: the client closes its end of the reply port and the service can stop work.

What you are looking at

The reply port does not have to carry one answer. This page asks a slow service for a job and keeps the reply port open. Progress arrives on it, ten per cent at a time. To cancel, this page says so on the same port and closes it. The service stops work, because nobody is waiting for the result any more.

The code

const { port1, port2 } = new MessageChannel();
service.postMessage({ job: "render" }, [port2]);
port1.onmessage = ({ data }) => data.done ? finish(data) : showProgress(data.percent);

// changed your mind
port1.postMessage({ cancel: true });
port1.close();

Step by step

What each press of Next does in this demo.

  1. Start a long job. The question goes out with a fresh reply port. Progress comes back on that port.
  2. Start a long job. The first job finished. Start a second one.
  3. Cancel it. This page tells the service to stop, on the reply port, and closes it. The service stops part-way.

Call a function on another origin and await the answer

The idea: Any request and response protocol over ports. It is what a remote procedure call library does underneath.

What you are looking at

Twelve lines turn the reply pattern into await call("add", 2, 3). Each call makes a channel, sends one end with the question, and returns a promise that settles when the other end speaks. Errors come back as rejections. Three calls made at once come back to the right callers, even when the slow one finishes last, because each has its own channel.

The code

const call = (method, ...args) => new Promise((resolve, reject) => {
  const { port1, port2 } = new MessageChannel();
  port1.onmessage = ({ data }) => { "error" in data ? reject(new Error(data.error)) : resolve(data.result); port1.close(); };
  service.postMessage({ method, args }, [port2]);
});

await call("add", 2, 3);       // 5, computed on another origin

Step by step

What each press of Next does in this demo.

  1. await call("add", 2, 3). A question goes out with a reply port. The promise resolves with the answer.
  2. await call("divide", 1, 0). The service refuses. The promise rejects with its message.
  3. Three calls at once. Three questions, three wires. The slow one comes back last and still reaches the right caller.

Things to try

  • Make both clients ask at once. Each gets its own answer on its own cable.
  • Ask several times from one client and watch a new cable appear for each question.

Common mistakes

  • A reply port that is never answered leaks until the page goes. Give requests a timeout.
  • A channel per request is cheap but it does cost something. For thousands of calls a second, batch.

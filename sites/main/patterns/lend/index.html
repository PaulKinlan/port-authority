Lend someone a network connection you opened

What you are looking at

The widget on the right is locked down so that it cannot reach the network at all. This page opens a WebSocket to the server and hands the widget the two streams that are the connection: one to write to, one to read from. The widget is now talking to the server. It never learns the address, it cannot open a second connection, and it keeps talking only until this page closes the socket. Hand over just the readable stream and it becomes a tap that can listen and not speak.

The code

const socket = new WebSocketStream(url);        // keep it: socket.close() ends the loan
const { readable, writable } = await socket.opened;
widget.postMessage({ readable, writable }, "*", [readable, writable]);

// the widget, which has no network of its own
await writable.getWriter().write("hello");
const { value } = await readable.getReader().read();   // the server's answer

Using it

// a team chat app, and a poll plug-in from another company in a sandboxed frame
// the frame's policy is default-src 'none', so the plug-in cannot open a connection itself
const socket = new WebSocketStream(url);          // url holds the person's session token
const { readable, writable } = await socket.opened;
widget.postMessage({ readable, writable }, "*", [readable, writable]);
// where WebSocketStream is missing, wrap a WebSocket in two streams and send those

// the plug-in: send a vote, then show the results for as long as the line is open
const writer = writable.getWriter(), reader = readable.getReader();
await writer.write(JSON.stringify({ vote: "Tuesday" }));
for (;;) {
  const { value, done } = await reader.read().catch(() => ({ done: true }));
  if (done) break;                                // the chat app closed the socket
  show(JSON.parse(value));
}

// the chat app: the person removes the plug-in, or leaves the room
removeButton.onclick = () => socket.close();
// The plug-in's read ends, and it has no other connection.

Where you would use it

A real case. A team chat app lets a room add a poll plug-in written by another company. The plug-in runs in a sandboxed frame whose content security policy is default-src 'none', so it cannot open a connection of its own. The chat app opens the WebSocket to the room, with the person's session token in the address, and hands the plug-in the two streams. The plug-in sends votes and reads results, and it is never given the address or the token. When the person removes the plug-in or leaves the room, the chat app closes the socket and the plug-in's streams end.

How it works

A WebSocket seen as streams is a readable for what the server says and a writable for what you say. WebSocketStream gives exactly that pair, and both can be transferred.

The widget's content security policy forbids all network access. It is handed the two streams and is now in conversation with the server. It never learns the address and cannot open a second connection.

The page kept the socket object. Closing it ends the widget's access at once. Hand over only the readable and the widget can listen and not speak.

Step by step

What each press of Next does in the demo at the top.

  1. Widget: try to connect by itself. The widget tries to reach the server by itself. Its rules forbid any network access.
  2. Open a connection to the server. This page opens a WebSocket.
  3. Lend the widget the connection. The two streams of that connection are handed to the widget.
  4. Widget: say hello to the server. The widget writes into the connection, and the server's answer comes back to it. It still has no network of its own.
  5. Close the connection. This page closes the socket, and the widget is cut off.

Give a logger the incoming half of a connection only

The idea: Read-only taps for logging or debugging.

What you are looking at

A WebSocket seen as streams has two halves. This page keeps the half that speaks and gives a logger only the half that listens. The logger has no network access of its own. It records everything the server says, and it has no way to send the server anything, because it was never given anything to write into.

The code

const { readable, writable } = await new WebSocketStream(url).opened;
logger.postMessage({ readable }, "*", [readable]);   // listening half only
const writer = writable.getWriter();                 // this page keeps the voice
writer.write("hello");

Step by step

What each press of Next does in this demo.

  1. Open a connection. This page opens a WebSocket to the server.
  2. Give the logger the listening half. Only the readable stream is handed over.
  3. This page: say something. This page speaks. The server's answer goes to the logger.
  4. Logger: try to speak. The logger has nothing to write into.

Sign in on the page, then hand the open session to a worker

The idea: A page that authenticates and then delegates the open session to a worker.

What you are looking at

The page signs in to an account service on another origin and gets back a port: the open session. The page does not need it. Its worker does, to keep the balance fresh in the background. So the page posts the port to the worker. The session is not copied and nobody signs in twice. The worker now holds it, and the page's own variable holds a dead port.

The code

const session = await signIn(password);         // a port to the account service
worker.postMessage({ session }, [session]);     // the worker has it now
session.postMessage({ ask: "balance" });        // goes nowhere: this end has left

Step by step

What each press of Next does in this demo.

  1. Sign in. The page sends a password and gets a session back, as a port.
  2. Hand the session to my worker. The port moves to the worker, which starts asking for the balance.
  3. Page: try to use the session. The page still has its variable. The port behind it has gone.

Common mistakes

  • Where WebSocketStream is missing the demo wraps a WebSocket in streams, and then every message passes through the page.
  • The same idea should hold for WebTransport streams. This site has not measured that yet.

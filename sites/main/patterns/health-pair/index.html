Port patterns / Knowing the other side is still there

Send a second port with the first, only for health checks

What you are looking at

A port does not tell you when its other end has gone. Posting into it still works, and nothing comes back. So this page sends the far side two ports at once. The first carries the work: a flower name goes in, a price comes out, and that is the whole protocol. The second carries pings and their answers and nothing else. The page pings once a second. One missed answer is late. Three in a row and the page treats the far side as gone. A page that is closing says goodbye on the health port as it goes, so most endings are seen at once and the pings are there for the ones that are not.

The code

import { watch, answer } from "/alive.js";

// this page
const data = new MessageChannel(), health = new MessageChannel();
frame.postMessage("ports", origin, [data.port2, health.port2]);
watch(health.port1, { every: 1000, misses: 3,
  onState: (state) => state === "silent" || state === "closed" ? giveUp() : null });

// the far side
onmessage = ({ ports: [data, health] }) => {
  data.onmessage = (e) => data.postMessage(price(e.data)); // no health logic here
  answer(health);  // answers pings, and says goodbye on pagehide
};

Using it

// a shop's basket page, and a delivery-price frame from a courier's site
// the same watch() call, with what it returns kept, so that giveUp() can stop the pings
const watcher = watch(health.port1, { every: 1000, misses: 3,
  onState: (state) => state === "silent" || state === "closed" ? giveUp() : null });

// work goes on the data port: a postcode in, a price out
data.port1.onmessage = (e) => { deliveryPrice.textContent = e.data; };
postcode.onchange = () => data.port1.postMessage(postcode.value);

// three pings went unanswered, or the frame said goodbye as it went
function giveUp() {
  watcher.stop();
  data.port1.close(); health.port1.close();
  courierFrame.remove();
  deliveryPrice.textContent = "No delivery price at the moment. You can still order.";
  retryButton.hidden = false;   // a press loads the frame again and sends it two new ports
}

Where you would use it

A real case. A shop's basket page embeds a delivery-price frame from a courier's site. The page sends the frame two ports when it loads, one for postcodes and prices and one for pings. If the frame's page crashes, hangs or is navigated away, a postcode posted into the data port gets no price and no error. After three missed pings, or a goodbye, the shop calls giveUp(): it stops the pings, closes its two ports, removes the frame and tells the person they can still order. Without the health port the price would stay at its last value and the person would wait.

How it works

A port has no state you can read and no event for the other end going away. If the page at the other end is closed, navigated, crashed or stuck, postMessage still returns normally and the message is dropped or waits. The only way to know is to hear something from the other side, regularly, and to treat a long silence as the other side being gone.

Doing that on the data port means every message on it needs a type, so that a ping can be told from a price, and the far side's work code has to answer pings. Sending a second port keeps the two apart. The data port's protocol stays exactly what it was. The health port carries { ping: n } one way and { pong: n } back, and the code that handles it can be the same small file in every project: /alive.js.

The far side also tells what it knows about itself. A page that is closing or navigating fires pagehide, and the far side posts a goodbye on the health port from that handler. That arrives in a few milliseconds, so the common endings are seen at once. The pings are for the endings that give no warning: a crash, a frozen thread, a page that called close() on its ports.

Silence doesn't prove it has gone. A far side in a long loop is alive and will answer later, which is why the demo's busy far side goes from silent back to alive. And if this page's own timer runs late, because this page was the busy one, the missed answers say nothing about the far side, so the count starts again.

There is no close event to wait for instead. One was added to the HTML standard in January 2024 and taken out again on 2 October 2026, with the note that no browser ships it. Chrome built it behind a flag and said it would not ship it as written, because it let a page observe garbage collection. /alive.js listens for it anyway where a browser has it, since nothing is quicker.

Step by step

What each press of Next does in the demo at the top.

  1. Connect. This page makes two channels and sends one end of each to a page on the florist's site. Pings start on the second.
  2. Ask the price of tulips. The question and the answer go on the first port. The health port is not involved.
  3. Far side: busy for 5 seconds. The far side runs a long loop and answers nothing. One missed ping is late, three is silent. When the loop ends it answers again and is alive.
  4. Remove the far side. The frame is destroyed. Its page said goodbye on the health port as it went, so this page knew at once.

What you could build with it

Already running

  • Tell the person that a tool they were using has gone, instead of leaving them waiting. See the demo at the top of this page.
  • Restart a worker that has stopped answering and send it the questions it had not answered. See a worker restarted when it stops answering.

Things to try

  • Make the far side busy and watch the state go late, silent, then alive again when its loop finishes.
  • Ask the price of tulips while the far side is busy. The answer arrives after the loop, because the question waited in the port.
  • Close the far side's ports instead of removing it. No goodbye is sent, and only the missed pings show it.

Common mistakes

  • Do not treat one missed ping as death. A busy main thread, a slow device or a garbage collection pause all delay answers. Count misses.
  • A page that has been hidden for a minute or more can answer slowly. Each answer says whether its page is hidden, and watch() then allows a minute between answers instead of a second.
  • Pings that are answered prove the thread is running, not that the work is going well. Put a timeout on work too.
  • A goodbye is sent from pagehide. It is not sent when a process crashes or a worker is terminated: no code of the dying side runs.
  • pagehide with persisted: true means the page is going into the back/forward cache and may come back. Treat it as paused, not gone. /alive.js does, and gives up after ten minutes if it does not return.

Measured

Chromium 153: the goodbye from a removed frame on another site arrives in under 200 ms, usually under 10. A frame busy for 5 seconds is late after 1 second, silent after 3, and alive again as soon as its loop ends. Other browsers are being filled in from the lab's results.

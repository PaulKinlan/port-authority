Port patterns / Knowing the other side is still there

Let the far side make the health channel and send a port back

What you are looking at

Here the page sends only one port, the one for work, the same as it would with no health checks at all. When the far side receives it, it makes a channel of its own for health checks and sends one end back. Each side set up exactly one channel. The page does not have to know in advance that the far side does health checks: if a port comes back, it watches it. If none comes, it carries on without. The far side decides how it is watched.

The code

// this page: one port, as usual
const data = new MessageChannel();
frame.postMessage("port", origin, [data.port2]);
addEventListener("message", (e) => {
  if (e.source === frame && e.data === "health") watch(e.ports[0], { onState });
});

// the far side: make the health channel, keep one end, send the other back
onmessage = ({ source, ports: [data] }) => {
  serve(data);
  const health = new MessageChannel();
  answer(health.port1);
  source.postMessage("health", "*", [health.port2]);
};

Using it

// an address-lookup frame from a postal service, embedded by many shops
// a shop that knows about health checks. This is its onState.
function onState(state) {
  if (state === "alive") lookupNote.textContent = "";
  if (state === "late") lookupNote.textContent = "Address lookup is slow.";
  if (state === "silent" || state === "closed") {
    lookupNote.textContent = "Address lookup has stopped. Type your address below.";
    addressFields.hidden = false;
  }
}

// work is the same whether a health port came back or not
data.port1.onmessage = (e) => showAddresses(e.data);
postcode.onchange = () => data.port1.postMessage(postcode.value);

// an older shop has no listener for "health". The port that comes back is never read.
// Its lookups work as before, and it cannot tell when the frame stops.

// the far side's serve(): a postcode in, addresses out, and nothing about health
function serve(data) {
  data.onmessage = (e) => data.postMessage(addressesFor(e.data));
}

Where you would use it

A real case. A postal service offers an address-lookup frame that many shops embed, and each shop sends it one port for postcodes and addresses. The postal service adds health checks to the frame and leaves the lookup messages as they were: the frame now makes a second channel and posts one end back. A shop whose page was written before that has no listener for it, and its lookups work as before. A shop that listens for the health message watches the port, and when the frame goes silent it shows plain address fields for the person to fill in. No shop had to change its code on the day the frame changed.

How it works

The previous pattern needs the caller to know, before it sends anything, that the far side does health checks. Here the far side decides. The caller sends one port, the same as it would with no health checks at all. The far side makes a second channel, keeps one end, and posts the other end back to whoever sent the first.

So each side makes exactly one channel and handles one kind of message on each port. A caller that has never heard of health checks still works: a port arrives back and is never read, which costs nothing. A caller that knows about them watches it.

The port comes back the way the first came in. From a frame that is parent.postMessage. From a worker it is postMessage on the worker's global. Over a port it can be sent back on the data port itself, as the only message that carries a port, so the data protocol still needs no types.

Step by step

What each press of Next does in the demo at the top.

  1. Connect. This page sends one port. The far side makes a second channel and sends an end back. That end is drawn as it arrives.
  2. Ask the price of tulips. Work goes on the port this page made.
  3. Far side: close its ports. The far side calls close() on both of its ports. Nothing is said: close() is silent. The pings stop being answered, and after three this page gives up.

What you could build with it

Already running

  • A service that callers can watch if they know about health checks, and use as normal if they do not. See the demo at the top of this page.

Things to try

  • Connect and watch the black cable appear from the far side, a moment after the teal one.
  • Close the far side's ports. close() sends nothing to the other end, so it takes three missed pings to notice.

Common mistakes

  • If the health port can arrive on the data port, check event.ports before treating a message as data.
  • The far side chooses how often it is pinged only if you let it. Here the caller still sets the interval.

Measured

Chromium 153: after the far side calls close() on both its ports, nothing arrives at this page. Three missed pings at one a second mark it silent after about 3 seconds. Other browsers are being filled in from the lab's results.

Port patterns / Between real sites

Pipe your data through another site, and get it back

What you are looking at

A transform has two ends, and both can be given away. The library's site makes one that blacks out email addresses and long numbers, and hands this page the end to write into and the end to read from. From here it is an ordinary pipeThrough: your lines go in, cross to the library's origin, are changed by code this page never loads or sees, and come back. Back-pressure crosses with them.

The code

// the library, on its own origin
const { readable, writable } = new TransformStream({ transform: redact });
parent.postMessage({ readable, writable }, "*", [readable, writable]);

// this page
myLines.pipeThrough({ readable, writable }).pipeTo(screen);

Using it

// a support desk app, and a redaction service from another company in a frame
// the service: redact is an ordinary transform function
const redact = (line, controller) =>
  controller.enqueue(line.replace(/[0-9][0-9 -]{6,}[0-9]/g, "[number]"));

// the support desk: take the two ends from the service's origin and from nowhere else
addEventListener("message", (e) => {
  if (e.origin !== serviceOrigin || !e.data?.readable) return;
  const { readable, writable } = e.data;
  // chat is the WebSocket that carries what the customer types
  const myLines = new ReadableStream({ start(c) { chat.onmessage = (m) => c.enqueue(m.data); } });
  const screen = new WritableStream({ write(line) { agentView.append(line); } });
  myLines.pipeThrough({ readable, writable }).pipeTo(screen);
});

// If the service's frame is removed, lines stop coming back and no error is raised.
// The support desk times each line, and shows a fault when one is late.

Where you would use it

A real case. A support desk app shows agents what customers type in a chat, and customers sometimes type card numbers. The app pipes every line through a redaction service from another company, which runs in a frame on its own origin and hands over both ends of its transform. The service's code is never loaded into the app's page, and the service sees only the lines that are piped to it. The app does trust the service with those lines. If the service's frame is removed the pipe stops with no error, so the app keeps a timer and reports a fault when a line is late.

How it works

A TransformStream has a writable end and a readable end, and both are transferable. The library makes one that redacts text and gives this page both ends.

From here it is an ordinary pipeThrough. Lines written here cross to the library's origin, are changed by code this page never loads, and come back through the readable end.

The transform runs with the library's origin, storage and code. This page sees only what goes in and what comes out. Back-pressure crosses both ways, so the library cannot be flooded.

Step by step

What each press of Next does in the demo at the top.

  1. Ask the library for its transform. The library's site makes a transform and gives this page both of its ends.
  2. Send a line through it. A line with an email address goes to the library's origin and comes back blacked out.
  3. Send a line through it. A card number goes through the same pipe.

An encryption service you pipe through, whose key you never hold

The idea: Translation, redaction, compression or encryption offered by another origin as a pipe. A paid service whose code and keys stay on its own origin.

What you are looking at

The cipher service makes a key that cannot be read, even by itself, and offers two pipes: one that seals and one that opens. This page writes a line into the first and gets back bytes it cannot read. It writes those bytes into the second and gets its line back. The key, and the code that uses it, stay on the service's origin. It could meter each line and charge for it, and this page would have no way around that.

The code

// the service
const seal = new TransformStream({ async transform(text, out) {
  const iv = crypto.getRandomValues(new Uint8Array(12));
  out.enqueue({ iv, data: await crypto.subtle.encrypt({ name: "AES-GCM", iv }, key, encode(text)) });
} });
parent.postMessage({ seal: { readable: seal.readable, writable: seal.writable } }, "*", [seal.readable, seal.writable]);

// this page
lines.pipeThrough(seal).pipeTo(storage);

Step by step

What each press of Next does in this demo.

  1. Ask the cipher service for its pipes. The service makes a key and hands over both ends of two transforms.
  2. Seal a line, then open it. A line goes into the sealing pipe and comes back as bytes. Those bytes go into the opening pipe and come back as the line.
  3. Seal a line, then open it. A second line. The key never left the service.

Three parties each supply one stage, and none of them sees the others

The idea: Chaining several origins' transforms with repeated pipeThrough.

What you are looking at

A zipped order needs unzipping, turning from bytes into text, and its card number hiding before it is shown. Each of those is a stream stage supplied by a different origin. This page asks each for a stage, joins the three end to end and sends the file through. This page holds both ends of every stage, so the data comes back here between one stage and the next. Each party sees only what flows through its own stage, and none of them needs to know the others exist.

The code

// each party
const stage = new TransformStream({ transform(chunk, out) { out.enqueue(work(chunk)); } });
parent.postMessage({ readable: stage.readable, writable: stage.writable }, "*", [stage.readable, stage.writable]);

// this page
zippedFile.pipeThrough(unzip).pipeThrough(decode).pipeThrough(redact).pipeTo(screen);

Step by step

What each press of Next does in this demo.

  1. Ask each party for a stage. Three origins each hand over both ends of one transform.
  2. Pour a zipped order through all three. Bytes go in at one end. Readable text with the card number hidden comes out of the other.

Things to try

  • Ask for the transform and send lines through it. Compare what went in with what came back.
  • Send the line with nothing secret in it. It returns unchanged.

Common mistakes

  • You are trusting the other origin with the data that goes in. The pattern hides their code from you, not your data from them.
  • If their frame goes away the pipe stalls with no error.

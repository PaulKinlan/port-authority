Port patterns / Between real sites

Send only the readable side of a stream

What you are looking at

A stream has a direction, and you can hand over one direction without the other. The library's site gets only something to read from: it can listen and has nothing to speak into. The florist's site gets only something to write into: it can post notes through the slot and cannot see what else is inside. The owner can cut either one off. Close the feed and the listener is told it has ended. Shut the box and the next write fails.

The code

// listen only
library.postMessage({ readable }, origin, [readable]);

// write only
const writable = new WritableStream({ start(c) { box = c; }, write: keep });
florist.postMessage({ writable }, origin, [writable]);
box.error(new Error("shut"));               // later: their next write fails

Using it

// a town noticeboard page, with the library's frame and the florist's frame in it
const readable = new ReadableStream({ start(c) { feed = c; } });
const keep = (notice) => feed.enqueue(notice);   // what a shop writes goes on the board

// the library: show each notice. Its stream has no method that writes.
const reader = readable.getReader();
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;                               // the noticeboard closed the feed
  show(value);
}

// the florist: send a notice in. It has nothing to read with.
const writer = writable.getWriter();
try { await writer.write("Tulips, half price on Friday"); }
catch { show("The noticeboard has shut our box"); }

// the noticeboard: the florist sends too many adverts
box.error(new Error("shut"));                    // the florist's next write fails
// the noticeboard: the board is taken down
feed.close();                                    // the library's next read says done

Where you would use it

A real case. A town noticeboard site embeds two other sites in frames. The library's frame shows the notices on a screen in its hall, so it is given the readable stream, which has no method that writes. The florist's frame sends notices in, so it is given a writable stream of its own and cannot read what other shops have sent. When the florist sends too many adverts, the noticeboard calls box.error() and the florist's next write fails, while the other shops' streams still work. When the board is taken down, the noticeboard closes the feed and the library's reader is told the stream has ended.

How it works

A readable stream can only be read and a writable stream can only be written. Each is transferable by itself. So if you hand someone one of them, they get one direction of the conversation.

The library gets a readable. It has no method that writes. The florist gets a writable. It has no method that reads, so it can drop notes into a box whose other contents it cannot see.

The owner made both streams and kept their controllers. Closing the feed ends the listener's stream cleanly. Erroring the box makes the writer's next write fail.

Step by step

What each press of Next does in the demo at the top.

  1. Give the library the listening half. The library's site gets a stream it can only read. This page keeps the controller.
  2. Give the florist the writing half. The florist's site gets a stream it can only write into.
  3. Florist: drop a note. The florist writes a note. It lands here, and the florist cannot see what else is in the box.
  4. Close the feed. This page ends the feed. The library is told it is over.
  5. Shut the drop box. This page shuts the box.
  6. Florist: drop a note. The florist's next note is refused.

A sealed bid box that two rivals write into

The idea: A submission box that accepts input from many parties who cannot see each other's.

What you are looking at

Two bidders on two origins each get something to write into, and nothing to read from. Their bids land in this page. Neither can see the other's bid, or even whether the other has bid. When the owner closes the box, both writers are refused from then on. It is a sealed auction with no server.

The code

const makeSlot = (who) => new WritableStream({
  start(controller) { slots.push(controller); },
  write(bid) { bids.push({ who, bid }); },
});
const slot = makeSlot("one");
bidderOne.postMessage({ slot }, "*", [slot]);   // write only
// closing time
slots.forEach((s) => s.error(new Error("bidding has closed")));

Step by step

What each press of Next does in this demo.

  1. Give each bidder a slot. Each bidder gets a stream it can write to and cannot read.
  2. Bidder one: bid. Bidder one's bid arrives here. Bidder two is told nothing.
  3. Bidder two: bid. Bidder two bids without knowing what it is up against.
  4. Close the box. The owner shuts both slots and names the winner.
  5. Bidder one: bid. A late bid is refused.

One feed, with a writing role and a reading role

The idea: Read-only and write-only views of the same resource for different roles.

What you are looking at

A greenhouse sensor should be able to report and never read. A dashboard should be able to read and never report. This page makes one stream and gives the writing end to the sensor and the reading end to the dashboard. Nobody has to check the roles. The sensor holds an object with no way to read, and the dashboard holds one with no way to write. The stream was made in this page and still runs through it, so readings stop if this page closes.

The code

const { readable, writable } = new TransformStream();
sensor.postMessage({ feed: writable }, "*", [writable]);       // can write, cannot read
dashboard.postMessage({ feed: readable }, "*", [readable]);    // can read, cannot write

Step by step

What each press of Next does in this demo.

  1. Give out the two ends. The sensor gets the writing end and the dashboard the reading end. This page keeps neither end, but the stream still runs through it.
  2. Sensor: report a reading. A reading goes from the sensor, through the stream in this page, to the dashboard.
  3. Sensor: try to read the feed. The sensor's end has nothing to read with.
  4. Dashboard: try to write a reading. The dashboard's end has nothing to write with.

Already running

  • A log or metrics feed that a third party may watch and not influence. See the demo at the top of this page.

Things to try

  • Give out both halves, drop a note, then close the feed and shut the box.
  • After shutting the box, drop another note and read the florist's log.

Common mistakes

  • A write can resolve before the far side refuses it. Do not treat a resolved write as delivered.
  • Erroring a stream is final. Make a new one to reopen.
  • The listening half is not fully one-way. The listener chooses when to read and the owner can see that. A frame sends a word back this way.

Port patterns / More things a port can carry

Tear a live widget off into its own window

What you are looking at

A port works the same in whichever window holds it. The meter here is fed by a service on another origin. Tear it off and the port is posted to a new window, which carries on from the next tick with no reconnect. Put it back and it returns the port.

The code

const win = window.open("/meter.html", "", "popup");
// once it says it is ready
win.postMessage({ feed: port }, location.origin, [port]);

Using it

// a share dealing page, with a live price meter the person moves to a second screen
// /meter.html, in the new window: say it is ready, then take the port
let port = null;
opener.postMessage("ready", location.origin);
addEventListener("message", (event) => {
  if (event.origin !== location.origin || !event.data.feed) return;
  port = event.data.feed;
  port.onmessage = (e) => showPrice(e.data);        // the next price arrives here
});
// the person closes the new window: post the port back first
addEventListener("pagehide", () => { if (port) opener.postMessage({ back: true }, location.origin, [port]); });

// the dealing page: send the port on "ready", and take it back later
addEventListener("message", (event) => {
  if (event.source !== win || event.origin !== location.origin) return;
  if (event.data === "ready") win.postMessage({ feed: port }, location.origin, [port]);
  if (event.data.back) { port = event.ports[0]; port.onmessage = (e) => showPrice(e.data); }
});
// If the new window is killed, pagehide does not run and the port is lost.
// The page can watch win.closed, and ask the feed for a new port.

Where you would use it

A real case. A share dealing page shows a live price meter. The prices arrive on a port from a frame run by the market data company, which the person signed in to once. The person wants the meter on a second screen while they fill in an order. The page opens a small window and posts the port to it, so the meter carries on from the next price with no new sign-in and no reconnect. When the person closes the small window it posts the port back, and the meter in the page starts again.

How it works

A widget in a frame holds a port to the page. The page opens a new window, and the widget's port is posted on to that window. A port works the same in whichever window holds it, so the conversation carries on.

No state is serialised and nothing reconnects. The same wire that fed the embedded widget now feeds the window. Queued messages are not lost in the move.

This works because a port isn't tied to the context that made it.

Float a tool above every other window, without moving its port

The idea: Moving a tool from a sidebar into Document Picture-in-Picture.

What you are looking at

Document Picture-in-Picture gives a page a small window that stays on top of everything. It differs from tearing off into a popup in one useful way: the new window has no script of its own. This page's script keeps running it. So the meter's element moves into the floating window and the port stays exactly where it was. Close the floating window and the element comes home. This needs Chrome or Edge on a desktop, and a real press of the button.

The code

const pip = await documentPictureInPicture.requestWindow({ width: 260, height: 150 });
pip.document.body.append(meter);          // the element moves
port.onmessage = ({ data }) => { meter.textContent = data; };   // the port and its listener do not
pip.addEventListener("pagehide", () => sidebar.append(meter));

Replace a running widget with its next version, and keep its connection

The idea: Handing a live session from one frame to its replacement during an upgrade.

What you are looking at

Version 1 of a chat widget is holding a port to a service that sends it numbered messages. Version 2 is ready. Loading it the usual way would mean dropping the connection and making another, and losing whatever arrived in between. Here version 1 stops listening, hands its port to version 2, and is removed. Messages that arrive during the swap wait in the port. The service is never told that anything changed.

The code

// version 1, when asked to step aside
port.onmessage = null;                                       // stop reading: what arrives now will wait
parent.postMessage({ handover: true, last }, "*", [port]);

// version 2
port.onmessage = ({ data }) => { /* carries on from last + 1 */ };

Step by step

What each press of Next does in this demo.

  1. Connect version 1 to the service. The service starts sending numbered messages down a port.
  2. Load version 2 and hand over. Version 1 gives up its port and is removed. Version 2 picks up at the next message.

Things to try

  • Tear the widget off. The count in the new window carries on from where the embedded one stopped.
  • Close the new window and start again.

Common mistakes

  • Browsers only open a window in answer to a real press.
  • If the page that opened the window reloads, the window's port to it is dead unless it was banked first. See keeping a port across a reload.

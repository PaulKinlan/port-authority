Port patterns

Thirty-three live demos showing what MessageChannel and MessagePort can do. Each box below is a real page, frame or worker. A solid cable appears when a port arrives, and each dot is a real message. A dashed line is something that is not a port, such as a stream, and says what it is.

How to read the diagrams

Windows, frames and workers are drawn differently, and each page and frame shows its address. There is a key under each diagram.

  • Window A top-level page in a tab or window of its own. Its address is in the bar at the top.
  • <iframe> A page embedded in this one. Its address is written underneath. One marked sandbox with the address about:srcdoc has no site behind it: this page wrote its HTML, and the sandbox gives it an opaque origin, which matches no other origin. It stands in for code from someone else.
  • Worker A background thread that belongs to one page. The script it runs is written underneath.
  • SharedWorker One background thread that every page of a site can connect to.
  • Service Worker A background thread that answers network requests for one part of a site. The browser starts and stops it.
  • AudioWorklet Code that runs on the thread that produces sound.
  • Another device A browser on a different machine.
  • In this page Something the page draws itself. It is not a separate page or thread.
  • MessageChannel A solid cable is one channel. The plug at each end is one of its two ports, and a moving dot is a message. The line a page has to its own worker, and a tab has to a shared worker, is a pair of ports too.
  • Stream A dashed line marked stream is a ReadableStream or WritableStream that was transferred. Chunks go one way, towards the arrow.
  • postMessage, no channel A dashed line marked postMessage is a message sent straight to a window or a service worker. Neither side keeps a port.
  • fetch A dashed line marked fetch is a network request that a service worker answers.
  • WebRTC data channel A dashed line marked WebRTC is a direct connection to another device. Each side wraps its end so that it can be used as a MessagePort.

Open a channel and send a message through it

new MessageChannel() gives you two entangled ports. Keep one, post the other to anyone you can already reach. From then on the two of you have a line of your own. What goes down it is not a window message, so a script that listens for window.postMessage messages does not see it.

const { port1, port2 } = new MessageChannel();
frame.contentWindow.postMessage("here", "*", [port2]); // port2 is moved, not copied
port1.onmessage = (e) => console.log(e.data);
port1.postMessage("ping");

Connect two sites to each other, then remove yourself

A port can be passed on by whoever holds it. So a third party that knows two sites can make a channel, give each of them an end, and step away. The three windows are three different sites, and each address is in its bar. So that you can see all three at once, each is shown as a frame inside this page. A site cannot go and find the introducer. Two windows that have nothing to do with each other cannot reach each other in a browser at all. A first line exists only because one window opened the other, or one is a frame inside the other. So an introducer is a window a site opens, or a window that opens the sites, or a page that holds them as frames. This page stands in for that: it holds all three, and hands Site A and Site B their first lines. Close the introducer and the other two do not notice. This is how the hub works.

// in the introducer, which holds a port to each side
const { port1, port2 } = new MessageChannel();
toLeft.postMessage({ meet: "right" }, [port1]);
toRight.postMessage({ meet: "left" }, [port2]);
// nothing else to do. It can close.

Send a reply port with each request

Instead of matching replies to requests with ids, make a new channel for each request and send one end along with it. The answer comes back on a port that only this request ever had. Answers can't get mixed up, and nobody else can answer in your place. The three boxes are frames in this page. This page gave each client its line to the service before the first press.

function ask(service, question) {
  const { port1, port2 } = new MessageChannel();
  service.postMessage(question, [port2]);
  return new Promise((resolve) => (port1.onmessage = (e) => { resolve(e.data); port1.close(); }));
}

Give a frame limited access, then revoke it

Holding a port is the permission to use it. The owner here doesn't hand out its real port. It makes a new channel, keeps one end, and only answers read on it. To revoke, it closes its end. It needs no account, token or list of who is allowed. The two boxes are frames in this page and have no line to each other at the start, so the owner hands the new port to this page, which passes it to the guest.

function readOnly(counter) {
  const { port1, port2 } = new MessageChannel();
  port1.onmessage = (e) => port1.postMessage(e.data === "read" ? counter.value : "denied");
  return { port: port2, revoke: () => port1.close() };
}

Use a SharedWorker to connect tabs to each other

Every tab on an origin can reach the same SharedWorker. Here it keeps a port to each tab and does one job: when a tab joins, it makes a channel between that tab and every other, then stays out of it. The tabs talk directly. Open a third in a new tab and it joins the same mesh.

// in the SharedWorker
const peers = new Set();
onconnect = ({ ports: [port] }) => {
  port.onmessage = ({ data: { name } }) => {     // each tab says its name once
    for (const other of peers) {
      const { port1, port2 } = new MessageChannel();
      port.postMessage({ meet: other.name }, [port1]);
      other.port.postMessage({ meet: name }, [port2]);
    }
    peers.add({ name, port });
  };
};

Send a stream to another frame

A ReadableStream is transferable too, so you can hand another origin a live stream and it reads with back-pressure, as if the source were local. Chrome and Firefox can do this today.

const stream = new ReadableStream({ pull(controller) { controller.enqueue(nextChunk()); } });
port.postMessage({ stream }, [stream]);

// other side
port.onmessage = async ({ data }) => { for await (const chunk of data.stream) use(chunk); };

What a port can carry and where it can end up. These use newer parts of the platform, so some won't work in every browser.

Let another origin paint on your page

The painter is a frame on another origin. It draws on a canvas of its own and sends each finished frame down a port as an ImageBitmap, which is moved and not copied. This page shows each one in a canvas it owns. The painter cannot read or touch anything here. Handing over the canvas's own drawing surface would be shorter, but Chrome crashes a frame in another process that draws on one, so that is kept for workers.

// the other origin: draw, then send the finished frame
const mine = new OffscreenCanvas(width, height);
const ctx = mine.getContext("2d");
requestAnimationFrame(async function draw(t) {
  paint(ctx, t);
  const frame = await createImageBitmap(mine);
  port.postMessage({ frame }, [frame]);       // moved
  requestAnimationFrame(draw);
});

// this page: show it
const show = canvas.getContext("bitmaprenderer");
port.onmessage = ({ data }) => show.transferFromImageBitmap(data.frame);

Pass a function to another origin

A function cannot be cloned, but a port can stand in for one. Wrap the function in a channel, send the other end, and the receiver gets something it can call. Arguments can be functions too, the same way. Close the port and the function stops existing for them. This is how Comlink works underneath.

const lend = (fn) => {
  const { port1, port2 } = new MessageChannel();
  port1.onmessage = (e) => fn(...e.data);
  return { port: port2, revoke: () => port1.close() };   // send port, keep revoke
};
const borrow = (port) => (...args) => port.postMessage(args);

Move 64 MB between origins without copying it

Post an ArrayBuffer and it is copied. Put it in the transfer list and the memory itself changes hands: the sender's buffer drops to zero bytes and the cost stops depending on size. Each button sends 64 MB to another origin and back, and times the round trip.

port.postMessage(buffer);            // structured clone: a copy each way
port.postMessage(buffer, [buffer]);  // transfer: buffer.byteLength is now 0

Serve pages to other tabs from this tab

A Service Worker can answer a fetch any way it likes, including by asking someone else. This page hands the worker a port. Every request under /patterns/served/ is sent up that port, and whatever you type on the left is the response. The page on the right is a real navigation to a real URL, and so is the new tab.

// Service Worker
onfetch = (event) => event.respondWith(new Promise((resolve) => {
  const { port1, port2 } = new MessageChannel();

A forwarded stream stops when the page that passed it on closes. A port keeps working.

You can pass a stream on, the same as a port. But a stream that was passed on keeps flowing through every context that touched it. Send one through the introducer, remove the introducer, and the reader stalls with no error and no end. So introduce with a port first, then send the stream down the direct line. Start again between the two to compare. The three boxes are frames in this page, and this page gave the source and the reader each a line to the introducer.

// fragile: the middle is now part of the pipe for ever
toMiddle.postMessage({ stream }, [stream]);

// sturdy: the middle only introduces
const direct = await introducedPort();
direct.postMessage({ stream }, [stream]);

Back-pressure across three origins

This page hands its stream to a frame on another origin. That frame transforms it and hands the result to a frame on a third origin, down a port it holds to that frame. Nothing is buffered without limit: pause the reader and, a few chunks later, the source stops being asked for more.

// the transformer, on its own origin
port.onmessage = ({ data }) => {
  const out = data.readable.pipeThrough(new TransformStream({ transform: shout }));
  toReader.postMessage({ readable: out }, [out]);   // a port to the third origin
};

Keep a port across a page reload

A port cannot be saved. IndexedDB, sessionStorage and history state all refuse it, because a port can be moved but never copied. But you can leave it with a SharedWorker. As this frame unloads it posts its port to the worker, and when it loads again it asks for it back. The worker is created with extendedLifetime, so it outlives the page even when that page was its only client. The feed doesn't notice. Ticks sent during the reload waited in the port, and the count has no gaps. The dark cable is the frame's own connection to the worker. The other one is the port that is kept, which this page made and gave to the feed and the frame.

const bank = new SharedWorker("/bank.js", { extendedLifetime: true });
addEventListener("pagehide", () => bank.port.postMessage({ deposit: key }, [port]));

// next load
bank.port.postMessage({ withdraw: key });
bank.port.onmessage = ({ data, ports }) => data.found ? resume(ports[0]) : connectAgain();

A worker that routes between windows that have never met

The three windows above the router know two things each: their own name, and how to reach the router. None of them has a reference to another, and none of them holds a port of another's. To reach the kitchen, the orders window posts a message to the router addressed to "kitchen". The router looks the name up and passes the message on, with the sender's name attached. Address a name nobody has and the router says so. The router here is a SharedWorker. Each box is a real page of this site, and the link opens a fourth window that can join in.

// every window: say who you are, then address others by name
const { port } = new SharedWorker("/router-worker.js");
port.postMessage({ iam: "orders" });
port.postMessage({ to: "kitchen", text: "two tulip bunches" });
port.onmessage = ({ data }) => show(data.from, data.text);

// the router: a table of names, and nothing else
onconnect = ({ ports: [port] }) => {
  port.onmessage = ({ data }) => {
    if (data.iam) return table.set(data.iam, port);
    const target = table.get(data.to);
    target ? target.postMessage({ from: nameOf(port), text: data.text })
           : port.postMessage({ undelivered: data.to });
  };
};

Across threads

A port can be held by a worker, and it can carry video frames or requests to sign with a key.

Two workers that keep talking while this page is frozen

A port given to a worker belongs to that worker's thread. Introduce two workers to each other and their messages never touch the page again. Freeze this page for three seconds: its own counter stops, the buttons go dead, and the two workers carry on. You can watch them do it, because each one paints its numbers into a canvas whose drawing surface it was handed, and a transferred canvas does not wait for the page either.

const { port1, port2 } = new MessageChannel();
workerA.postMessage({}, [port1]);
workerB.postMessage({}, [port2]);
// this page is now out of the conversation, and can stall without harm
while (performance.now() < until) {}

Run live video through a filter on another origin

Video can leave your page one frame at a time and come back changed. The picture on the left is drawn by this page, and it is your camera if you turn that on. The filter lives on another origin, in a sandbox. It has no camera, cannot see this page, and holds each frame only until it sends it on. Frames are moved, not copied: after sending, this page's own handle to the frame is empty. A VideoFrame is the natural thing to move. A browser hands one to a worker, or to a frame of your own site. Chrome will not hand one to another process, and a sandboxed frame or a frame from another site now runs in one. So the page tries a VideoFrame, and if the filter cannot rebuild it, it moves an ImageBitmap from then on, which does cross. The note under the right-hand picture says which was used. It is a way to build video plug-ins that get pixels and nothing else.

const frame = new VideoFrame(source, { timestamp });
port.postMessage({ frame }, [frame]);          // frame is now closed here

// the filter, on its own origin
port.onmessage = ({ data }) => {
  ctx.filter = "invert(1)"; ctx.drawImage(data.frame, 0, 0); data.frame.close();
  const out = new VideoFrame(canvas, { timestamp: data.frame.timestamp });
  port.postMessage({ frame: out }, [out]);
};
// a frame the browser could not rebuild here arrives as this, with nothing in it
port.onmessageerror = () => port.postMessage({ unreadable: true });

// the page again: an ImageBitmap crosses where a VideoFrame does not
const bitmap = await createImageBitmap(source);
port.postMessage({ bitmap }, [bitmap]);

Let another origin sign with your key without giving it the key

The vault makes a signing key the browser will not let anyone read, itself included. It gives this page a port that signs. This page lends the shop a weaker port: orders only, three uses. The shop gets real signatures that anyone can check against the public key, and at no point does the key, or the full port, move.

// the vault
const { privateKey, publicKey } = await crypto.subtle.generateKey(ECDSA, false, ["sign", "verify"]);
port.onmessage = async ({ data }) => port.postMessage({ id: data.id, signature: await sign(privateKey, data.text) });

// this page, lending less than it has
lent.onmessage = ({ data }) => {
  if (uses-- > 0 && data.text.startsWith("order:")) vault.postMessage(data); else refuse(data);
};

Between real sites

Most frames on this page are sandboxed frames that this page wrote. Each has an opaque origin, so it is cross-origin to this page and to every other frame, but it is not a site: it has no address and no storage. In this part the outer boxes are the florist's and the library's actual sites, embedded here, each with its own address and its own storage. They show what you hand over and whether you can get it back.

Send a key to another site: it gets a copy you cannot take back

A CryptoKey can be posted to another origin. This page makes a signing key that cannot be read, and sends the key itself to the florist's site. The florist can now sign as you. It cannot read the key either, but it can keep it: it saves the key in its own IndexedDB, and after a reload it still has it. Nothing this page does can undo that. Compare the signer pattern, where the key stays put and only a port travels.

const { privateKey } = await crypto.subtle.generateKey(ECDSA, false, ["sign"]);
floristWindow.postMessage({ key: privateKey }, floristOrigin);   // a copy, not a move

// the florist, on its own origin
await db.put(key, "theirs");                 // kept, for as long as it likes
await crypto.subtle.sign(ECDSA, key, bytes); // signs as you

Send only the readable side of a stream

A stream has a direction, and you can hand over one direction without the other. The library's site gets only something to read from: it can listen and has nothing to speak into. The florist's site gets only something to write into: it can post notes through the slot and cannot see what else is inside. The owner can cut either one off. Close the feed and the listener is told it has ended. Shut the box and the next write fails.

// listen only
library.postMessage({ readable }, origin, [readable]);

// write only
const writable = new WritableStream({ start(c) { box = c; }, write: keep });
florist.postMessage({ writable }, origin, [writable]);
box.error(new Error("shut"));               // later: their next write fails

Pipe your data through another site, and get it back

A transform has two ends, and both can be given away. The library's site makes one that blacks out email addresses and long numbers, and hands this page the end to write into and the end to read from. From here it is an ordinary pipeThrough: your lines go in, cross to the library's origin, are changed by code this page never loads or sees, and come back. Back-pressure crosses with them.

// the library, on its own origin
const { readable, writable } = new TransformStream({ transform: redact });
parent.postMessage({ readable, writable }, "*", [readable, writable]);

// this page
myLines.pipeThrough({ readable, writable }).pipeTo(screen);

Lend someone a network connection you opened

The widget on the right is locked down so that it cannot reach the network at all. This page opens a WebSocket to the server and hands the widget the two streams that are the connection: one to write to, one to read from. The widget is now talking to the server. It never learns the address, it cannot open a second connection, and it keeps talking only until this page closes the socket. Hand over just the readable stream and it becomes a tap that can listen and not speak.

const socket = new WebSocketStream(url);        // keep it: socket.close() ends the loan
const { readable, writable } = await socket.opened;
widget.postMessage({ readable, writable }, "*", [readable, writable]);

// the widget, which has no network of its own
await writable.getWriter().write("hello");
const { value } = await readable.getReader().read();   // the server's answer

Join two sites with a port that carries messages one way only

A MessagePort always works in both directions. Whoever you give one to can post into it, and there is no setting that stops them. This page wants the library's site to publish prices to the florist's site, and wants nothing to come back. So it does not give them the two ends of one channel. It makes two channels and stands between them. What the library posts is posted on to the florist. What the florist posts stops at this page and is counted. The florist holds a real port and can call postMessage on it as often as it likes. A message with a port or a stream in it is refused in the forward direction too, because either one would be a way to answer.

function oneWay() {
  const inlet = new MessageChannel(), outlet = new MessageChannel();
  // forward: post it again, with no transfer list, so a port cannot ride along
  inlet.port2.onmessage = (e) => { try { outlet.port1.postMessage(e.data); } catch {} };
  // backward: nothing
  outlet.port1.onmessage = () => {};
  return { send: inlet.port1, receive: outlet.port2,
           cut: () => { inlet.port2.close(); outlet.port1.close(); } };
}

const link = oneWay();
library.postMessage({ cmd: "feed" }, libraryOrigin, [link.send]);
florist.postMessage({ cmd: "feed" }, floristOrigin, [link.receive]);

Other devices, Service Workers, sockets and audio

The other end of a port can be on another device, behind a path on your own site, in a worker that every tab shares, or on the thread that makes sound. The code that holds the port doesn't change.

A port whose other end is on another device

This page meets another device through a pairing code, the two connect directly with WebRTC, and each side wraps its end of that connection in a MessagePort. Then this page hands its port on. The counter at the end of the yellow cable is a sandboxed frame that was given a port and knows nothing more. Your phone is now pressing its buttons. The server carried a few messages so the two could find each other, and nothing since. The port carries more than text: bytes, other ports and streams can be posted into it, and each is rebuilt on the other device. See sending a photo as a stream and lending a port to another device.

// this page shows a pairing code. onPort is given a real MessagePort
far({ code, host: true, onPort(port) {
  counterFrame.postMessage({ cmd: "port" }, "*", [port]);   // give it away like any other port
} });

// the other device, with the same code: ordinary port code
far({ code, onPort(port) {
  port.postMessage({ do: "add" });
  port.onmessage = ({ data }) => show(data.count);
} });

Mount another site at a path on yours

A Service Worker can answer a request by asking a port, and the other end of that port can be on another origin. This page introduces a Service Worker to the florist's site. From then on, every request under /patterns/mounted/florist/ is answered by the florist: pages, images, and a file whose body is a stream that the florist is still writing while this origin reads it. The florist's server is never contacted. Its page, open in a frame, is the server. The same worker script, registered again for /patterns/mounted/library/ and given a port to the library's site, mounts that site beside it. What is mounted here runs as this origin, so mount only what you would let act as you.

// this page: a worker for the path, and a port to the site that will serve it
const reg = await navigator.serviceWorker.register("/mount-sw.js", { scope: "/mounted/florist/" });
const { port1, port2 } = new MessageChannel();
floristFrame.postMessage({ cmd: "serve" }, floristOrigin, [port1]);
reg.active.postMessage({ mount: true }, [port2]);

// Service Worker
origin.postMessage({ path }, [replyPort]);
// the florist answers with a body that is a ReadableStream, transferred

One connection to the server, shared by every tab

Ten tabs of the same site usually means ten connections to the server. Here no tab has one. A SharedWorker holds the only WebSocket, and each tab holds a port to the worker. A tab speaks by posting to its port. The worker numbers each question, and the answer with that number goes back down the port of the tab that asked, so replies are never mixed up. Close a tab and the worker notices and carries on. Drop the connection and the worker opens another and asks again anything that was not answered. The tabs have no code for any of that. The two boxes on the outside are real pages of this site, and the link opens a third in a real tab that joins the same socket.

// every tab
const { port } = new SharedWorker("/socket-worker.js");
port.postMessage({ say: "hello" });
port.onmessage = ({ data }) => show(data.answer);

// the worker: one socket, and a note of who asked what
port.onmessage = ({ data }) => {
  const id = ++ids;
  pending.set(id, { port, text: data.say });
  socket.send(JSON.stringify({ id, text: data.say }));
};
socket.onmessage = ({ data }) => {
  const { id, text } = JSON.parse(data);
  pending.get(id).port.postMessage({ answer: text });
  pending.delete(id);
};
// a dropped connection: open another and ask again what is still waiting
socket.onclose = () => setTimeout(connect, 300);

A worker that plays music while this page is frozen

Sound is made on a thread of its own, and that thread accepts a port. This page starts an audio processor and a worker, gives each one end of a channel, and steps away. The worker writes the tune and sends each note straight to the audio thread, which plays it and says so. Freeze this page for three seconds: the buttons stop working and its counter stops, but the music keeps time because none of it passes through here. The audio thread has no DOM, no timers and no network. A port is the only way to reach it, and anything that holds the other end can.

const node = new AudioWorkletNode(audio, "bell");
const { port1, port2 } = new MessageChannel();
composerWorker.postMessage({}, [port1]);
node.port.postMessage({}, [port2]);        // the audio thread now holds a port

// the worker, every beat. The page is not involved.
port.postMessage({ freq: 440 });

Join the service workers of two sites with a port

The florist's site and the library's site each have a service worker. A service worker can post to pages of its own site and to nothing else, so the two cannot reach each other. A port can be carried between them. The florist's worker makes a channel, keeps one port and gives the other to its page. The page sends that port over a line it holds to the library's page, and the library's page gives it to the library's worker. Now each worker holds one end of the same channel, and they ask each other questions with no page taking part. The answers are read from each site's own Cache Storage. A browser stops a service worker that has been idle for about thirty seconds, and the port is lost with it. Nothing tells the other worker. So each question has a time limit of 1.5 seconds. When it passes, the asking worker closes its port, makes a new channel, and has the pages carry one end across again. In the diagram this page gave the two pages their line. On the real web the florist's page opens the library's window and gives it one, which the link under the demo does.

// florist's service worker: make a channel, keep one port, give the other to my page
const { port1, port2 } = new MessageChannel();
peer = port1;
client.postMessage({ pair: "carry" }, [port2]);

// florist's page: it opened the library's window earlier and gave it one end of a channel.
// The port from the worker goes over that port.
navigator.serviceWorker.onmessage = (event) =>
  lineToLibraryPage.postMessage({ carry: true }, [event.ports[0]]);

// library's page: give the port to its own worker. This starts the worker if it was stopped.
lineToFloristPage.onmessage = (event) =>
  registration.active.postMessage({ pair: "peer", from: "florist" }, [event.ports[0]]);

// library's service worker: this port now reaches the florist's worker directly
onmessage = (event) => { peer = event.ports[0]; peer.onmessage = answer; peer.postMessage({ hello: "library" }); };

// either worker, later: a question, with a time limit, because a stopped worker says nothing
const reply = new MessageChannel();
peer.postMessage({ ask: "Dune" }, [reply.port2]);
const answer = await firstMessageOrTimeout(reply.port1, 1500);
if (!answer) { peer.close(); peer = null; await join(); /* a new channel, carried across again */ }

Knowing the other side is still there

A port does not tell you when its other end has gone. The page that held it can be closed, navigated, frozen or stuck, and posting into the port still works but nothing comes back. These demos put health checks on a second port, so the code that does the work doesn't have to know about them.

Send a second port with the first, only for health checks

A port does not tell you when its other end has gone. Posting into it still works, and nothing comes back. So this page sends the far side two ports at once. The first carries the work: a flower name goes in, a price comes out, and that is the whole protocol. The second carries pings and their answers and nothing else. The page pings once a second. One missed answer is late. Three in a row and the page treats the far side as gone. A page that is closing says goodbye on the health port as it goes, so most endings are seen at once and the pings are there for the ones that are not.

import { watch, answer } from "/alive.js";

// this page
const data = new MessageChannel(), health = new MessageChannel();
frame.postMessage("ports", origin, [data.port2, health.port2]);
watch(health.port1, { every: 1000, misses: 3,
  onState: (state) => state === "silent" || state === "closed" ? giveUp() : null });

// the far side
onmessage = ({ ports: [data, health] }) => {
  data.onmessage = (e) => data.postMessage(price(e.data)); // no health logic here
  answer(health);  // answers pings, and says goodbye on pagehide
};

Let the far side make the health channel and send a port back

Here the page sends only one port, the one for work, the same as it would with no health checks at all. When the far side receives it, it makes a channel of its own for health checks and sends one end back. Each side set up exactly one channel. The page does not have to know in advance that the far side does health checks: if a port comes back, it watches it. If none comes, it carries on without. The far side decides how it is watched.

// this page: one port, as usual
const data = new MessageChannel();
frame.postMessage("port", origin, [data.port2]);
addEventListener("message", (e) => {
  if (e.source === frame && e.data === "health") watch(e.ports[0], { onState });
});

// the far side: make the health channel, keep one end, send the other back
onmessage = ({ source, ports: [data] }) => {
  serve(data);
  const health = new MessageChannel();
  answer(health.port1);
  source.postMessage("health", "*", [health.port2]);
};

Send a beat each way on two one-way ports

Each side makes a channel, keeps the end it posts into and gives the other side the end to listen on. Then it posts a beat on a timer and never reads its own port. Each side only listens to the other's. Both sides learn whether the other is there, with half the messages of ping and answer, and neither side's code has to match an answer to a question. Each beat says how often beats will come, and whether the page that sent it is hidden, because a browser slows the timers of a hidden page.

import { beat, listen } from "/alive.js";

// each side does the same
const mine = new MessageChannel();
beat(mine.port1, { every: 1000 });           // post into this end, never read it
other.postMessage("beats", origin, [mine.port2]);
// ...and listens on the end the other side sent
listen(theirs, { onState: (state) => show(state) });

Restart a worker that has stopped answering, and ask again

A worker counts prime numbers for this page. It is given a port for the work and a port to answer health pings on. If it stops answering, because it is stuck in a loop or has closed itself, the page waits for three missed pings, terminates it, starts a new one and sends it every question that was not answered. Nothing about health is in the work protocol, so the restart is invisible to the code that asked: it gets its answer, later than usual.

function start() {
  const worker = new Worker("/patterns/alive-worker.js", { type: "module" });
  const work = new MessageChannel(), health = new MessageChannel();
  worker.postMessage({ ports: true }, [work.port2, health.port2]);
  current = work.port1;                            // questions go to the newest worker
  work.port1.onmessage = ({ data }) => { pending.get(data.id).resolve(data.count); pending.delete(data.id); };
  watch(health.port1, { every: 500, misses: 3, onState(state) {
    if (state !== "silent") return;
    worker.terminate();
    start();                                       // a new worker
    for (const [id, ask] of pending) current.postMessage({ id, n: ask.n }); // ask again
  } });
}

Block on a port: a synchronous call with no await

Ports are asynchronous and a lot of old code isn't. With a few bytes of shared memory, a worker can ask a question down a port and block on that line until the answer is written, even when the answer is a person pressing a button. Common mistakes

  • A port you attach with addEventListener stays silent until you call port.start(). Setting onmessage starts it for you.
  • Messages posted before the other side is listening are not lost. They wait in the port. You can send a port and start talking into it straight away.
  • Nothing tells you when the other end has gone. A close event for ports was added to the HTML standard in 2024, never switched on in any browser, and removed again in October 2026. Put health checks on a second port: pings or beats, with a goodbye on pagehide. On one origin, a Web Lock held by the other side is released the moment it is destroyed. Which signal notices what.
  • A SharedWorker inside a cross-site iframe is partitioned by the top-level site, so a hidden hub iframe is a different hub on every site. A window of its own is first party and reaches the real one. Ports that have already been handed over are not affected.
  • A transferred port is gone from the sender. Post it twice and the second call throws.
  • A stream that is passed on through a middle context keeps flowing through it. If the middle goes away the reader stalls with no error and no end. Send streams down a direct port.
  • A port cannot be saved anywhere. IndexedDB, sessionStorage and history state all refuse it. To keep one across a reload, post it to a SharedWorker in pagehide and ask for it back. Create the worker with extendedLifetime: true, or it dies with its last page.

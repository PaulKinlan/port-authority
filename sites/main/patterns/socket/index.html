One connection to the server, shared by every tab

What you are looking at

Ten tabs of the same site usually means ten connections to the server. Here no tab has one. A SharedWorker holds the only WebSocket, and each tab holds a port to the worker. A tab speaks by posting to its port. The worker numbers each question, and the answer with that number goes back down the port of the tab that asked, so replies are never mixed up. Close a tab and the worker notices and carries on. Drop the connection and the worker opens another and asks again anything that was not answered. The tabs have no code for any of that. The two boxes on the outside are real pages of this site, and the link opens a third in a real tab that joins the same socket.

The code

// every tab
const { port } = new SharedWorker("/socket-worker.js");
port.postMessage({ say: "hello" });
port.onmessage = ({ data }) => show(data.answer);

// the worker: one socket, and a note of who asked what
port.onmessage = ({ data }) => {
  const id = ++ids;
  pending.set(id, { port, text: data.say });
  socket.send(JSON.stringify({ id, text: data.say }));
};
socket.onmessage = ({ data }) => {
  const { id, text } = JSON.parse(data);
  pending.get(id).port.postMessage({ answer: text });
  pending.delete(id);
};
// a dropped connection: open another and ask again what is still waiting
socket.onclose = () => setTimeout(connect, 300);

Using it

// an issue tracker. A person has ten issues open in ten tabs.
// each tab: ask about its own issue, and hold a lock under a name of its own while the tab lives
port.postMessage({ say: "status of issue 4127" });
navigator.locks.request(lock, () => { port.postMessage({ lock }); return new Promise(() => {}); });

// the worker: every tab arrives here with a port of its own
onconnect = (e) => {
  const port = e.ports[0];
  port.onmessage = ({ data }) => {
    // when the worker gets the tab's lock, the tab has gone. leave() drops its questions.
    if (data.lock) return navigator.locks.request(data.lock, () => leave(port));
    // otherwise it is data.say, and the handler above
  };
};

// the worker: the laptop changes network and the socket closes. connect() runs again.
function connect() {
  socket = new WebSocket("wss://tracker.example/live");
  // ask again for every tab that is still waiting. No tab did anything.
  socket.onopen = () => { for (const [id, { text }] of pending) socket.send(JSON.stringify({ id, text })); };
  // socket.onmessage and socket.onclose are set here, as above
}

Where you would use it

A real case. An issue tracker's server allows each person a small number of connections, and people open ten issues in ten tabs. Every tab asks the worker about its own issue, and the worker sends all the questions over one WebSocket. When the laptop changes network the socket closes, and the worker opens another and asks again what was not answered. The tabs run no code for this and their ports are unchanged. A status question is safe to send twice, which matters because a repeated question may reach the server twice.

How it works

Each tab connects to one SharedWorker and gets a port. The worker opens a single WebSocket and keeps it. Tabs post to their port, and the worker sends on the socket.

The worker gives each question a number and remembers which port asked it. The server's answer carries the number, and the worker sends it down that port and no other. It is the reply pattern with a socket in the middle.

If the socket closes while tabs are still open, the worker opens another and sends again every question that has no answer yet. A tab's port is unaffected by any of this, because the port goes to the worker and not to the server.

Tabs hold a Web Lock for as long as they live. The worker waits on each lock, so it knows when a tab has gone, and it hangs up when the last one leaves.

Step by step

What each press of Next does in the demo at the top.

  1. Connect both tabs to the SharedWorker. Each tab opens a port to the SharedWorker. Neither tab opens a WebSocket; the worker holds the only one.
  2. Tab one: say hello. Tab one posts to its port. The worker sends it on the only socket, and the server's answer comes back to tab one alone.
  3. Tab two: say hello. Tab two does the same, on the same socket.
  4. Close tab one. Tab one is destroyed. The worker notices, and the socket stays open for the other.
  5. Drop the connection. The worker's socket is closed, as a failed network would close it. The worker opens another. Tab two did nothing and was told nothing.
  6. Tab two: say hello. Tab two posts to the same port as before, and the answer arrives over the new socket.

One subscription feeds every tab, and one place handles reconnecting

The idea: One subscription feeding every open tab. A single place to handle reconnection and backoff.

What you are looking at

Both tabs show a live price, and neither has a connection to the server. A shared worker holds the one subscription and passes each price down a port to every tab. When the connection drops, the worker is the only thing that notices. It waits, tries again, waits longer if that fails, and carries on. The tabs contain no reconnection code at all. Drop the connection and watch them wait.

The code

// the worker: the only code that knows about the connection
socket.onmessage = ({ data }) => { for (const port of tabs) port.postMessage({ price: data }); };
socket.onclose = () => setTimeout(connect, Math.min(8000, 500 * 2 ** attempt++));

// every tab, in full
port.onmessage = ({ data }) => show(data.price);

Step by step

What each press of Next does in this demo.

  1. Drop the connection. The server hangs up on the worker. The worker waits half a second and connects again. The tabs did nothing.
  2. Close tab one. One tab goes. The subscription stays up for the other.

Things to try

  • Have both tabs say hello and check the worker's socket count.
  • Open a third tab for real from the link.

  • Drop the connection, then have a tab say hello. The count of sockets opened goes up by one.

Common mistakes

  • Without SharedWorker, fall back to a socket per tab.
  • The worker is partitioned inside cross-site iframes.
  • Do not match answers to askers by the order they arrive in. One lost or reordered answer gives every later tab the wrong one. Number the questions.
  • A question that is sent again after a reconnect may reach the server twice. Make the server ignore a number it has already answered, or only repeat requests that are safe to repeat.

Measured

Chromium 157: three tabs, one socket opened, each answer delivered only to the tab that asked. After the socket is closed the worker opens a second, and a tab's next question is answered with no change in the tab. Other browsers are being filled in from the lab's results.

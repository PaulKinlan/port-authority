Port patterns / More things a port can carry

A forwarded stream stops when the page that passed it on closes. A port keeps working.

What you are looking at

You can pass a stream on, the same as a port. But a stream that was passed on keeps flowing through every context that touched it. Send one through the introducer, remove the introducer, and the reader stalls with no error and no end. So introduce with a port first, then send the stream down the direct line. Start again between the two to compare. The three boxes are frames in this page, and this page gave the source and the reader each a line to the introducer.

The code

// fragile: the middle is now part of the pipe for ever
toMiddle.postMessage({ stream }, [stream]);

// sturdy: the middle only introduces
const direct = await introducedPort();
direct.postMessage({ stream }, [stream]);

Using it

// a photo editor, a "Save to" chooser window it opened, and the storage site the person picks
// the chooser: make a channel, give one end to each side, keep neither
const { port1, port2 } = new MessageChannel();
toEditor.postMessage({}, [port1]);
toStorage.postMessage({}, [port2]);

// the editor: introducedPort() waits for that port to arrive from the chooser
const introducedPort = () => new Promise((resolve) => { toMiddle.onmessage = (e) => resolve(e.ports[0]); });
const direct = await introducedPort();
const stream = exportPhoto();                 // a ReadableStream of bytes
direct.postMessage({ stream }, [stream]);

// the storage site: a port arrives from the chooser, then the stream arrives on that port
toMiddle.onmessage = (e) => {
  e.ports[0].onmessage = async ({ data }) => {
    const reader = data.stream.getReader();
    for (;;) { const { value, done } = await reader.read(); if (done) break; await save(value); }
  };
};

// The person closes the chooser. The export carries on, because no chunk passes through the chooser.
// Sent with toMiddle.postMessage, the same stream would stall here, with no error and no end.

Where you would use it

A real case. A photo editor exports a large file to a storage site that the person picks in a chooser window the editor opened. The chooser opened the storage site's upload page, so it is the only one with a line to both. If the export stream is passed through the chooser, the upload stalls when the person closes the chooser, and neither side gets an error. So the chooser makes a channel and posts one end to each side, and the editor sends the stream down that port. The person can then close the chooser and the upload carries on.

How it works

Introduce two parties with a port and you can leave. Do the same with a stream and you cannot. This demo lets you try both ways, one after the other.

A port passed through a middle context is re-homed: the two ends find each other and the middle drops out. A stream passed through a middle context is piped: every chunk still travels through the middle, which has to stay alive to carry it.

When the middle goes away the reader of the stream is not told. It gets no error and no end, and just stalls. The port carries on.

Step by step

What each press of Next does in the demo at the top.

  1. Connect Source and Reader to the introducer. Source and Reader each get a line to the introducer. They have no direct line to each other yet.
  2. Stream through the introducer. Source sends a stream to the introducer, which forwards it to Reader. Every chunk now flows through the middle.
  3. Remove the introducer. The introducer is destroyed, and the reader stalls with no error and no end.

What you could build with it

Already running

  • For a long-lived connection through a broker, send a port and let the far side make its stream over that. See the demo at the top of this page.

Things to try

  • Stream through the introducer, then remove the introducer. The reader stalls.
  • Start again, introduce first and stream directly, then remove the introducer. The stream carries on.
  • Read the stalled reader's log: it never learns why.

Common mistakes

  • It is easy to build a broker that forwards streams and works until the broker tab closes.
  • A stalled stream needs a timeout of your own to detect.

Measured

Chromium 157: a forwarded stream stalls with no error when the forwarding frame is removed. A forwarded port is unaffected. Other browsers are being filled in from the lab's results.

Port patterns / The six basic patterns

Open a channel and send a message through it

What you are looking at

new MessageChannel() gives you two entangled ports. Keep one, post the other to anyone you can already reach. From then on the two of you have a line of your own. What goes down it is not a window message, so a script that listens for window.postMessage messages does not see it.

The code

const { port1, port2 } = new MessageChannel();
frame.contentWindow.postMessage("here", "*", [port2]); // port2 is moved, not copied
port1.onmessage = (e) => console.log(e.data);
port1.postMessage("ping");

Using it

// inside the frame: a help chat from a support company, on a shop's order page
addEventListener("message", (event) => {
  // check who sent it once, here. Messages on the port need no check.
  if (event.origin !== shopOrigin || event.data !== "here") return;
  const port = event.ports[0];          // this is port2. It belongs to the frame now.
  // the page posted "ping" before this ran. It waited in the port.
  port.onmessage = (e) => {
    if (e.data === "ping") port.postMessage("pong");
    else showOrder(e.data.order);
  };
});

// back in the shop's page, when the person opens an order
port1.postMessage({ order: "A-1041" });

Where you would use it

A real case. A shop puts a help chat from a support company on its order page, in a frame. When the frame has loaded, the shop's page makes a channel and posts one end into it. The chat checks the sender's origin once, when the port arrives, and keeps the port. After that the shop sends the order the person is looking at down the port, and the chat answers on it. A third-party script in the shop's page that listens for window message events sees none of these messages.

How it works

new MessageChannel() gives you two ports that are joined to each other and to nothing else. Whatever is posted into one comes out of the other, in order. There is no address, name or origin check, because nobody else is on the channel.

A port is one of the few things that can be moved with postMessage. Put it in the transfer list and it leaves your context and arrives in the other one, still joined to its twin. Every other pattern on this site uses that.

Compare it with window.postMessage, where every listener in the window gets every message, and both sides have to check event.origin and event.source on every message. With a port you check once, when you decide who to hand the port to.

A private line that other scripts on the page cannot hear

The idea: A private line between a page and one embedded widget, where other scripts in either window cannot listen in.

What you are looking at

A sign-in widget from another origin has a token to hand to this page. If it posts the token to the window, every script in the page hears it, including an advert's. If the page first gives the widget one end of a channel, the token arrives on the page's own port, and there is nothing for the advert's script to listen to.

The code

// heard by every "message" listener in the page
parent.postMessage({ token }, "*");

// heard only by whoever holds the other end
port.postMessage({ token });

Step by step

What each press of Next does in this demo.

  1. Widget: post the token to the window. The page gets the token. So does the advert's script, which only had to listen.
  2. Open a private line. This page makes a channel, keeps one end and gives the widget the other.
  3. Widget: post the token down the line. The token arrives on the page's port. The advert's script hears nothing.

One window.postMessage to deliver a port, and everything after it on the port

The idea: The first step of every protocol on this site: one window.postMessage to deliver a port, then ports only.

What you are looking at

This page calls window.postMessage on the frame once. That message carries nothing except one end of a channel. Everything after it goes over the port: a question with an answer, then a subscription that sends five prices. The frame counts what it hears on its window and what it hears on the port, and sends both counts back with every reply. The window count stays at one however long the conversation goes on. The buttons below use the port only.

The code

const { port1, port2 } = new MessageChannel();
frame.contentWindow.postMessage({ cmd: "port" }, "*", [port2]);   // the only window message

// from here on, only the port
port1.postMessage({ id: 1, sum: [19, 23] });
port1.postMessage({ subscribe: "prices" });
port1.onmessage = ({ data }) => show(data);

Step by step

What each press of Next does in this demo.

  1. Deliver a port with one window.postMessage. The frame's window hears one message. It holds a port and no data.
  2. Ask for a sum over the port. The question and the answer both travel on the port. The window count is still one.
  3. Subscribe to prices over the port. Five prices arrive, half a second apart, all on the port.
  4. Ask for a sum over the port. Still the same port, and the frame's window has still heard one message.

Things to try

  • Open the channel, then send several pings quickly. The answers come back in the order you asked.
  • Press Start again and send a ping before opening the channel. Nothing happens, because there is no channel yet.

Common mistakes

  • A port you listen to with addEventListener is silent until you call port.start(). Setting onmessage starts it for you.
  • Messages posted before the other side is listening are queued in the port, not lost. You can post a port and talk into it straight away.
  • A transferred port is gone from the sender. Posting it a second time throws.

Port patterns / More things a port can carry

A worker that routes between windows that have never met

What you are looking at

The three windows above the router know two things each: their own name, and how to reach the router. None of them has a reference to another, and none of them holds a port of another's. To reach the kitchen, the orders window posts a message to the router addressed to "kitchen". The router looks the name up and passes the message on, with the sender's name attached. Address a name nobody has and the router says so. The router here is a SharedWorker. Each box is a real page of this site, and the link opens a fourth window that can join in.

The code

// every window: say who you are, then address others by name
const { port } = new SharedWorker("/router-worker.js");
port.postMessage({ iam: "orders" });
port.postMessage({ to: "kitchen", text: "two tulip bunches" });
port.onmessage = ({ data }) => show(data.from, data.text);

// the router: a table of names, and nothing else
onconnect = ({ ports: [port] }) => {
  port.onmessage = ({ data }) => {
    if (data.iam) return table.set(data.iam, port);
    const target = table.get(data.to);
    target ? target.postMessage({ from: nameOf(port), text: data.text })
           : port.postMessage({ undelivered: data.to });
  };
};

Using it

// one delivery business, one computer, three windows: orders, kitchen and driver
// the kitchen window: it is told who sent each message, and answers by that name
const { port } = new SharedWorker("/router-worker.js");
port.postMessage({ iam: "kitchen" });
port.onmessage = ({ data }) => {
  if (data.undelivered) return warn("No window called " + data.undelivered + " is open");
  show(data.from, data.text);
  port.postMessage({ to: data.from, text: "started" });
};
readyButton.onclick = () => port.postMessage({ to: "driver", text: "two tulip bunches, ready to go" });

// the router's table, and how it finds the sender's name
const table = new Map();                      // name -> port
const nameOf = (port) => [...table].find(([, p]) => p === port)?.[0];

// Nobody has opened the driver window yet today, so "driver" is not in the table.
// The kitchen gets { undelivered: "driver" } back and shows the warning. The message is not kept.

Where you would use it

A real case. A small delivery business runs one web app on one computer, in three windows on three screens: orders at the counter, the kitchen's list, and the driver's list by the door. The windows are opened and closed through the day in any order, and none of them opened another, so none has a handle to another. Each one tells the router its name and addresses the others by name. The kitchen answers the orders window using the from that the router filled in. The moment that matters is a message to a name nobody holds: the router sends undelivered back, and the kitchen can tell its staff that the driver's window is not open.

How it works

Most of this site is about introducing two parties and then leaving. Here the router stays in the path of every message on purpose, so that the windows need to know almost nothing. A window knows its own name and how to reach the router. It never learns which window answers to a name, whether that window is open, or how many there are.

The whole router is a table from names to places it can post to. A window registers by saying its name. To send, a window posts { to, text } to the router. The router looks to up, and posts { from, text } to whatever it finds. The sender's name is filled in by the router from the connection the message arrived on, so a window cannot claim to be somebody else.

As a shared worker, the table holds ports: one per window, handed over when the window connected. As a service worker, there are no ports to hold. The table holds client ids, and the worker reaches a window with clients.get(id) and client.postMessage. Either way the windows share an origin, because that is who can reach the same worker.

The two differ in how long they remember. A shared worker lives as long as one of its pages does, and its table lives with it. A service worker is stopped by the browser whenever it has been idle for a while, and starts again with nothing. The version below deals with that the simple way: when it cannot place a name, it asks every open window to say who it is, waits a moment, and looks again.

Because every message passes through one place, that place can do more than forward. It can refuse, log, queue for a window that is not open yet, or send to every window with a role. And if two windows turn out to talk a lot, the router can stop carrying their traffic and introduce them instead: make a channel, post one end to each, and step back.

Step by step

What each press of Next does in the demo at the top.

  1. Register the three windows. Each window connects to the SharedWorker and registers its name. None of them has a line to another window.
  2. Orders: send to the kitchen. The orders window posts to the router, addressed to "kitchen". The router looks the name up and passes it on.
  3. Kitchen: send to the driver. The kitchen does the same for the driver. It has never seen the driver's window.
  4. Driver: send to orders. And the driver reaches orders. Every message went through the middle.
  5. Orders: send to the florist. Nobody registered that name. The router tells the sender it could not be delivered.
  6. Close the kitchen. The kitchen's window is destroyed. The router notices and takes it out of its table.
  7. Orders: send to the kitchen. The same message as before. This time there is nobody to give it to.

The same router as a Service Worker, which forgets and asks again

The idea: Windows of one app that open and close in any order, and still reach each other by role.

What you are looking at

A Service Worker can do the same job with no ports at all. Each window posts to the Service Worker, and the Service Worker reaches the others through its list of open windows. There is one difference that matters. A browser stops a Service Worker when it is idle, and it wakes with an empty table. So when this one cannot place a name, it asks every open window to say who it is, and then tries again. The button that makes it forget stands in for the browser stopping it, which a page cannot ask for.

The code

// every window
registration.active.postMessage({ iam: "orders" });
registration.active.postMessage({ to: "kitchen", text: "two tulip bunches" });
navigator.serviceWorker.onmessage = ({ data }) =>
  data.rollcall ? registration.active.postMessage({ iam: "orders" }) : show(data.from, data.text);

// the Service Worker
onmessage = async (event) => {
  let target = await clients.get(table.get(event.data.to));
  if (!target) { await rollCall(); target = await clients.get(table.get(event.data.to)); }   // woke up empty?
  target.postMessage({ from: nameOf(event.source.id), text: event.data.text });
};

Step by step

What each press of Next does in this demo.

  1. Register the three windows. Each window tells the Service Worker its name. No MessagePorts are used.
  2. Orders: send to the kitchen. The orders window posts to the Service Worker, which finds the kitchen's window and passes the message on.
  3. Make the Service Worker forget. Its table is emptied, as it would be if the browser had stopped it.
  4. Kitchen: send to the driver. The Service Worker knows nobody. It asks every window to say who it is, rebuilds its table, and delivers.
  5. Orders: send to the florist. It asks again, nobody answers to that name, and the sender is told.

Messages kept in the worker until the window they are for opens

The idea: A message queue in the worker, holding messages for a window that has not opened yet.

What you are looking at

The orders and kitchen windows are open. The driver's window is not. When either of them sends to "driver", the shared worker finds no such name in its table and keeps the message in a list under that name. When a window opens and says it is the driver, the worker hands over everything in the list, oldest first. After that it passes messages straight through. The senders do the same thing in both cases. The list is in the worker's memory, so it lasts for as long as at least one window of the app stays open.

The code

// the worker
const table = new Map();   // name -> port
const held = new Map();    // name -> messages waiting for that name

port.onmessage = ({ data }) => {
  if (data.iam) {
    table.set(data.iam, port);
    for (const message of held.get(data.iam) || []) port.postMessage(message);
    held.delete(data.iam);
  }
  if (data.to) {
    const target = table.get(data.to);
    const message = { from: nameOf(port), text: data.text };
    target ? target.postMessage(message)
           : held.set(data.to, [...(held.get(data.to) || []), message]);
  }
};

Step by step

What each press of Next does in this demo.

  1. Orders: send to the driver. No window is called driver. The worker keeps the message.
  2. Kitchen: send to the driver. A second message for the driver, from a different window. The worker is now holding two.
  3. Open the driver's window. The new window tells the worker its name. The worker hands over both messages, in the order they were sent.
  4. Orders: send to the driver. The driver is open now, so this one is passed straight on.

One message to every window with a role

The idea: One window addressing every window with a role at once, such as every open editor.

What you are looking at

Each window tells the worker its name and its role. Two of these are editors and one is a preview. The settings window does not know how many editors are open or what they are called. It posts one message addressed to the role "editor", and the worker sends a copy to every window that gave that role. Open another editor and it is included from then on. Close one and the worker takes it out of the table, so the next message goes to the ones that are left.

The code

// each window
port.postMessage({ iam: "editor-1", role: "editor" });

// the settings window
port.postMessage({ toRole: "editor", text: "use font size 18" });

// the worker
if (data.toRole) {
  for (const [, w] of table)
    if (w.role === data.toRole && w.port !== port)
      w.port.postMessage({ from: nameOf(port), text: data.text });
}

Step by step

What each press of Next does in this demo.

  1. Settings: tell every editor. One message, addressed to the role "editor". Both editors get it. The preview has a different role and gets nothing.
  2. Open a third editor. Another window opens and gives the same role.
  3. Settings: tell every editor. The same call as before. This time three windows get it.
  4. Close editor 1. The window is destroyed. The worker notices and takes it out of its table.
  5. Settings: tell every editor. Two editors are left, and those two get it.

A request sent to whichever open window offers the tool

The idea: A hub that routes each request to whichever open window offers the tool that was asked for.

What you are looking at

Windows tell the worker which tool they offer. The shop window asks for a tool by what it does, "print-label" or "find-route", and never names a window. The worker looks for an open window that offers it, passes the request on, and that window answers the shop by name through the same worker. Close the label printer and the request has nowhere to go, and the shop is told. Open a different window that offers the same tool and the same request reaches that one. The hub on this site does this between sites on different origins.

The code

// a window that offers a tool
port.postMessage({ iam: "label-printer", tool: "print-label" });
port.onmessage = ({ data }) =>
  data.job && port.postMessage({ to: data.from, text: print(data.text) });

// the shop: asks for the tool, not for a window
port.postMessage({ need: "print-label", text: "order 1" });

// the worker
if (data.need) {
  const found = [...table].find(([, w]) => w.tool === data.need);
  found ? found[1].port.postMessage({ from: nameOf(port), job: data.need, text: data.text })
        : port.postMessage({ nobody: data.need });
}

Step by step

What each press of Next does in this demo.

  1. Shop: ask for a label. The shop asks for "print-label". The worker finds the window that offers it. The answer comes back to the shop.
  2. Shop: ask for a route. A different tool, so the worker picks a different window.
  3. Close the label printer. The only window that prints labels is destroyed.
  4. Shop: ask for a label. No open window offers that tool now. The worker tells the shop.
  5. Open the back office. A different window opens. It also offers "print-label".
  6. Shop: ask for a label. The same request as before. It goes to the back office.

Things to try

  • Open a fourth window from the link. It is called florist. Now send from orders to the florist again: it arrives.
  • Close the kitchen, then send to it. The router has already taken it out of the table.
  • In the service worker version, make it forget and then send. Watch the count of times it asked who is here go up by one.

Common mistakes

  • The router sees everything. Where that matters, use it only to introduce, and let the two talk directly.
  • A shared worker reached from inside a frame on another site is partitioned by the top-level site. Two sites that embed the same frame get two routers, and their windows cannot find each other.
  • A service worker forgets its table whenever the browser stops it. Keep nothing in it that you cannot rebuild by asking the windows, or store it.
  • Names are first come, first served here. A second window that registers a name takes it over. Decide whether that is a takeover you want, a refusal, or a group.
  • Nothing tells the router that a window has closed. The shared worker waits on a Web Lock the window holds. The service worker finds out when clients.get returns nothing.

Measured

Chromium 157: three same-origin frames with no references to each other exchange messages through a shared worker, and through a service worker using clients.get. After the service worker's table is cleared, one roll call rebuilds it and the message is delivered. Other browsers are being filled in from the lab's results.

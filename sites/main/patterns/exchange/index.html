Port patterns / The six basic patterns

Use a SharedWorker to connect tabs to each other

What you are looking at

Every tab on an origin can reach the same SharedWorker. Here it keeps a port to each tab and does one job: when a tab joins, it makes a channel between that tab and every other, then stays out of it. The tabs talk directly. Open a third in a new tab and it joins the same mesh.

The code

// in the SharedWorker
const peers = new Set();
onconnect = ({ ports: [port] }) => {
  port.onmessage = ({ data: { name } }) => {     // each tab says its name once
    for (const other of peers) {
      const { port1, port2 } = new MessageChannel();
      port.postMessage({ meet: other.name }, [port1]);
      other.port.postMessage({ meet: name }, [port2]);
    }
    peers.add({ name, port });
  };
};

Using it

// in every tab of a notes app
const worker = new SharedWorker("/exchange.js");
const others = new Map();
worker.port.onmessage = ({ data, ports: [direct] }) => {
  others.set(data.meet, direct);          // one port for each other tab
  direct.onmessage = (e) => showEdit(e.data);
};

// the person types in this tab. Each other tab gets the edit on its own port.
// The worker does not see it.
editor.oninput = () => {
  for (const direct of others.values()) direct.postMessage({ note: noteId, text: editor.value });
};

// A tab that has closed stays in the map. Posting to it does nothing
// and raises no error.

Where you would use it

A real case. A notes app is open in three tabs, and the person types in one of them. Each tab connects to the same SharedWorker when it loads, and the worker hands it a direct port to every tab that is already open. The typing tab posts each edit down those ports, so the other tabs show it without asking the server, and the worker carries none of it. A tab can also post to one other tab alone, for example to ask it for the newest draft, where a BroadcastChannel would send that to every tab. This needs a browser that has SharedWorker.

How it works

A SharedWorker is one worker that every tab of an origin can connect to. Each tab gets a port to it. Here the worker never carries a chat message. When a new tab joins, the worker makes a channel for each tab already present and posts one end to each side.

Every tab ends up with a direct line to every other tab. It is the introduce pattern with a worker as the introducer.

The worker needs to know when a tab has gone, and a port doesn't tell it. Each tab holds a Web Lock named after itself for as long as it lives, and the worker queues for the same lock. When the worker gets it, the tab is gone.

Step by step

What each press of Next does in the demo at the top.

  1. Left tab joins SharedWorker. Left tab connects to the SharedWorker. Nobody else is connected yet.
  2. Right tab joins SharedWorker. Right tab connects. The SharedWorker makes a new channel and hands one end to each tab, forming the teal direct line.
  3. Left tab says hi. Left tab sends a message directly to Right tab. Notice the SharedWorker saw 0 chat messages.
  4. Right tab says hi. Right tab sends a message directly back. The SharedWorker is completely out of the chat.

One tab does the background job, and another takes over when it closes

The idea: One tab as the leader for a background job, chosen and replaced by the worker. A presence list of the site's open tabs.

What you are looking at

Three tabs of this site are open in the boxes below. A shared worker holds a port to each, keeps the list of who is here, and names one the leader. Only the leader runs the sync job. Close it, and the worker notices through a lock the tab was holding, promotes the tab that has been here longest, and tells everyone. The link opens a fourth tab for real.

The code

// each tab
navigator.locks.request(myName, () => new Promise(() => {}));   // held until this tab dies
port.postMessage({ join: true, lock: myName });
port.onmessage = ({ data }) => { iAmLeader = data.lead; };

// the worker
navigator.locks.request(lock, () => leave(port));   // runs when the tab has gone

Step by step

What each press of Next does in this demo.

  1. Close the leader. The leading tab is destroyed. The worker gets its lock, and promotes the next tab.
  2. Close the leader. And again. The last tab left is the leader.

A list that stays the same in every tab, with no server

The idea: Tab-to-tab sync that does not go through a server.

What you are looking at

The two boxes are two tabs of this site, each showing a shopping list. Add an item in one and it appears in the other. Tick it in the other and it is ticked in the first. The list lives in a shared worker that holds a port to every tab. Nothing is sent to a server, and nothing is written to storage. The checkboxes in the boxes work too, and the link opens a third tab for real.

The code

// every tab
const port = new SharedWorker("/sync-worker.js").port;
port.onmessage = ({ data }) => render(data.list);
addButton.onclick = () => port.postMessage({ add: true });

// the worker
onconnect = ({ ports: [port] }) => {
  ports.add(port);
  port.onmessage = ({ data }) => { change(list, data); for (const p of ports) p.postMessage({ list }); };
};

Step by step

What each press of Next does in this demo.

  1. Tab one: add an item. Tab one tells the worker. The worker tells every tab.
  2. Tab one: add an item. A second item, in both tabs.
  3. Tab two: tick the first item. Tab two ticks it, and it is ticked in tab one.

Things to try

  • Open another peer in a new tab and watch the introduction count: one new line per peer already there.
  • Send from one peer and see that the worker carried none of it.

Common mistakes

  • Inside a cross-site iframe a SharedWorker is partitioned by the top-level site. A hidden hub iframe is a different hub on every site.
  • A SharedWorker dies with its last page unless created with extendedLifetime.
  • Safari on iOS only gained SharedWorker in 16, and Chrome on Android later still. Check before relying on it.

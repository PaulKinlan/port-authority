Port patterns / Between real sites

Join two sites with a port that carries messages one way only

What you are looking at

A MessagePort always works in both directions. Whoever you give one to can post into it, and there is no setting that stops them. This page wants the library's site to publish prices to the florist's site, and wants nothing to come back. So it does not give them the two ends of one channel. It makes two channels and stands between them. What the library posts is posted on to the florist. What the florist posts stops at this page and is counted. The florist holds a real port and can call postMessage on it as often as it likes. A message with a port or a stream in it is refused in the forward direction too, because either one would be a way to answer.

The code

function oneWay() {
  const inlet = new MessageChannel(), outlet = new MessageChannel();
  // forward: post it again, with no transfer list, so a port cannot ride along
  inlet.port2.onmessage = (e) => { try { outlet.port1.postMessage(e.data); } catch {} };
  // backward: nothing
  outlet.port1.onmessage = () => {};
  return { send: inlet.port1, receive: outlet.port2,
           cut: () => { inlet.port2.close(); outlet.port1.close(); } };
}

const link = oneWay();
library.postMessage({ cmd: "feed" }, libraryOrigin, [link.send]);
florist.postMessage({ cmd: "feed" }, floristOrigin, [link.receive]);

Using it

// a town's what's-on page, with the library's frame and the florist's frame in it
// the library: publish each event on the port it was given
addEventListener("message", (e) => {
  if (e.origin !== townOrigin || e.data?.cmd !== "feed") return;
  const send = e.ports[0];
  send.postMessage({ event: "Poetry reading", at: "19:00" });
});

// the florist: hear each event, and try to answer
addEventListener("message", (e) => {
  if (e.origin !== townOrigin || e.data?.cmd !== "feed") return;
  const receive = e.ports[0];
  receive.onmessage = ({ data }) => offerFlowersFor(data.event);
  receive.postMessage({ advert: "10% off" });   // stops at the town's page. The library hears nothing.
});

// the town's page: the florist's listing ends
link.cut();
// The library's posts go nowhere now, and the florist hears nothing more.
// Neither site is told, so each needs a timeout of its own to notice.

Where you would use it

A real case. A town's what's-on page embeds two other sites in frames. The library's frame publishes the day's events, and the florist's frame shows flowers to go with each one. The town wants the florist to hear the events, and wants nothing the florist posts into its port to reach the library's frame, which runs with the library's own storage. So the town's page keeps the middle of the link and gives each site one end. When the florist's listing ends, the town's page calls cut(), and neither site is told, so each needs a timeout to notice.

How it works

A MessageChannel has two ports and each can both send and receive. There is no read-only port. Giving someone a port always gives them something to post into.

To get one direction only, use two channels and keep the middle. The sender gets one end of the first channel. The receiver gets one end of the second. The page holds the other two ends and copies messages from the first to the second. It has a listener on the second that does nothing, so what the receiver posts is taken off the queue and thrown away.

The copy is made with postMessage(data) and no transfer list. A MessagePort or a stream cannot be copied, only moved, so a message that contains one makes that call throw, and nothing is sent. This matters because a port sent forward would give the two sides a private two-way line that skips the middle. Shared memory can be copied, so the middle looks for it and refuses it.

The middle can be a page, as here, or a worker. Whoever holds it can close both ends, which cuts the link for both sides.

Step by step

What each press of Next does in the demo at the top.

  1. Join them one way. This page makes two channels. The library gets an end it can post into. The florist gets an end it can hear on.
  2. Library: publish a price. The library posts a price. This page posts it on, and the florist hears it.
  3. Florist: post an order back. The florist posts into its port. The message reaches this page and goes no further. The library hears nothing.
  4. Florist: post a port back. The florist tries to open a way back by posting a port. This page closes that port.
  5. Library: send a port forward. The library tries to hand the florist a private line. A port cannot be copied, so posting the message on fails, and the florist gets nothing.
  6. Cut the link. This page closes its two ends.
  7. Library: publish a price. The library posts again. Nothing is on the other end, and the florist hears nothing.

Give a chart widget your figures on a port it cannot answer on

The idea: Giving a third-party widget your figures to draw, on a port it cannot answer on.

What you are looking at

The widget stands in for someone else's code. It is a sandboxed frame with an opaque origin and a Content Security Policy that forbids it any network access. This page sends it a month of spending to draw. The widget receives the figures on a real port, and then tries two ways to send them somewhere: a network request, and a message back into the port. The browser blocks the first. The second reaches this page's valve and stops there, and this page counts it.

The code

const link = oneWay();
widget.postMessage({ cmd: "feed" }, "*", [link.receive]);

link.send.postMessage({ figures });       // the widget draws them

// the widget, trying
port.postMessage({ stolen: figures });    // stops at the valve
fetch(somewhere, { body: figures });      // blocked: default-src 'none'

Step by step

What each press of Next does in this demo.

  1. Give the widget a one-way port. This page makes the two channels and gives the widget the end it can hear on.
  2. Send this month's spending. The figures go down the port, and the widget draws them.
  3. Widget: try to send the figures out. The widget posts the figures back into its port and tries a network request. Neither arrives anywhere.

A stream given as read-only still lets the reader signal the writer

The idea: Checking whether a read-only handle is one-way before relying on it.

What you are looking at

A ReadableStream looks one-way: the holder can read and has nothing to write into. But a stream asks its source for the next chunk only when the reader wants one, so the writer can see when each read happens. The frame here holds only a readable stream. It spells a word by choosing when to read: a short wait for a 0, a long wait for a 1. This page reads the word back from nothing but the times its own pull() was called. Then the same frame gets a one-way port. Messages on a port arrive when the sender posts them, and nothing the receiver does changes that, so there is nothing to read back.

The code

// the writer sees when the reader reads
const readable = new ReadableStream({
  pull(controller) { times.push(performance.now()); controller.enqueue("tick"); },
}, { highWaterMark: 0 });
frame.postMessage({ readable }, "*", [readable]);

// the reader, holding only the readable, sends bits with its timing
for (const bit of bits) { await wait(bit ? 360 : 120); await reader.read(); }

Step by step

What each press of Next does in this demo.

  1. Give the frame a read-only stream. The frame gets a stream it can read. It has nothing to write into.
  2. Frame: spell a word by when it reads. The frame reads slowly or quickly, one bit per read. This page works the word out from the times its source was asked.
  3. Give the frame a one-way port. Now the same ticks go to the frame as messages on a one-way port.
  4. Frame: try the same on the port. The frame takes its messages on the same rhythm as before. This page sends on its own clock and sees no difference.

Common mistakes

  • Only the port is one-way. A frame can still call parent.postMessage, make network requests or navigate itself. Close those with a sandbox, a content security policy and by not listening.
  • A readable stream is not a one-way link. The reader chooses when to read, and the writer can see that. The timing demo below reads a word out of it.
  • Forwarding with a transfer list, or forwarding event.ports, lets a port through, and then it is no longer one-way.
  • Every message passes through the middle and is copied twice. For large buffers that costs time.
  • If the page in the middle closes, the link is gone.
  • Two contexts that share a thread can still signal by keeping it busy, whatever joins them. A frame in the same process as the page delays the page's timers when it loops.

Measured

Chromium 157, between two real origins: 0 of the messages posted by the receiving site reached the sending site, and a message carrying a port was refused with a DataCloneError. Through a transferred ReadableStream, a reader in a sandboxed frame sent 16 bits to the writer by timing its reads, and all 16 were read correctly. Other browsers are being filled in from the lab's results.

Let another origin sign with your key without giving it the key

What you are looking at

The vault makes a signing key the browser will not let anyone read, itself included. It gives this page a port that signs. This page lends the shop a weaker port: orders only, three uses. The shop gets real signatures that anyone can check against the public key, and at no point does the key, or the full port, move.

The code

// the vault
const { privateKey, publicKey } = await crypto.subtle.generateKey(ECDSA, false, ["sign", "verify"]);
port.onmessage = async ({ data }) => port.postMessage({ id: data.id, signature: await sign(privateKey, data.text) });

// this page, lending less than it has
lent.onmessage = ({ data }) => {
  if (uses-- > 0 && data.text.startsWith("order:")) vault.postMessage(data); else refuse(data);
};

Using it

// a company's purchasing page, its key vault in one frame, a florist's ordering widget in another
// the vault: how it signs, and how it gives out the public half of the key
const ECDSA = { name: "ECDSA", namedCurve: "P-256" }, SHA = { name: "ECDSA", hash: "SHA-256" };
const sign = (key, text) => crypto.subtle.sign(SHA, key, new TextEncoder().encode(text));
port.postMessage({ publicKey: await crypto.subtle.exportKey("jwk", publicKey) });

// the page: pass answers down to the widget, and say why when it refuses
vault.onmessage = ({ data }) => data.publicKey ? publish(data.publicKey) : lent.postMessage(data);
const refuse = (data) => lent.postMessage({ id: data.id, refused: "this port signs orders only, three times" });

// the florist's widget: ask, then get a signature or a refusal
port.postMessage({ id: 1, text: "order: 2 dozen tulips" });
port.postMessage({ id: 2, text: "pay: 5000 to the florist" });
port.onmessage = ({ data }) => data.refused ? showError(data.refused) : sendOrder(data.id, data.signature);

// anyone with the public key can check an order. The florist has it as jwk
const key = await crypto.subtle.importKey("jwk", jwk, ECDSA, false, ["verify"]);
const ok = await crypto.subtle.verify(SHA, key, signature, new TextEncoder().encode(text));

// the buyer signs out
lent.close();
// The widget still holds its port. Nothing answers it now, and it is told nothing.

Where you would use it

A real case. A company buys flowers through a florist's ordering widget, which sits in a frame on the company's purchasing page. The florist only accepts orders signed with the company's key, and that key lives in a vault frame from the company's identity provider. The page holds the vault's signing port and lends the widget a weaker one: orders only, three uses. The widget gets signed orders it can send to the florist, and its attempt to sign a payment is refused by the page. When the buyer signs out the page closes the lent port, and the widget can sign nothing more.

How it works

WebCrypto can make a key that cannot be exported. Code can use it and no code can read it. The vault frame makes one and never sends it anywhere.

What the vault gives out is a port. Post bytes in, get a signature back. Whoever holds that port can sign, for as long as the vault keeps listening.

The page then lends the shop a weaker port of its own: orders only, three uses. The shop's requests pass through the page, which checks them and forwards the allowed ones. So there are three layers. Each hands on less than it holds and can cut off the one below.

Step by step

What each press of Next does in the demo at the top.

  1. Ask the vault. The vault makes a key nobody can read, and gives this page a port that signs.
  2. Lend the shop. This page lends the shop a weaker port: orders only, three uses.
  3. Shop: sign an order. The shop asks for a signature. The request passes through this page to the vault, and the result is checked here.
  4. Shop: try to sign a payment. The shop asks to sign a payment. This page refuses, because that port only does orders.
  5. Take the port back. The shop's port is closed.

A wallet the shop can charge, up to a limit you set

The idea: Spending rules: amount caps, allow-lists and expiry enforced in the forwarding handler.

What you are looking at

The wallet is a frame on its own origin that pays whoever asks down its port. This page holds that port and does not pass it on. It gives the shop a port of its own, and forwards a charge to the wallet only if the running total stays under fifty. The shop cannot go around it, because the only port the shop has ends in this page.

The code

let spent = 0;
shopPort.onmessage = ({ data }) => {
  if (spent + data.amount > 50) return shopPort.postMessage({ refused: "over the limit" });
  spent += data.amount;
  walletPort.postMessage(data);             // only now does the wallet hear of it
};

Step by step

What each press of Next does in this demo.

  1. Let the shop charge up to 50. The shop gets a port that ends here, not at the wallet.
  2. Shop: charge 20. 20 is under the limit. This page passes it on and the wallet pays.
  3. Shop: charge 20. 40 so far. Still allowed.
  4. Shop: charge 20. This would make 60. This page refuses, and the wallet never hears of it.

One API key, used by two apps, each under its own limit

The idea: API credentials held by one origin and used by many under limits.

What you are looking at

The key holder has a key that cannot be read, and signs requests with it. Two apps from other origins need signed requests. Neither is given the key. Each is given its own port to the key holder, and each port has its own allowance: three requests for the weather app, one for the garden app. The key holder counts per port, so it knows who is asking without anyone having to say.

The code

// the key holder, once per app
const { port1, port2 } = new MessageChannel();
let left = allowance;
port1.onmessage = async ({ data }) => {
  if (left-- <= 0) return port1.postMessage({ refused: "allowance used" });
  port1.postMessage({ signed: await crypto.subtle.sign("HMAC", key, encode(data.request)) });
};
give(app, port2);

Step by step

What each press of Next does in this demo.

  1. Give each app a line to the key holder. Two ports, two allowances. The key stays where it is.
  2. Weather app: sign a request. The key holder signs it. One of three used.
  3. Garden app: sign a request. The garden app's one request.
  4. Garden app: sign a request. Its allowance is used. The weather app's is untouched.

Already running

Things to try

  • Have the shop sign an order, then try a payment. The second is refused by the page, not the vault.
  • Use the port three times and try a fourth.
  • Take the port back and try again.

Common mistakes

  • The vault signs whatever it is sent. The rules live in the layer that forwards, so that layer must be one you trust.
  • Compare with sending the key itself, which cannot be undone.

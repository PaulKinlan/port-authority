Port patterns / Between real sites

Send a key to another site: it gets a copy you cannot take back

What you are looking at

A CryptoKey can be posted to another origin. This page makes a signing key that cannot be read, and sends the key itself to the florist's site. The florist can now sign as you. It cannot read the key either, but it can keep it: it saves the key in its own IndexedDB, and after a reload it still has it. Nothing this page does can undo that. Compare the signer pattern, where the key stays put and only a port travels.

The code

const { privateKey } = await crypto.subtle.generateKey(ECDSA, false, ["sign"]);
floristWindow.postMessage({ key: privateKey }, floristOrigin);   // a copy, not a move

// the florist, on its own origin
await db.put(key, "theirs");                 // kept, for as long as it likes
await crypto.subtle.sign(ECDSA, key, bytes); // signs as you

Using it

// a flower company: sign-in pages on one origin, the shop (the florist) on another
// the sign-in page: give the server the public half of the pair, so it can check signatures
const spki = await crypto.subtle.exportKey("spki", publicKey);
await fetch("/devices", { method: "POST", body: spki });

// the florist: take a key from the sign-in origin and from nowhere else
addEventListener("message", async (e) => {
  if (e.origin !== signInOrigin || !e.data?.key) return;
  await db.put(e.data.key, "theirs");
});

// the florist, a week later. The sign-in page is not open.
const key = await db.get("theirs");
const signature = await crypto.subtle.sign(ECDSA, key, bytes);   // sent to the server with the order

// the person signs out. The key cannot be taken back from the florist,
// so the sign-in page asks the server to stop accepting its signatures.
await fetch("/devices/this-one", { method: "DELETE" });

Where you would use it

A real case. A flower company runs its sign-in pages on one origin and its shop on another. When a person signs in, the sign-in page makes a signing key, gives the public half to the company's server, and posts the private key to the shop. The shop keeps the key in its own IndexedDB and signs each order with it, so the sign-in page does not have to stay open. This is right only because one company owns both origins and the shop is meant to keep the key. The moment to plan for is sign-out: the sign-in page cannot remove the key from the shop's storage, so it asks the server to stop accepting that key's signatures.

How it works

A CryptoKey can be cloned by postMessage, including to another origin, and including when it is marked non-extractable. The receiver gets a working key.

Non-extractable means nobody can read the bytes. It does not mean nobody else can have the key. The florist cannot export it, and it does not need to: it stores the key object in its own IndexedDB and still has it after a reload.

So you can't take a posted key back. This page can destroy its own copy and the florist keeps signing as this page for ever. In the signer pattern only a port was sent, and closing it ended the access.

Step by step

What each press of Next does in the demo at the top.

  1. Send the key itself. A copy of the key goes to the florist's real site. This page still has its own.
  2. Florist: sign an order. The florist signs with the key, and this page checks the signature. It is valid: the florist can sign as this page.
  3. Reload the florist. The florist's page is thrown away and loaded again. It saved the key in its own storage first.
  4. Florist: sign an order. It still has the key, and still signs. There is no way to take a copied key back.

Make a key on the page, then keep it only in a worker

The idea: Moving a key from a setup page to a worker on the same origin.

What you are looking at

Giving a key away is permanent, which is sometimes what you want. This page makes a signing key and posts it to its own worker, then drops its copy. From here on the page cannot sign anything by itself. A script injected into the page finds no key to use. It can only ask the worker, which can say no.

The code

const { privateKey, publicKey } = await crypto.subtle.generateKey(ECDSA, false, ["sign", "verify"]);
worker.postMessage({ key: privateKey });     // a copy goes to the worker
// let the page's copy go out of scope: the worker now holds the only one

worker.postMessage({ sign: "order 1" });     // the page can ask

Step by step

What each press of Next does in this demo.

  1. Make a key and give it to the worker. The page makes a key nobody can read, posts it to its worker and forgets it.
  2. Ask the worker to sign. The worker signs. This page checks the signature with the public half.
  3. Page: try to sign by itself. The page has no key any more.

Already running

  • Provisioning: an origin you trust completely is given a key to keep. See the demo at the top of this page.
  • If you want to be able to change your mind, send a port and not the key. See the signer, which sends a port instead.

Things to try

  • Send the key, have the florist sign, and see the signature verify here.
  • Destroy this page's copy and reload the florist. It still signs.

Common mistakes

  • There is no revocation. The only fix is a new key pair.
  • The receiver's storage is its own. Clearing your site data does not clear theirs.

Measured

Chromium 157: a non-extractable ECDSA key posted to a frame on a real second origin signs there, is stored in that origin's IndexedDB, and survives a reload of that frame. Other browsers are being filled in from the lab's results.

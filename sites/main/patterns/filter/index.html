Run live video through a filter on another origin

What you are looking at

Video can leave your page one frame at a time and come back changed. The picture on the left is drawn by this page, and it is your camera if you turn that on. The filter lives on another origin, in a sandbox. It has no camera, cannot see this page, and holds each frame only until it sends it on. Frames are moved, not copied: after sending, this page's own handle to the frame is empty. A VideoFrame is the natural thing to move. A browser hands one to a worker, or to a frame of your own site. Chrome will not hand one to another process, and a sandboxed frame or a frame from another site now runs in one. So the page tries a VideoFrame, and if the filter cannot rebuild it, it moves an ImageBitmap from then on, which does cross. The note under the right-hand picture says which was used. It is a way to build video plug-ins that get pixels and nothing else.

The code

const frame = new VideoFrame(source, { timestamp });
port.postMessage({ frame }, [frame]);          // frame is now closed here

// the filter, on its own origin
port.onmessage = ({ data }) => {
  ctx.filter = "invert(1)"; ctx.drawImage(data.frame, 0, 0); data.frame.close();
  const out = new VideoFrame(canvas, { timestamp: data.frame.timestamp });
  port.postMessage({ frame: out }, [out]);
};
// a frame the browser could not rebuild here arrives as this, with nothing in it
port.onmessageerror = () => port.postMessage({ unreadable: true });

// the page again: an ImageBitmap crosses where a VideoFrame does not
const bitmap = await createImageBitmap(source);
port.postMessage({ bitmap }, [bitmap]);

Using it

// a video call page, and a background blur plug-in from another company in a sandboxed frame
// sendNext runs for each camera picture. source is that picture, and carry is what it travels as
let carry = "VideoFrame", waiting = false;
const sendNext = async (timestamp) => {
  if (waiting) return;                          // one picture out at a time
  waiting = true;
  if (carry === "VideoFrame") {
    const frame = new VideoFrame(source, { timestamp });
    port.postMessage({ frame }, [frame]);
  } else {
    const bitmap = await createImageBitmap(source);
    port.postMessage({ bitmap }, [bitmap]);
  }
};
port.onmessage = ({ data }) => {
  waiting = false;
  if (data.unreadable) { carry = "ImageBitmap"; return; }   // that picture is lost. Bitmaps from now on
  const picture = data.frame || data.bitmap;
  output.drawImage(picture, 0, 0);              // the blurred picture, which the call sends out
  picture.close();
};
// If the plug-in stops answering, waiting stays true and the picture stops. Use a timeout to notice.

Where you would use it

A real case. A video call page offers background blur as a plug-in made by another company. The plug-in runs in a sandboxed frame, so it has no camera and cannot read the page. The page hands it one camera picture at a time down a port, and draws what comes back on the canvas that the call sends out. In Chrome 159 the first picture, a VideoFrame, arrives unreadable in that frame, and the plug-in answers { unreadable: true }. The page then sends each picture as an ImageBitmap, and the blur works from the next picture on.

How it works

A VideoFrame is a handle to decoded pixels, often on the GPU. It is transferable, so one frame can be handed to another context without copying the picture.

The page makes a frame from its canvas, transfers it to the filter, and is left holding an empty handle. The filter draws the frame through an effect, closes it, makes a new frame from the result and transfers that back.

How far a VideoFrame can go depends on the browser. Chrome hands one to a worker and to a frame of the same site, which run in the page's own process. It will not rebuild one in another process, and a sandboxed frame, a frame from another site, a shared worker and a service worker all run in one. The sender's postMessage() does not throw. The receiver gets a messageerror event with nothing in it. So the demo listens for that, and when it comes it moves an ImageBitmap instead, which crosses to all of those places. The picture arrives the same either way.

The picture in the demo is drawn by the page on a canvas, sixty times a second, and each frame is made from that canvas. It is not a video file. Turn the camera on and the canvas is filled from the camera instead. Nothing else changes: the filter still has no camera and no permission to use one. It is handed frames.

One frame is in flight at a time. The next leaves when the last returns, so a slow filter lowers the frame rate and never builds a queue.

Step by step

What each press of Next does in the demo at the top.

  1. Connect the filter. This page opens a channel to the filter frame on another origin.
  2. Start the video. Frames leave this page one at a time, pass through the filter, and come back changed. The note under the right-hand picture says what each frame was sent as.
  3. Ask for another effect. This page asks the filter to switch effects over the port.
  4. Remove the filter. The filter frame is destroyed and the output stops with it.

A captions and watermark plug-in that only ever sees pixels

The idea: Background blur, captions or watermarking supplied as a plug-in that gets pixels and nothing else.

What you are looking at

The plug-in is a frame on another origin. Each frame of this page's video is handed to it, it draws a caption and a watermark on top, and hands the frame back. It has no access to the camera, the page or the network path the video came from. A frame goes as a VideoFrame where the browser will hand one to the plug-in, and as an ImageBitmap where it will not. Chrome will not hand a VideoFrame to another process, which is where a frame like this one runs.

The code

// the plug-in
port.onmessage = ({ data }) => {
  ctx.drawImage(data.frame, 0, 0); data.frame.close();
  ctx.fillText(caption, 12, height - 14);
  const out = new VideoFrame(canvas, { timestamp: data.frame.timestamp });
  port.postMessage({ frame: out }, [out]);
};

Step by step

What each press of Next does in this demo.

  1. Start the video. Frames go to the plug-in one at a time and come back with a caption and a watermark.
  2. Change the caption. This page sends new caption text. The next frame comes back with it.

A recorder that gets its own copy of a stream, and cannot touch the original

The idea: Inspecting or recording a stream in a separate context.

What you are looking at

Orders flow from this page to a kitchen display on another origin. An auditor wants a record of every one. The page splits the stream in two with tee() and gives the second branch to a recorder on a third origin. The recorder sees every order and keeps them. It has no way to change, delay or drop what the kitchen receives, because it holds a different stream.

The code

const [forKitchen, forRecorder] = orders.tee();
kitchen.postMessage({ orders: forKitchen }, "*", [forKitchen]);
recorder.postMessage({ orders: forRecorder }, "*", [forRecorder]);

Step by step

What each press of Next does in this demo.

  1. Attach the kitchen and a recorder. The order stream is split, and each origin is handed one branch.
  2. Send an order. One order is written once. Both branches carry it.
  3. Send an order. And another.
  4. Recorder: say what you hold. The recorder reports what it kept.

A blur that runs in a worker, so the page does not stop

The idea: Moving effects off the main thread.

What you are looking at

The picture is 1600 by 900, which is 1.4 million pixels. Blurring it takes a noticeable part of a second. Run on the page, the blur holds the main thread for that long: the marker under "Main thread" stops moving and nothing on the page can respond. Run in a worker, the same function gets the same pixels and the marker keeps moving. The pixels are not copied either way. Their buffer is transferred to the worker and transferred back, so for that time the page does not have them. The number shown is the longest gap between two frames of the page while the blur ran.

The code

import { blur } from "/patterns/effect.js";
const image = ctx.getImageData(0, 0, width, height);

// on the page: nothing else happens until this returns
blur(image.data, width, height);
ctx.putImageData(image, 0, 0);

// in a worker: the buffer leaves, the page carries on, the buffer comes back
worker.postMessage({ buffer: image.data.buffer, width, height }, [image.data.buffer]);
worker.onmessage = ({ data }) =>
  ctx.putImageData(new ImageData(new Uint8ClampedArray(data.buffer), width, height), 0, 0);

// the worker
onmessage = ({ data }) => {
  const pixels = blur(new Uint8ClampedArray(data.buffer), data.width, data.height);
  postMessage({ buffer: pixels.buffer }, [pixels.buffer]);
};

Step by step

What each press of Next does in this demo.

  1. Blur it on the page. The blur runs on the main thread. The marker stops until it has finished.
  2. Draw the picture again. The sharp picture is back.
  3. Blur it in a worker. The pixels go to a worker and come back blurred. The marker did not stop.

Things to try

  • Start the video and cycle the effects.
  • Press Use my camera. The left-hand picture becomes your camera, and the filter is handed its frames. Nothing leaves your browser.
  • Remove the filter. The video on the right stops with it, because every frame went through there.

Common mistakes

  • Every frame must be closed by whoever ends up holding it, or the browser warns and video stalls.
  • Measured in Chrome 159: a VideoFrame reaches a worker and a frame of the same site. It arrives unreadable in a sandboxed frame, a frame on another site, a shared worker and a service worker. An ImageBitmap reaches all of them. In Chromium 157 a VideoFrame still reached a sandboxed frame, which is how this demo was first built.
  • A frame that cannot be rebuilt is not an error at the sender. Listen for messageerror at the receiver, or the video just stops.

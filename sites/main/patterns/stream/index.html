Port patterns / The six basic patterns

Send a stream to another frame

What you are looking at

A ReadableStream is transferable too, so you can hand another origin a live stream and it reads with back-pressure, as if the source were local. Chrome and Firefox can do this today.

The code

const stream = new ReadableStream({ pull(controller) { controller.enqueue(nextChunk()); } });
port.postMessage({ stream }, [stream]);

// other side
port.onmessage = async ({ data }) => { for await (const chunk of data.stream) use(chunk); };

Using it

// a spreadsheet app sends a large sheet to a chart tool, a frame from another company
let next = 0;
const nextChunk = () => sheet.rows.slice(next, (next += 500));
const stream = new ReadableStream({
  pull(controller) {                    // runs when the reader has room for more
    if (next >= sheet.rows.length) return controller.close();
    controller.enqueue(nextChunk());
  },
});
try { port.postMessage({ stream }, [stream]); }
catch { tellPerson("This browser cannot send a stream."); }

// the chart tool
async function use(rows) { await chart.add(rows); }
port.onmessage = async ({ data }) => {
  for await (const chunk of data.stream) await use(chunk);  // a slow use() slows pull()
  chart.finish();                       // reached after controller.close()
};

Where you would use it

A real case. A spreadsheet app lets the person send a sheet to a chart tool from another company, which runs in a frame. The sheet has a million rows, so the app hands the frame a stream and cuts the next 500 rows each time the stream asks for more. The frame draws rows as they arrive, and when it falls behind, the app is asked less often. When the rows run out the app closes the stream and the frame's loop ends. This works in Chrome and Firefox today.

How it works

A ReadableStream can go in the transfer list. The far side receives a stream it can read, and the near side keeps producing into it. Chunks cross as they are made, so the reader starts before the writer has finished.

What a stream adds over a plain port is back-pressure. The stream asks the source for more only when the reader has room. A slow reader on another origin slows the producer on yours, with no code from you.

The stream is moved, not copied. After the transfer the original is locked and the sender cannot read from it.

An answer that appears in another origin as it is written

The idea: Feeding live data, such as model output, to an embedded viewer.

What you are looking at

A language model answers a word at a time. This page stands in for one, and hands the answer to a viewer on another origin as a stream. The viewer shows each word as it arrives. It does not poll and is not sent a message per word by hand: it reads a stream, and when this page stops, the stream ends and the viewer knows the answer is complete.

The code

const answer = new ReadableStream({ async pull(controller) {
  const word = await nextWord();
  word ? controller.enqueue(word) : controller.close();
} });
viewer.postMessage({ answer }, "*", [answer]);

// the viewer
for await (const word of answer) page.append(word + " ");

Step by step

What each press of Next does in this demo.

  1. Stream an answer to the viewer. The answer is handed over as a stream before it has been written. Words appear on the other origin as they are produced.
  2. Stop writing. This page ends the stream early. The viewer is told it is over.

Stream 64 MB to a worker a megabyte at a time

The idea: Handing a large download or a generated file to a worker or another origin without holding it all in memory. Progress reporting, by counting the chunks.

What you are looking at

This page produces a large file a megabyte at a time and gives the worker a stream of it. The worker reads, adds up a checksum and asks for more. The page makes the next megabyte only when asked, so neither side ever holds more than a chunk or two. The progress bar needs no extra messages, because it counts the chunks.

The code

const file = new ReadableStream({ pull(controller) {
  made < TOTAL ? controller.enqueue(nextMegabyte()) : controller.close();   // only when asked
} });
worker.postMessage({ file }, [file]);

// the worker
for await (const chunk of file) { sum = checksum(sum, chunk); postMessage({ read: chunk.length }); }

Step by step

What each press of Next does in this demo.

  1. Stream 64 MB to the worker. The worker is handed a stream. Each megabyte is made when the worker asks for it, and checked as it lands.

Things to try

  • Send a stream and watch chunks arrive one at a time while the page is still producing.
  • Start again and send two. Each is independent.

Common mistakes

  • If a stream is passed on through a middle context, it keeps flowing through that context. Remove the middle and the reader stalls with no error.
  • A write to a transferred WritableStream can resolve before the far side has refused it.

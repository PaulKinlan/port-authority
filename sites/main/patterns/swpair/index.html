Port patterns / Other devices, Service Workers, sockets and audio

Join the service workers of two sites with a port

What you are looking at

The florist's site and the library's site each have a service worker. A service worker can post to pages of its own site and to nothing else, so the two cannot reach each other. A port can be carried between them. The florist's worker makes a channel, keeps one port and gives the other to its page. The page sends that port over a line it holds to the library's page, and the library's page gives it to the library's worker. Now each worker holds one end of the same channel, and they ask each other questions with no page taking part. The answers are read from each site's own Cache Storage. A browser stops a service worker that has been idle for about thirty seconds, and the port is lost with it. Nothing tells the other worker. So each question has a time limit of 1.5 seconds. When it passes, the asking worker closes its port, makes a new channel, and has the pages carry one end across again. In the diagram this page gave the two pages their line. On the real web the florist's page opens the library's window and gives it one, which the link under the demo does.

The code

// florist's service worker: make a channel, keep one port, give the other to my page
const { port1, port2 } = new MessageChannel();
peer = port1;
client.postMessage({ pair: "carry" }, [port2]);

// florist's page: it opened the library's window earlier and gave it one end of a channel.
// The port from the worker goes over that port.
navigator.serviceWorker.onmessage = (event) =>
  lineToLibraryPage.postMessage({ carry: true }, [event.ports[0]]);

// library's page: give the port to its own worker. This starts the worker if it was stopped.
lineToFloristPage.onmessage = (event) =>
  registration.active.postMessage({ pair: "peer", from: "florist" }, [event.ports[0]]);

// library's service worker: this port now reaches the florist's worker directly
onmessage = (event) => { peer = event.ports[0]; peer.onmessage = answer; peer.postMessage({ hello: "library" }); };

// either worker, later: a question, with a time limit, because a stopped worker says nothing
const reply = new MessageChannel();
peer.postMessage({ ask: "Dune" }, [reply.port2]);
const answer = await firstMessageOrTimeout(reply.port1, 1500);
if (!answer) { peer.close(); peer = null; await join(); /* a new channel, carried across again */ }

Using it

// one company's mail app and calendar app, on two origins. Mail is the florist, the calendar is the library.
// the calendar's worker: answer() reads its own cache and replies on the port that came with the question
async function answer(event) {
  const busy = await (await caches.match("/busy.json")).json();
  event.ports[0].postMessage({ free: !busy.includes(event.data.ask) });
}

// the mail's worker: a mail tab asks if a time is free, and the worker asks the calendar's worker
addEventListener("message", (event) => {
  if (event.data.time) event.waitUntil(isFree(event.data.time).then((free) => event.source.postMessage({ free })));
});

async function isFree(time, tries = 2) {
  if (!peer && !(await join())) return null;          // no page of each app is open to carry a new port
  const reply = new MessageChannel();
  peer.postMessage({ ask: time }, [reply.port2]);
  const answer = await firstMessageOrTimeout(reply.port1, 1500);
  if (answer) return answer.free;
  peer.close(); peer = null;                       // no answer in time. Treat the port as lost.
  return tries > 1 ? isFree(time, tries - 1) : null;  // once more, on a new port
}

Where you would use it

A real case. One company runs a mail app and a calendar app on two origins, and each has a service worker with its own Cache Storage. The mail app shows, beside an invitation, whether that time is free. The person opens the calendar from the mail page, the two pages carry one port across, and after that the mail's worker asks the calendar's worker directly, for every mail tab. The interesting moment comes when the browser stops the calendar's worker for being idle: the next question gets no answer in 1.5 seconds, so the mail's worker closes its port, calls join(), and the pages carry a new port across. That repair needs both pages to be open still.

How it works

A service worker can post to the pages of its own site, through clients, and to nothing else. It cannot open a window, it has no window.postMessage to another origin, and it cannot be embedded. So two service workers on two sites have no way to find each other. What they can do is hold a MessagePort, and a port can be carried by anyone who holds it. The join is one port making four hops: from the florist's worker to the florist's page, over a line the two pages share, to the library's page, and into the library's worker. After that the port joins the two workers and nothing else.

The pages need a line between them first. On the real web the florist's page opens a window on the library's site and posts it one end of a new channel, checking the origin of the window it is talking to. That window is the only time the two sites are on screen together. Both pages can close afterwards, and the workers keep talking as long as both are running.

They don't run for long. A browser stops a Service Worker that has been idle for about thirty seconds, and starts it again for the next fetch or message. Everything in its variables is lost, the port included, and the worker at the other end is not told. A close event for ports was added to the HTML standard in 2024, never shipped on by default in any browser, and was removed again in October 2026. So the only signal is silence, and every question here carries a reply port of its own and has a time limit of 1.5 seconds. When the time passes, the asking worker closes its end, makes a new channel, and asks its pages for one that holds a line to the other site. That page carries the new port across, the other page hands it to its worker, and the question is asked again. The demo's forget button stands in for a stop, because a page cannot ask the browser to stop a worker. The test for this page also stops both workers for real, through the browser's debugging protocol, and the next question is answered over a new port.

The rejoin needs a page of each site that still holds a line to the other. Without that, a worker that loses its port has lost the other site until a person opens the two pages together again. Shared workers have this problem less. A shared worker is not stopped while one of its tabs is open, so a link between two of them lasts as long as each site has a tab, with no time limits at all.

Once two workers are joined, the port between them can carry more ports. A tab can be given a port whose other end is the other site's worker, made by its own worker and sent over the join. A fetch on one site can be answered by the other site's worker, with the body as a ReadableStream that is transferred and still being written. And none of what arrives says where it came from: a message on a port has an empty origin and no source. What a worker knows about the other end is what the page that handed it the port said, so each page checks the origin of the window it got the port from, and a receiver that needs more can ask the other end to sign something.

Step by step

What each press of Next does in the demo at the top.

  1. Give the two pages a line to each other. This page makes a channel and gives one port to the florist's page and one to the library's page. It stands in for the florist's page opening the library's window.
  2. Join the two workers. The florist's worker makes a channel and gives one port to its page. The port goes over the pages' line, and the library's page gives it to the library's worker.
  3. Florist's worker: ask about Dune. The florist's worker posts the question into its port. The library's worker reads its own cache and answers. Neither page took part.
  4. Library's worker: ask about tulips. The same port carries a question the other way.
  5. Make the library's worker forget. The library's worker closes its port and forgets it. This is what happens when the browser stops it. The florist's worker is told nothing.
  6. Florist's worker: ask about Dune. No answer comes in 1.5 seconds. The florist's worker closes its port, makes a new channel, and the pages carry one end across. Then it asks again and is answered.
  7. Close the library's page. The library's page is destroyed. The two workers still hold their ports.
  8. Florist's worker: ask about Dune. It is answered. The port between the workers does not pass through any page.
  9. Make the florist's worker forget. The florist's worker closes its port. There is no page on the library's side to receive a new one.
  10. Florist's worker: ask about Dune. The florist's worker sends a new port out and nothing answers on it. Without a page on each side, the workers cannot be joined again.

Each tab gets its own port to the other site's service worker

The idea: A tab that needs the other site often gets a port of its own to that site's worker, so its questions do not queue through its own worker.

What you are looking at

The two workers are joined by one port. A florist tab that wants to ask the library something could ask the florist's worker to pass the question on, and then every question from every tab would queue through that worker. Instead the tab asks its worker for a line. The florist's worker makes a new channel, gives the tab one port, and posts the other port to the library's worker over the port that joins them. From then on the tab asks the library's worker directly. The florist's worker can forget its own port, or be stopped, and the tab's line still works, because the line never passed through it. The line ends when the library's worker is stopped. The tab finds out the same way a worker does, by getting no answer, and asks for another line.

The code

// florist's service worker: a tab asked for a line
const line = new MessageChannel();
tab.postMessage({ pair: "line" }, [line.port1]);
peer.postMessage({ line: true, from: "florist" }, [replyPort, line.port2]);   // a port, sent over a port

// library's service worker: answer on whatever port arrives over the port
peer.onmessage = (event) => {
  if (event.data.line) event.ports[1].onmessage = answer;
};

// florist's tab: ask the library's worker directly
line.postMessage({ ask: "Dune" }, [reply.port2]);

How it works

There are three kinds of port in this demo. The teal one joins the two pages, and is only ever used to carry other ports. The yellow one joins the two workers. Each red one joins a single florist tab to the library's worker.

A tab cannot make its own line, because it has no way to reach the library's worker. Its own worker can. When a tab asks, the florist's worker calls new MessageChannel(). It posts one port to the tab with client.postMessage. It posts the other to the library's worker in the transfer list of an ordinary message on the yellow port. That message carries two ports: one for the library's worker to say it has the line, and the line itself.

The library's worker sets onmessage on the port it was sent and keeps it in a set. From that moment the florist's worker holds neither end. A question from the tab goes from the tab's thread to the library's worker's thread and nowhere else, so the florist's worker can lose its yellow port, or be stopped by the browser, and the tab does not notice.

The red line lasts as long as the library's worker keeps running. When that worker is stopped, its ends of every line are lost together. A tab is not told. It learns the way a worker does: its next question gets no answer within 1.5 seconds. It then asks its own worker for a new line, and if that worker has no yellow port either, the pages carry a new one across first.

Step by step

What each press of Next does in this demo.

  1. Give the two pages a line to each other. The florist's page and the library's page get a direct channel between them.
  2. Join the two workers. The florist's Service Worker makes a channel, and the pages carry one port across to the library's Service Worker.
  3. Tab one: get a line of its own. The florist's worker makes a channel, gives tab one a port, and sends the other port to the library's worker over the port that joins them.
  4. Tab two: get a line of its own. A second channel, for the second tab.
  5. Tab one: ask about Dune on its line. Tab one posts to the library's worker. The florist's worker is not involved.
  6. Make the florist's worker forget. The florist's worker closes the port that joins it to the library's worker.
  7. Tab two: ask about Dune on its line. Tab two is still answered. Its line was never part of the florist's worker.
  8. Make the library's worker forget. The library's worker closes every port it holds, as a stop would. Both lines end there.
  9. Tab one: ask about Dune on its line. No answer comes in 1.5 seconds, and the tab says its line is gone.
  10. Tab one: get a line of its own. The florist's worker has no port either, so the pages carry a new one across first. Then tab one gets a new line.

An address on the florist's site, answered by the library's service worker

The idea: An address on one site whose content comes from the other site's worker, as a stream.

What you are looking at

The florist's page fetches /pair/from-other/shelf.txt, an address on the florist's own site. No such file exists on the florist's server, and the request never leaves the browser. The florist's worker takes the request and asks the library's worker for the file over the port that joins them. The library's worker reads its cache and posts back a status, headers and a ReadableStream. The stream is transferred, so the florist's worker returns it as the body of the response while the library's worker is still writing into it. The page reads the file a line at a time as the lines are written. The library's server is not contacted, and the library's page does nothing. If the library's worker was stopped, the first try gets no answer, a new port is carried across, and the same fetch still succeeds, a little later.

The code

// florist's service worker
addEventListener("fetch", (event) => {
  if (!new URL(event.request.url).pathname.startsWith("/pair/from-other/")) return;
  event.respondWith(askPeer({ get: "shelf.txt" }).then((a) => new Response(a.body, a)));
});

// library's service worker: the body is a stream, and it is moved, not copied
peer.onmessage = async (event) => {
  const body = new ReadableStream({ pull(controller) { /* a line every 350 ms */ } });
  event.ports[0].postMessage({ status: 200, headers, body }, [body]);
};

How it works

A page's fetch for an address on its own site goes to that site's service worker first. The florist's worker looks at the path. For anything under /pair/from-other/ it calls event.respondWith with a promise, and then asks the library's worker for the file over the port that joins them. The question carries a reply port.

The library's worker builds the answer as a plain object: a status, some headers, and a ReadableStream for the body. It posts that on the reply port with the stream in the transfer list. A transferred stream is moved. The library's worker keeps the end it writes into, and the florist's worker receives an end it can read from.

The florist's worker does not read it. It passes the stream straight to new Response(body, { status, headers }) and returns that. So each line the library's worker writes goes to the florist's worker, and from there to the page that called fetch, as it is written. The page reads the response with a stream reader and shows each line when it arrives, 350 milliseconds apart.

The page cannot tell that another site was involved. The address is the florist's, the response has no cross-origin restrictions, and no request went to any server. That is also the risk: whatever the library's worker sends is served as the florist's own content, so a site should only do this with a site it trusts as much as itself.

If the library's worker has lost its port, the first question gets no answer. The florist's worker waits 1.5 seconds, has a new port carried across, and asks again, all inside the same respondWith. The page sees one fetch that took longer.

Step by step

What each press of Next does in this demo.

  1. Give the two pages a line to each other. The florist's page and the library's page get a direct channel between them.
  2. Join the two workers. The florist's Service Worker makes a channel, and the pages carry one port across to the library's Service Worker.
  3. Florist's page: fetch the library's shelf. The page fetches an address on its own site. Its worker asks the library's worker, which answers with a stream and writes four lines into it.
  4. Make the library's worker forget. The library's worker closes its port, as a stop would.
  5. Florist's page: fetch the library's shelf. The first try gets no answer. A new port is carried across, and the same fetch is answered.
  6. Florist's page: fetch a file the library does not have. The library's worker answers 404, and that is the status the page sees.

A third site introduces two service workers and closes

The idea: A third site that knows both introduces their workers and leaves.

What you are looking at

Here neither site opens the other. A third site, the planner, has a frame of each. It makes one channel and posts a port to each page, addressed so that only that site can receive it. Each page gives its port to its own worker. The planner keeps nothing, and when its frame is destroyed the two workers go on talking. This is the cheapest way to join two workers, and it is the least durable. With the planner gone there is nobody who can carry a new port, so the link lasts until either worker is next stopped and then it cannot be repaired. Each page is trusting the planner about who holds the other port: the page accepts a port only from the planner's origin, and what it tells its worker about the other end is what the planner said.

The code

// planner's page: one channel, one port to each site, addressed
const { port1, port2 } = new MessageChannel();
floristFrame.postMessage({ pair: "adopt", from: "library" }, floristOrigin, [port1]);
libraryFrame.postMessage({ pair: "adopt", from: "florist" }, libraryOrigin, [port2]);

// each site's page: take a port only from the planner, and give it to my worker
addEventListener("message", (event) => {
  if (event.origin !== plannerOrigin) return;
  registration.active.postMessage({ pair: "peer", from: event.data.from }, [event.ports[0]]);
});

How it works

The planner's page has a frame of the florist and a frame of the library, or here, sits beside them in the same page. It can post to both windows. It calls new MessageChannel() and posts one port to each with window.postMessage, giving the site's origin as the second argument, so the browser will deliver the message only if that window is still showing that site.

Each page receives an ordinary window message. This is the one moment the browser says who is speaking: event.origin is the planner's origin. The page checks it, and refuses a port from anywhere else. Then it gives the port to its own worker with registration.active.postMessage, along with what the planner said about the other end.

Now the two workers hold the two ends of the planner's channel. The planner kept neither, so it cannot read what they say, and destroying its frame changes nothing.

What is missing is a way back. In the demo at the top of the page, the two pages hold a line to each other and can carry a second port when the first is lost. Here the only thing that could reach both sites was the planner. When one worker is stopped, the other gets no answer, asks its pages for one that can carry a port, and none can.

Step by step

What each press of Next does in this demo.

  1. Planner: introduce the two sites. The planner makes a channel and posts one port to each page. Each page gives its port to its worker.
  2. Close the planner. The planner's frame is destroyed. It held no port, so nothing changes for the workers.
  3. Florist's worker: ask about Dune. The florist's worker asks, and the library's worker answers.
  4. Library's worker: ask about tulips. And the other way.
  5. Make the library's worker forget. The library's worker closes its port, as a stop would.
  6. Florist's worker: ask about Dune. No answer comes. The florist's worker looks for a page that can carry a new port. There is none, because the planner is gone.

Join the shared workers of two sites once, and use the link from every tab

The idea: The same join between two shared workers, used by every tab of both sites, and lasting as long as each site has a tab open.

What you are looking at

The same join, with shared workers. Each site has one shared worker, and every tab of that site holds a port to it. Tab one of each site carries a port across once. From then on, a note posted by any tab of either site goes to its own worker, over the link, and to every tab of the other site. Close the two tabs that made the link and nothing changes. A shared worker is not stopped while one of its tabs is open, so this link needs no time limits and is never rejoined. It ends when the last tab of either site closes. A shared worker is not told when a tab goes, so each tab says goodbye on pagehide. Inside a frame, as here, a shared worker belongs to the top-level site as well as its own, so these two workers are the florist's and the library's workers for pages embedded on port-authority.dev.

The code

// florist's shared worker: every florist tab is connected
onconnect = ({ ports: [tab] }) => {
  tab.onmessage = ({ data, ports }) => {
    if (data.join) { const c = new MessageChannel(); link = c.port1; tab.postMessage({ carry: true }, [c.port2]); }
    if (data.peer) link = ports[0];   // on the library's side
    if (data.note) { everyTab(data.note); link?.postMessage({ note: data.note }); }
  };
};
link.onmessage = ({ data }) => everyTab(data.note);

// a tab: one port to its own worker, and goodbye when it goes
const { port } = new SharedWorker("/pair-shared.js");
addEventListener("pagehide", () => port.postMessage({ bye: name }));

How it works

A shared worker is one thread for every tab of a site. Each tab connects with new SharedWorker(url) and gets a port, and the worker gets the other end in its connect event. The dark cables in the diagram are those ports. The worker keeps them in a list.

The join is the same four hops as for service workers. The florist's shared worker makes a channel and posts one port down the port of the tab that asked. That tab sends it over the line to the library's tab, which posts it to the library's shared worker. The yellow cable is that channel.

A note takes three hops. The tab posts it to its own worker. The worker posts it to every tab in its list and into the yellow port. The other worker receives it and posts it to every tab in its list. No tab holds a port to the other site, and no tab needs to have taken part in the join.

The two tabs that carried the port are not part of the path, so closing them changes nothing. What matters is that each worker stays alive, and a shared worker lives as long as one tab of its site is connected. There is no idle limit, so there are no time limits in this code and no rejoining.

Two things are not reported by the browser. A shared worker is not told when a tab closes, so each tab posts a goodbye in pagehide and the worker takes it off the list. And when a site's last tab closes, its worker ends and the other worker is not told. Its next post into the yellow port goes nowhere, with no error.

Step by step

What each press of Next does in this demo.

  1. Give tab one of each site a line. Florist tab one and library tab one get a direct channel between them.
  2. Join the two SharedWorkers. The florist's SharedWorker makes a channel and tab one carries a port across to the library's SharedWorker.
  3. Florist tab two: post a note. Florist tab two did not take part in the join. Its note reaches both florist tabs and both library tabs.
  4. Close tab one of each site. The two tabs that carried the port are destroyed. Each says goodbye to its worker as it goes.
  5. Library tab two: post a note. The link is still there. The note reaches florist tab two.
  6. Close library tab two. That was the library's last tab, so the browser ends the library's SharedWorker, and its port with it.
  7. Florist tab two: post a note. The florist's worker posts into the link as before. Nothing is at the other end, and nothing says so.

Check who holds the other end of a port that came over a port

The idea: A receiver that checks who holds the other end of a port that came over a port, by asking it to sign a random value.

What you are looking at

A port carries no name. When a port has come over another port, the receiver has only what the sender of the outer message said about it, and the sender may have been told something false by whoever gave it the port. Here this page passes the library two ports, as a page would pass on ports from whoever asked it to. Both ports say "I am the florist" as their first message. One is held by the florist and one by a stranger. The library looks at everything the browser tells it about each message, and it is the same for both: event.origin is an empty string and event.source is null. So the library checks. It has the florist's public key, which a site would publish at an address of its own. It posts a random value into each port and asks for it to be signed. Only the florist has the private key. The port whose signature does not match is closed.

The code

// the receiver: nothing about a port's messages says who holds the other end
port.onmessage = (event) => { event.origin; // ""  event.source; // null };

// so ask the other end to prove it, with a key only the real holder has
const challenge = crypto.getRandomValues(new Uint8Array(32));
port.postMessage({ prove: challenge });
const { signature } = await nextMessage(port);
const ok = await crypto.subtle.verify({ name: "ECDSA", hash: "SHA-256" }, floristPublicKey, signature, challenge);
if (!ok) port.close();

// the florist: its private key cannot be read, so it cannot be given away by mistake
const keys = await crypto.subtle.generateKey({ name: "ECDSA", namedCurve: "P-256" }, false, ["sign", "verify"]);

How it works

When a message arrives from a window, the browser fills in event.origin with the sender's origin, and the sender cannot fake it. A message that arrives on a port has no such field to rely on. A port has no address. Its origin is an empty string and its source is null, whoever posted it.

So what a receiver knows about a port is what it was told by whoever handed it over. That is fine for one hop, where the receiver checked the origin of the window that gave it the port. It is weaker after two hops. This page passes on ports it was given, and it has no idea what is at their other ends. Both ports here open by saying "I am the florist", and the library shows what the browser reports for each. The two lines are identical.

The check uses a key pair. The florist made one with crypto.subtle.generateKey and marked the private key as not extractable, which means no script can read it, the florist's own included. The public key can be given to anyone. The library has it.

The library makes 32 random bytes and posts them into a port. Whoever holds the other end has to post back a signature of those bytes. The library runs crypto.subtle.verify with the florist's public key. The florist's signature passes. The stranger can sign too, but only with a key of its own, and that signature does not pass. The value is new each time, so an old signature cannot be sent again.

This proves who was at the other end when it signed, and a port can still be handed on afterwards. It also depends on the library having the right public key, which in practice means fetching it from the florist's own site over HTTPS.

Step by step

What each press of Next does in this demo.

  1. Give the library the florist's public key. The florist made a key pair when it started. This page passes its public half to the library.
  2. Pass the library a port from the florist. The florist makes a channel and sends one port out. This page passes it on. Its first message says: I am the florist.
  3. Pass the library a port from the stranger. The stranger does exactly the same, with the same first message.
  4. Library: check both ports. The library posts a random value into each port and asks for a signature. The florist's is good. The stranger signs with a key of its own, the signature does not match, and the library closes that port.

Things to try

  • Open the florist's page from the link under the demo. It opens the library's window for real. Join the two workers, close the library's window, and ask again: the workers still talk.
  • Leave that tab alone for a minute, then ask again. The browser has stopped the workers by then, and the page says so: the run name of its worker has changed, and a new port was carried across.
  • In the demo at the top of this page, make the library's worker forget, then run the cross-site fetch demo below. The first try gets no answer and the fetch still succeeds, later.

Common mistakes

  • A port held in a service worker's variable is lost when the browser stops the worker, and nothing tells the other end. Give every question a time limit and be ready to rejoin.
  • A service worker cannot be asked to stay running. event.waitUntil keeps it alive only until the promise it was given settles, and a browser will still stop one that runs too long.
  • Only a page can carry a port between sites. If neither site has a page open that holds a line to the other, a broken join cannot be repaired.
  • A port does not say who holds its other end. Check the origin of the window that gives it to you, and pass on to the worker only what that window is trusted to say.
  • Inside a frame on another site, a shared worker belongs to the top-level site as well as its own. Tabs of the florist embedded on two different sites reach two different shared workers.

Measured

Chromium 157: two service workers on two origins exchange messages over a port carried through two pages, with both pages gone. After both workers are stopped by the browser, the next question gets no answer in 1.5 seconds, a new port is carried across and the question is answered. A ReadableStream sent from one origin's service worker to another's is returned as a fetch response body and read line by line. A message on a port that came over a port has origin "" and source null. Other browsers are being filled in from the lab's results.

Mount another site at a path on yours

What you are looking at

A Service Worker can answer a request by asking a port, and the other end of that port can be on another origin. This page introduces a Service Worker to the florist's site. From then on, every request under /patterns/mounted/florist/ is answered by the florist: pages, images, and a file whose body is a stream that the florist is still writing while this origin reads it. The florist's server is never contacted. Its page, open in a frame, is the server. The same worker script, registered again for /patterns/mounted/library/ and given a port to the library's site, mounts that site beside it. What is mounted here runs as this origin, so mount only what you would let act as you.

The code

// this page: a worker for the path, and a port to the site that will serve it
const reg = await navigator.serviceWorker.register("/mount-sw.js", { scope: "/mounted/florist/" });
const { port1, port2 } = new MessageChannel();
floristFrame.postMessage({ cmd: "serve" }, floristOrigin, [port1]);
reg.active.postMessage({ mount: true }, [port2]);

// Service Worker
origin.postMessage({ path }, [replyPort]);
// the florist answers with a body that is a ReadableStream, transferred
return new Response(answer.body, answer);

Using it

// a wedding planner's site, and one florist it trusts
// the florist's frame: answer each request that comes down the port
addEventListener("message", (e) => {
  if (e.origin !== plannerOrigin || e.data?.cmd !== "serve") return;
  e.ports[0].onmessage = ({ data, ports }) => {
    const body = stockList(data.path);            // a ReadableStream the florist is still writing
    ports[0].postMessage({ status: 200, headers: { "content-type": "text/plain" }, body }, [body]);
  };
});

// the planner's own pages: the florist's files have addresses on this origin
const stock = await fetch("/mounted/florist/stock.txt");
picture.src = "/mounted/florist/tulip.svg";

// the Service Worker was stopped and lost its port. It asks, and the page sends a new one.
// introduce() makes a new channel and posts its two ends, as above.
navigator.serviceWorker.addEventListener("message", (e) => { if (e.data.needMount) introduce(); });

// the planner drops the florist
reg.active.postMessage({ unmount: true });
// Requests under /mounted/florist/ now get a 503 from the worker.

Where you would use it

A real case. A wedding planner's site works with one florist and wants the florist's stock list and pictures inside its own pages. It mounts the florist's site at /mounted/florist/, and the florist's page, open in a frame, answers each request. The planner's pages load those files with an ordinary fetch or img from addresses on the planner's own origin, and the planner runs no proxy. What is mounted runs as the planner's origin, so the planner does this only with a florist it would let act in its name. When the planner drops the florist it tells the worker to unmount, and requests under that path get a 503.

How it works

The tab-as-server pattern answered requests from a tab of the same origin. The port can just as well end on another origin. This page makes a channel, gives one end to the florist's embedded page and the other to its own service worker.

Requests under one path now go down that port. The florist answers with a status, headers and a body. When the body is a ReadableStream it is transferred, and the service worker hands it straight to the browser as the response while the florist is still writing it.

The florist's server is never contacted. Its page, sitting in a frame, is the server. And the content it supplies is served from this origin's address.

The worker script holds no site's name. It reads the path to serve from the scope it was registered with. Registering it a second time with another scope makes a second worker with its own port, so each mounted site has a path of its own and they do not share a port.

Step by step

What each press of Next does in the demo at the top.

  1. Mount the florist's site here. This page gives one end of a channel to the florist's site and the other to a Service Worker for that path.
  2. Open the catalogue. A page at an address on this origin. Its HTML, its picture and a slowly written file all come from the florist, down the port.
  3. Mount the library's site too. The same worker script is registered for a second path and given a port to the library's site.
  4. Open the library's catalogue. A second address on this origin, served by a second site.
  5. Unmount. The florist's worker drops its port. That address has nothing behind it, and the library's still works.

Plug-ins that each add a page, with its own picture, to a host app

The idea: Plug-ins that contribute pages and assets to a host app.

What you are looking at

The host app is a real page on this site. Two plug-ins each want to add a page to it. Each plug-in here is a sandboxed frame with an opaque origin, standing in for a frame from the plug-in maker's site. Installing a plug-in means giving the service worker a port to it, and a path. From then on, requests under that path are answered by the plug-in: its page, and the picture that page asks for. No server is asked for the plug-in's page, and nothing was uploaded. The same caution applies as for any mounted site: a plug-in's page runs as this origin.

The code

// installing a plug-in: a path, and a port to whoever will answer for it
const { port1, port2 } = new MessageChannel();
pluginFrame.postMessage({ cmd: "serve" }, "*", [port1]);
serviceWorker.postMessage({ serve: true, prefix: "/app/calendar/" }, [port2]);

Step by step

What each press of Next does in this demo.

  1. Install the calendar plug-in. The service worker gets a port to the plug-in and a path to use it for. The app lists it.
  2. Open the calendar's page. A real navigation inside the app. The page and its picture come from the plug-in.
  3. Install the invoices plug-in. A second plug-in, a second port, a second path.
  4. Open the invoices' page. The other plug-in answers this one.

Preview a page whose files are kept by a storage provider on another origin

The idea: Serving a person's files from a storage provider's origin into an editor's preview.

What you are looking at

A person's draft lives with a storage provider. The provider here is a sandboxed frame with an opaque origin, standing in for a frame from the provider's site. This editor wants to show it as a real page, with real relative links, and without copying the files here. So the provider is given a path. The preview on the right is a real navigation, and each file it asks for is fetched from the provider over a port as it is needed. Save a new version at the provider and reload: the preview has it, and the editor never held a file.

The code

// the storage provider, answering one request
port.onmessage = ({ data, ports: [reply] }) => {
  const file = files.get(nameFrom(data.url));
  reply.postMessage(file ? { body: file.text, headers: { "content-type": file.type } } : { status: 404, body: "no such file" });
};

Step by step

What each press of Next does in this demo.

  1. Mount the provider's files for preview. The service worker gets a port to the storage provider.
  2. Open the preview. The draft loads as a real page. Its stylesheet is a second request, to the same provider.
  3. Provider: save a new version. The file changes at the provider. Nothing is sent here.
  4. Reload the preview. The preview asks again and gets the new version.

Common mistakes

  • What is mounted runs as your origin, with your cookies and storage. Mount only what you would let act as you.
  • The other site's frame has to stay open.
  • A stopped service worker forgets its port and must be introduced again.
  • Two mounted sites both run as your origin, so they can read each other's storage there.

Measured

Chromium 157: two sites mounted at two paths at once, each answered by its own site. A stream made in a frame on a second origin is accepted by the service worker as a response body, and its three lines arrive about 0.45 s apart. Other browsers are being filled in from the lab's results.

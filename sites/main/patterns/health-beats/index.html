Port patterns / Knowing the other side is still there

Send a beat each way on two one-way ports

What you are looking at

Each side makes a channel, keeps the end it posts into and gives the other side the end to listen on. Then it posts a beat on a timer and never reads its own port. Each side only listens to the other's. Both sides learn whether the other is there, with half the messages of ping and answer, and neither side's code has to match an answer to a question. Each beat says how often beats will come, and whether the page that sent it is hidden, because a browser slows the timers of a hidden page.

The code

import { beat, listen } from "/alive.js";

// each side does the same
const mine = new MessageChannel();
beat(mine.port1, { every: 1000 });           // post into this end, never read it
other.postMessage("beats", origin, [mine.port2]);
// ...and listens on the end the other side sent
listen(theirs, { onState: (state) => show(state) });

Using it

// a slide deck in one window, and its speaker notes in a window the deck opened
// both windows: take the end the other window sent, and listen on it
addEventListener("message", (e) => {
  if (e.source !== other || e.origin !== origin || e.data !== "beats") return;
  const theirs = e.ports[0];
  listen(theirs, { onState: (state) => show(state) });
});

// show() in the deck: when the notes have gone, the button that opens them works again
const show = (state) => { openNotes.disabled = state === "alive" || state === "late"; };

// show() in the notes window: say what has happened to the deck
function show(state) {
  if (state === "alive") notice.textContent = "";
  if (state === "silent") notice.textContent = "The slides are not answering. They may come back.";
  if (state === "closed") { notice.textContent = "The slides have closed."; clearInterval(clock); }
}

// the deck ends the talk and stays open: keep what beat() returns, say goodbye, stop the timer
const beats = beat(mine.port1, { every: 1000 });
endTalk.onclick = () => { beats.bye(); beats.stop(); };

Where you would use it

A real case. A slide deck runs in one window and opens its speaker notes in a second window, which shows the next slide and a clock. Each window makes a channel, beats into one end and posts the other end to the other window. If the notes window is closed or its page hangs, the deck's listener reports it and the deck turns its Open notes button back on. If the deck is closed, the notes window stops its clock and says that the slides have closed. A deck that hangs while it is hidden behind another tab is called silent only after some minutes, because listen() allows a hidden window a minute between beats.

How it works

A heartbeat does not need questions. Each side makes a channel, keeps the end it posts into, and gives away the end to listen on. Then it posts { beat: n, every, hidden } on a timer and never reads its own port. The other side does the same.

That halves the messages, and neither side has to match answers to questions. It also means both sides know about each other. With ping and answer only the asker knows. Here the far side can tell that this page has stopped, which the demo shows when this page stops its beats.

Each beat says how often beats will come, so the listener needs no setting, and whether the page that sent it is hidden. Browsers slow the timers of hidden pages. Chrome's published rule is that a page hidden for more than five minutes, with a timer chain of five or more and no sound for 30 seconds, may run timers only once a minute. Measured below, it can happen sooner. So listen() allows a minute between beats from a page that said it was hidden. A worker's beats are not slowed this way.

A page that is being removed becomes hidden as it goes. An extra beat sent on visibilitychange would tell the listener to wait a minute just as the page disappears, so no beat is sent then.

Step by step

What each press of Next does in the demo at the top.

  1. Connect. This page sends a data port and the end of its beat channel. The far side sends back the end of its own.
  2. This page: stop sending beats. This page stops its timer. The far side, which only listens, sees the beats stop and says so in its log.
  3. Remove the far side. The far side is destroyed. Its goodbye arrives on its beat port.

What you could build with it

Already running

  • A widget that notices the page that embeds it has stopped beating, and stops its own work. See the demo at the top of this page.

Things to try

  • Stop this page's beats and read the far side's log: late, then silent.
  • Remove the far side. Its goodbye comes on the same one-way port as its beats.

Common mistakes

  • A hidden page's timers can be held to once a minute in Chrome, and then a crash takes minutes to notice. If that is too slow, beat from a dedicated worker the page starts: it dies with the page and its timers kept full speed in our measurement.
  • Beats say the sender's timer is running. They do not say it can still do work. Pair them with timeouts on work.

Measured

Chromium 153, real hidden tabs: a tab on its own, beating every second to a shared worker, dropped to one beat a minute between one and two minutes after it was hidden, and the listener's one-minute allowance meant it was never wrongly called silent. A tab opened by a visible tab of the same site kept a one-second pace for about six minutes before dropping to once a minute. Beats from a worker that page had started kept coming every second throughout. Answers to pings from that page slowed as well. A listener that stops hearing beats sent every 0.5 s marks the sender silent after 1.5 to 1.8 s. Other browsers are being filled in from the lab's results.

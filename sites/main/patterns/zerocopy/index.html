Port patterns / More things a port can carry

Move 64 MB between origins without copying it

What you are looking at

Post an ArrayBuffer and it is copied. Put it in the transfer list and the memory itself changes hands: the sender's buffer drops to zero bytes and the cost stops depending on size. Each button sends 64 MB to another origin and back, and times the round trip.

The code

port.postMessage(buffer);            // structured clone: a copy each way
port.postMessage(buffer, [buffer]);  // transfer: buffer.byteLength is now 0

Using it

// a photo editor. A filter plug-in from another company runs in a frame.
const image = ctx.getImageData(0, 0, canvas.width, canvas.height);
const buffer = image.data.buffer;       // 48 MB for a picture of 4000 by 3000
port.postMessage(buffer, [buffer]);
// buffer.byteLength is 0 now, and so is image.data.length.
// The editor holds no pixels until the plug-in sends them back.
// With port.postMessage(buffer) both sides would hold 48 MB.

// the plug-in: change the bytes, then transfer the same buffer back
port.onmessage = ({ data: buffer }) => {
  sepia(new Uint8ClampedArray(buffer));
  port.postMessage(buffer, [buffer]);
};

// the editor: the old view stays empty, so make a new one
port.onmessage = ({ data: buffer }) =>
  ctx.putImageData(new ImageData(new Uint8ClampedArray(buffer), canvas.width), 0, 0);

Where you would use it

A real case. A photo editor lets filter plug-ins from other companies change the picture, each in a frame of its own. A picture of 4000 by 3000 pixels is 48 MB. The editor transfers the buffer to the plug-in, the plug-in changes the bytes and transfers the same buffer back. Only one side holds the buffer at a time, where a plain postMessage would leave 48 MB on each side. While the buffer is away the editor has zero bytes, so it waits for the buffer to return before it draws or lets the person paint.

How it works

An ArrayBuffer in the transfer list changes hands. The bytes stay where they are in memory and ownership moves to the receiver. The sender's buffer becomes zero length in the same instant.

Without the transfer list the same call copies every byte. For 64 MB that is tens of milliseconds and twice the memory. With it, the time does not depend on the size.

Because the sender is left with nothing, there is no shared state and nothing to lock. It is the simplest safe way to give a large block of data to another thread or another origin.

Step by step

What each press of Next does in the demo at the top.

  1. Open a channel. This page opens a channel to the frame on another origin.
  2. Transfer 64 MB. 64 MB moves to the other origin and back without copying. While it is away, this page holds zero bytes.
  3. Copy 64 MB. The same 64 MB is cloned instead of moved, so you can compare the round-trip time.

Reuse two buffers between a page and a worker without copying

The idea: Passing decoded images, audio or model weights to a worker. A pool of buffers that travels back and forth between two contexts.

What you are looking at

A worker needs somewhere to put each result, and making a fresh 8 MB buffer every time is wasteful. This page makes two, once. One goes to the worker, which fills it and sends it back, while the other is being read here. Then they swap. The counters show megabytes moved climbing and megabytes copied staying at zero.

The code

const pool = [new ArrayBuffer(SIZE), new ArrayBuffer(SIZE)];
worker.onmessage = ({ data }) => {
  use(data.buffer);                            // read the result
  worker.postMessage({ buffer: data.buffer }, [data.buffer]);   // and send the same memory back
};
for (const buffer of pool) worker.postMessage({ buffer }, [buffer]);

Step by step

What each press of Next does in this demo.

  1. Start the pool. Two buffers are made once, and then only moved.
  2. Stop. The pool stops. Two buffers were ever made.

A sandboxed calculation that hands back 16 MB without copying it

The idea: Returning large results from a sandboxed computation.

What you are looking at

The frame is sandboxed and on another origin, which is where you want code you did not write. It marks every prime below 16.7 million in a 16 MB buffer. Posting that back the ordinary way makes a second 16 MB and takes time that grows with the size. Posting it with the buffer in the transfer list moves the memory itself. The frame measures how long each call took, and how much it has left afterwards.

The code

// in the sandbox
const sieve = findPrimes(16 * 1024 * 1024);                // a 16 MB Uint8Array
port.postMessage({ sieve }, [sieve.buffer]);               // moved
sieve.byteLength;                                          // 0: it is the page's now

Step by step

What each press of Next does in this demo.

  1. Sandbox: work it out and send a copy. The frame computes, then posts the result the ordinary way. It keeps its 16 MB, and the page gets another.
  2. Sandbox: work it out and move it. The same work, and this time the buffer is in the transfer list.

Things to try

  • Transfer 64 MB and read the time. Then copy 64 MB and compare.
  • Watch the byte count held by this page drop to zero while the buffer is away.

Common mistakes

  • Forgetting the transfer list silently copies. Nothing warns you.
  • After the transfer, typed arrays on the old buffer have length zero. Code that still holds one reads nothing.
  • A SharedArrayBuffer is a different thing: both sides keep it, and it needs a cross-origin isolated page.

Measured

Chromium 157: 64 MB to a sandboxed frame and back in a few milliseconds by transfer. Other browsers are being filled in from the lab's results.

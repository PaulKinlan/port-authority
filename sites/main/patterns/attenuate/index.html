Port patterns / The six basic patterns

Give a frame limited access, then revoke it

What you are looking at

Holding a port is the permission to use it. The owner here doesn't hand out its real port. It makes a new channel, keeps one end, and only answers read on it. To revoke, it closes its end. It needs no account, token or list of who is allowed. The two boxes are frames in this page and have no line to each other at the start, so the owner hands the new port to this page, which passes it to the guest.

The code

function readOnly(counter) {
  const { port1, port2 } = new MessageChannel();
  port1.onmessage = (e) => port1.postMessage(e.data === "read" ? counter.value : "denied");
  return { port: port2, revoke: () => port1.close() };
}

Using it

// a document editor, and a word-count plug-in from another company in a frame
const grant = readOnly(counter);
plugin.contentWindow.postMessage({ counter: grant.port }, pluginOrigin, [grant.port]);

// the plug-in can read for as long as the editor lets it
port.postMessage("read");
port.onmessage = (e) => show(e.data);

// the person turns the plug-in off, or signs out
offButton.onclick = () => grant.revoke();

// The plug-in still holds its port, and nothing answers it now.
// It is told nothing, so it needs a timeout of its own to notice.

Where you would use it

A real case. A document editor lets a plug-in from another company read the document, to count words. The editor gives the plug-in a read-only port when the person turns the plug-in on. When the person turns it off, signs out, or opens a document marked private, the editor calls revoke(). The editor does not have to find the plug-in or trust it to stop. Each plug-in has a port of its own, so turning one off leaves the others working.

How it works

The owner holds something powerful, here a counter it can read and change. It wants to let a guest read it and nothing else. So it makes a new channel, keeps one end, and listens on that end for read only. The other end goes to the guest.

The limit is enforced in the owner's handler, on the owner's side of the port. The guest can post any message it likes and the handler ignores it.

Because the owner kept its end, it can close it. After that the guest still holds a port, but nothing answers it. You don't need a list of who was given what, because each grant is its own channel and closing it ends only that grant.

Step by step

What each press of Next does in the demo at the top.

  1. Share read-only. The owner makes a channel, keeps one end that only answers read, and hands the other end to the guest.
  2. Guest reads. The guest asks to read the counter through its port and gets 41.
  3. Guest tries to add. The guest asks to change the counter and is denied. Its port does not allow that.
  4. Owner adds one. The owner increments its own counter to 42.
  5. Revoke. The owner closes its end of the guest's channel, cutting the cable.
  6. Guest reads. The guest asks again and hears nothing. Its port goes nowhere now.

Access that runs out after eight seconds

The idea: Time-limited or use-limited access: count calls in the handler and close the port at the limit.

What you are looking at

The owner lends the guest a port to its diary, and starts a clock. While the clock runs, the guest's questions are answered. When it stops, the owner closes its end. The guest still holds a port. Nothing comes back from it. There was no token to expire and no session to clean up.

The code

const { port1, port2 } = new MessageChannel();
port1.onmessage = () => port1.postMessage(diary.today());
guest.postMessage({ cmd: "port" }, "*", [port2]);
setTimeout(() => port1.close(), 8000);      // that is the whole expiry

Step by step

What each press of Next does in this demo.

  1. Lend the diary for 8 seconds. The guest is given a port. The owner will close its end in eight seconds.
  2. Guest: ask what is on today. Inside the time, the guest gets an answer.
  3. Guest: ask what is on today. Time is up. The guest asks again and hears nothing.

Pass access on to a third party, with less than you were given

The idea: Delegation chains. A guest can attenuate again before passing its port on, and can only ever give away less.

What you are looking at

The owner lets an assistant read the diary and add to it. The assistant passes part of that on to an intern: reading only. The intern's port ends at the assistant, and the assistant's ends at the owner. Nobody in the chain can hand on more than they hold. When the owner cuts off the assistant, the intern is cut off too, without the owner knowing the intern exists.

The code

// the assistant, passing on less than it was given
const { port1, port2 } = new MessageChannel();
port1.onmessage = ({ data }) => {
  if (data.do !== "read") return port1.postMessage({ refused: "read only" });
  ownerPort.postMessage(data);            // forwarded up the chain
};
give(intern, port2);

Step by step

What each press of Next does in this demo.

  1. Give the assistant read and add. The assistant gets a port that reads and adds.
  2. Assistant: pass on read only. The assistant makes a weaker port and gives it to the intern.
  3. Intern: read. The intern's question goes to the assistant, then to the owner, and the answer comes back down.
  4. Intern: try to add. The assistant refuses. It never reaches the owner.
  5. Owner: cut off the assistant. The owner closes the assistant's port.
  6. Intern: read. The intern asks again. The chain is broken above it, and nothing comes back.

An embed that is shown two fields of your app's state, and no others

The idea: Third-party embeds that get a narrow view of your app's state.

What you are looking at

This page's state has a name, an email address, a theme and a basket. A reviews embed from another origin needs to match the theme and show how many things are in the basket. It is given a port that carries those two fields, each time they change. A change to the email address sends nothing, and asking for it is refused.

The code

const view = ({ theme, basket }) => ({ theme, basket });     // the whole of what the embed may know
const { port1, port2 } = new MessageChannel();
onStateChange((state, changed) => {
  if (changed in view(state)) port1.postMessage(view(state));
});
embed.postMessage({ cmd: "port" }, "*", [port2]);

Step by step

What each press of Next does in this demo.

  1. Give the embed a narrow view. The embed gets a port, and the two fields it may see.
  2. Switch the theme. The theme is in the view, so the embed hears of it.
  3. Add to the basket. So is the basket.
  4. Change the email address. The email address is not in the view. Nothing is sent.
  5. Embed: ask for the email address. The embed asks anyway, and is refused.

Things to try

  • Share read-only, read, then try to add from the guest. Then revoke and read again.
  • Share twice. The first guest port still works after the second is made: each grant is separate.

Common mistakes

  • Attenuation only holds if the guest never also gets the powerful port. Check what else you post to it.
  • Closing your end does not notify the guest — the HTML standard removed the port close event in October 2026 and no browser ships it on by default. Their calls go quiet, with no error.

Port patterns / More things a port can carry

Keep a port across a page reload

What you are looking at

A port cannot be saved. IndexedDB, sessionStorage and history state all refuse it, because a port can be moved but never copied. But you can leave it with a SharedWorker. As this frame unloads it posts its port to the worker, and when it loads again it asks for it back. The worker is created with extendedLifetime, so it outlives the page even when that page was its only client. The feed doesn't notice. Ticks sent during the reload waited in the port, and the count has no gaps. The dark cable is the frame's own connection to the worker. The other one is the port that is kept, which this page made and gave to the feed and the frame.

The code

const bank = new SharedWorker("/bank.js", { extendedLifetime: true });
addEventListener("pagehide", () => bank.port.postMessage({ deposit: key }, [port]));

// next load
bank.port.postMessage({ withdraw: key });
bank.port.onmessage = ({ data, ports }) => data.found ? resume(ports[0]) : connectAgain();

Using it

// a notes app that the person has connected to their calendar, open in another tab
// /bank.js: hold a port under a key until a page asks for it
const kept = new Map();
onconnect = ({ ports: [client] }) => {
  client.onmessage = ({ data, ports }) => {
    if (data.deposit) return kept.set(data.deposit, ports[0]);
    const port = kept.get(data.withdraw);
    kept.delete(data.withdraw);
    client.postMessage({ found: !!port }, port ? [port] : []);
  };
};

// the notes app: a key that this tab keeps across a reload
const key = sessionStorage.portKey || (sessionStorage.portKey = crypto.randomUUID());

// on load: take the port back, or ask the person to connect again if the bank has nothing
const resume = (port) => { port.onmessage = (e) => showEvent(e.data); };
bank.port.onmessage = ({ data, ports }) => data.found ? resume(ports[0]) : connectAgain();

// What the calendar sent during the reload waited in the port, and arrives now in order.
// The bank is empty on a first visit, and after a crash, when pagehide did not run.
// A deposit can arrive after the withdraw, so a real bank waits a moment before it says no.

Where you would use it

A real case. A notes app is connected to a calendar that is open in another tab. The person made that connection by hand, through a chooser, and the port is all the notes app has of it. When the person presses reload, the page deposits the port as it goes and the new page withdraws it, so the person is not asked to connect a second time. If the bank comes back empty, as it does after a crash or where the worker did not live through the reload, the app asks the person to connect again.

How it works

A port dies with the page that holds it, and it cannot be saved: IndexedDB, session storage and history state all refuse it. But it can be transferred, and a SharedWorker outlives a reload.

In pagehide the page posts its port to a SharedWorker, which holds it. The new page connects to the same worker and asks for the port back. Messages sent in between wait in the port's queue.

The far side doesn't notice. It sees a short pause and then the messages carry on.

Step by step

What each press of Next does in the demo at the top.

  1. Connect the feed to the frame. A channel is opened between the feed on another origin and the frame, and ticks begin arriving.
  2. Reload the frame. The frame deposits its port in the SharedWorker bank on pagehide, reloads, and withdraws it with zero gaps.

Replace a running widget with its next version, and keep its connection

The idea: Handing a live port from an old version of a page to a new one.

What you are looking at

Version 1 of a chat widget is holding a port to a service that sends it numbered messages. Version 2 is ready. Loading it the usual way would mean dropping the connection and making another, and losing whatever arrived in between. Here version 1 stops listening, hands its port to version 2, and is removed. Messages that arrive during the swap wait in the port. The service is never told that anything changed.

The code

// version 1, when asked to step aside
port.onmessage = null;                                       // stop reading: what arrives now will wait
parent.postMessage({ handover: true, last }, "*", [port]);

// version 2
port.onmessage = ({ data }) => { /* carries on from last + 1 */ };

Step by step

What each press of Next does in this demo.

  1. Connect version 1 to the service. The service starts sending numbered messages down a port.
  2. Load version 2 and hand over. Version 1 gives up its port and is removed. Version 2 picks up at the next message.

A connection granted once, kept across every page of a site

The idea: Keeping a granted connection through a navigation in a multi-page site.

What you are looking at

The box on the right is a small site with three pages, and each link is a real navigation that throws the old page away. On the first page it was granted a port to an order feed on another origin. On the way out of each page it leaves that port with a shared worker, and on the way in it collects it. The feed keeps sending throughout. Updates sent while no page existed wait in the port, so none are missed.

The code

// on every page of the site
const bank = new SharedWorker("/bank.js", { extendedLifetime: true });
bank.port.postMessage({ withdraw: "orders" });                 // is one waiting for me?
bank.port.onmessage = ({ ports }) => ports[0] ? resume(ports[0]) : askToBeGranted();
addEventListener("pagehide", () => bank.port.postMessage({ deposit: "orders" }, [port]));

Step by step

What each press of Next does in this demo.

  1. Go to the next page. A real navigation, from Shop to Basket. The new page collects the port.
  2. Go to the next page. And again, to Account. The count has no gaps.

Already running

  • Single-page apps that must survive a hard refresh without re-asking the person for permission. See the demo at the top of this page.

Things to try

  • Try to store a port in IndexedDB and read the refusal.
  • Reload the frame and check the count: no gaps and no repeats.
  • Reload several times in a row.

Common mistakes

  • The worker must be created with extendedLifetime: true or it dies with its last page, taking the port with it.
  • pagehide does not run on a crash or a killed tab. The port is lost then.
  • On a different site the worker is partitioned. This is for one origin's own pages.

Measured

Chromium 157: the count from the feed shows no gap across a reload of the receiving frame. Other browsers are being filled in from the lab's results.

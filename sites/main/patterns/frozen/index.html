Port patterns / Across threads

Two workers that keep talking while this page is frozen

What you are looking at

A port given to a worker belongs to that worker's thread. Introduce two workers to each other and their messages never touch the page again. Freeze this page for three seconds: its own counter stops, the buttons go dead, and the two workers carry on. You can watch them do it, because each one paints its numbers into a canvas whose drawing surface it was handed, and a transferred canvas does not wait for the page either.

The code

const { port1, port2 } = new MessageChannel();
workerA.postMessage({}, [port1]);
workerB.postMessage({}, [port2]);
// this page is now out of the conversation, and can stall without harm
while (performance.now() < until) {}

Using it

// a live prices page: workerA parses what a socket sends, workerB draws the chart
const workerA = new Worker("/parse.js"), workerB = new Worker("/draw.js");
const surface = chart.transferControlToOffscreen();
workerB.postMessage({ surface }, [surface]);       // then the channel: port1 to workerA, port2 to workerB

// /parse.js, workerA: port1 arrives here. Parsed prices go straight to the other worker
const socket = new WebSocket("wss://prices.example/live");
onmessage = ({ ports: [toDraw] }) => { socket.onmessage = (e) => toDraw.postMessage(parse(e.data)); };

// /draw.js, workerB: the canvas arrives first, then port2
let ctx = null;
onmessage = ({ data, ports: [fromParse] }) => {
  if (data.surface) ctx = data.surface.getContext("2d");
  if (fromParse) fromParse.onmessage = (e) => draw(ctx, e.data);
};

// the page: the person sorts a table of 50,000 rows, and the main thread is busy
rows.sort(byPrice);
// The table does not respond until the sort ends. The chart keeps moving all the while.

Where you would use it

A real case. A prices page has a long table and a live chart. One worker holds the socket and parses what arrives, and a second worker draws the chart on a canvas the page handed it. The page introduces the two workers once and keeps no port. When the person sorts the table, the page's thread is busy and the page does not respond, but parsed prices still go from one worker to the other and the chart still moves. If the prices went through the page, the chart would stop for as long as the sort took.

How it works

Each worker has its own thread and its own event loop. A port given to a worker is serviced by that worker's thread. So two workers that hold the two ends of a channel exchange messages without the page's thread being involved at all.

The demo shows this by blocking the page in a tight loop for three seconds. The page's own counter stops and its buttons do nothing. The two workers keep counting.

You can see them count because each paints into a canvas whose surface it was handed. A transferred canvas is presented by the worker, not the page.

A decoder worker feeding a renderer worker, while the page is busy

The idea: A decoder worker feeding a renderer worker. Keeping a pipeline smooth while the page does layout or garbage collection.

What you are looking at

One worker makes video frames. Another paints them into a canvas it was handed. This page introduces the two with a channel and steps away, so frames go from one worker straight to the other and never touch the page's thread. Freeze the page for three seconds, as a long layout or a garbage collection would, and the picture keeps moving.

The code

const { port1, port2 } = new MessageChannel();
decoder.postMessage({ out: port1 }, [port1]);
renderer.postMessage({ in: port2, surface }, [port2, surface]);

// the decoder: each frame's memory is moved to the renderer
out.postMessage({ pixels }, [pixels.buffer]);

Step by step

What each press of Next does in this demo.

  1. Connect the decoder to the renderer. Each worker gets one end of a channel. Frames start to flow between them.
  2. Freeze this page for 3 seconds. The page's counter stops. The picture does not.

Already running

  • Any worker pool where workers hand work to each other. See a decoder worker handing frames to a renderer worker.

Things to try

  • Introduce the workers, then freeze the page. Watch the page's tick count against the workers' message count.
  • Freeze before introducing: nothing moves anywhere, because nobody has a channel yet.

Common mistakes

  • A worker created from the page still needs the page to exist. It survives a freeze, but not the page closing.
  • Workers talking directly are harder to observe. Have them report counts, as these do.

Measured

Chromium 157: during a 3 second main-thread freeze the page ticked 0 times and the workers went on exchanging a message every 100 ms. Other browsers are being filled in from the lab's results.

Port patterns / Knowing the other side is still there

Restart a worker that has stopped answering, and ask again

What you are looking at

A worker counts prime numbers for this page. It is given a port for the work and a port to answer health pings on. If it stops answering, because it is stuck in a loop or has closed itself, the page waits for three missed pings, terminates it, starts a new one and sends it every question that was not answered. Nothing about health is in the work protocol, so the restart is invisible to the code that asked: it gets its answer, later than usual.

The code

function start() {
  const worker = new Worker("/patterns/alive-worker.js", { type: "module" });
  const work = new MessageChannel(), health = new MessageChannel();
  worker.postMessage({ ports: true }, [work.port2, health.port2]);
  current = work.port1;                            // questions go to the newest worker
  work.port1.onmessage = ({ data }) => { pending.get(data.id).resolve(data.count); pending.delete(data.id); };
  watch(health.port1, { every: 500, misses: 3, onState(state) {
    if (state !== "silent") return;
    worker.terminate();
    start();                                       // a new worker
    for (const [id, ask] of pending) current.postMessage({ id, n: ask.n }); // ask again
  } });
}

Using it

// a document scanner. A text-recognition library in a worker counts the words on page n.
const pending = new Map();           // every question that has no answer yet
let current, next = 0;               // current: work.port1 of the newest worker
start();

// the rest of the app calls this and nothing else
const wordsOnPage = (n) => new Promise((resolve) => {
  const id = ++next;
  pending.set(id, { n, resolve });   // kept until answered, so that start() can ask again
  current.postMessage({ id, n });
});

// page 12 is asked for and the worker hangs. Three pings are missed, and start() runs again.
wordCount.textContent = await wordsOnPage(12);   // this line waited longer, and saw nothing else

// the worker: pings on one port, work on the other. answer() is from /alive.js.
onmessage = ({ ports: [work, health] }) => {
  answer(health);
  work.onmessage = ({ data: { id, n } }) => work.postMessage({ id, count: countWords(n) });
};

Where you would use it

A real case. A document scanner app counts the words on each scanned page with a text-recognition library that runs in a worker. The library is not the app's own code, and now and then it stops answering part way through a page. The app keeps every unanswered question in pending, and the worker answers health pings on a second port. After three missed pings the app terminates the worker, starts another and asks again, so the code that called wordsOnPage(12) gets its number after a longer wait. Counting the words on a page twice does no harm, which is what makes asking again safe.

How it works

A page that depends on a worker keeps a list of questions it has asked and not had answered. The worker answers health pings on a second port. When three pings go unanswered, the page terminates the worker, starts a new one and sends it every question on the list.

terminate() works on a worker that is stuck in a loop, so the page can always get rid of it. A worker that called close() on itself, or crashed, gives no sign at all, and is caught the same way.

The code that asked only sees an answer that took longer. It never learns there was a second worker, because health checks are on their own port and the work protocol knows nothing about them.

Asking again is only safe for questions that can be asked twice. Counting primes can. Charging a card cannot. For work like that, give each question an id the far side remembers, so that a repeat is recognised and not done twice.

Step by step

What each press of Next does in the demo at the top.

  1. Start the worker. This page starts a worker and sends it two ports: one for prime calculations and one for health pings.
  2. Ask: primes below 5 million. The question goes on the work port and the answer comes back on it.
  3. Make the worker hang. The worker is sent into a loop that never ends. It cannot answer pings or work.
  4. Ask: primes below 5 million. This question waits. After three missed pings the page terminates the worker, starts a new one, and asks it again.
  5. Make the worker close itself. The worker calls close(). Nothing is said to this page. The pings go unanswered and it is replaced.

What you could build with it

Already running

  • A pool of workers that replaces any worker that stops answering, without the callers noticing. See the demo at the top of this page.

Things to try

  • Make the worker hang, then ask. The question waits about two seconds and is answered by worker number 2.
  • Make it close itself. Nothing is said, and it is replaced as soon as three pings go unanswered.

Common mistakes

  • Only resend work that is safe to do twice, or that the far side can recognise as a repeat.
  • A worker that is slow, not stuck, will be killed too if its pings wait behind long work. Answer pings between chunks of work, or run work in a second worker.
  • Give up after a few restarts in a row. A worker that fails at startup would otherwise be restarted for ever.

Measured

Chromium 153: a worker stuck in an endless loop was terminated and replaced 1.5 to 2 seconds after it stopped answering pings sent every 0.5 s, and the replacement answered the waiting question. Other browsers are being filled in from the lab's results.

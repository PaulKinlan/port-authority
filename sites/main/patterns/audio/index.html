A worker that plays music while this page is frozen

What you are looking at

Sound is made on a thread of its own, and that thread accepts a port. This page starts an audio processor and a worker, gives each one end of a channel, and steps away. The worker writes the tune and sends each note straight to the audio thread, which plays it and says so. Freeze this page for three seconds: the buttons stop working and its counter stops, but the music keeps time because none of it passes through here. The audio thread has no DOM, no timers and no network. A port is the only way to reach it, and anything that holds the other end can.

The code

const node = new AudioWorkletNode(audio, "bell");
const { port1, port2 } = new MessageChannel();
composerWorker.postMessage({}, [port1]);
node.port.postMessage({}, [port2]);        // the audio thread now holds a port

// the worker, every beat. The page is not involved.
port.postMessage({ freq: 440 });

Using it

// a step sequencer. The page loaded bell.js with audio.audioWorklet.addModule("/bell.js").
// It runs on the audio thread and takes the port that came through node.port.
class Bell extends AudioWorkletProcessor {
  constructor() {
    super();
    this.port.onmessage = ({ ports: [notes] }) => {
      notes.onmessage = ({ data }) => { this.freq = data.freq; notes.postMessage({ played: true }); };
    };
  }
  process(inputs, outputs) { /* write a tone at this.freq into outputs[0] */ return true; }
}
registerProcessor("bell", Bell);

// the composer worker takes the other port and sends one note for each step of the pattern
onmessage = ({ ports: [port] }) => {
  port.onmessage = () => { played++; };          // the audio thread says it played the note
  setInterval(() => port.postMessage({ freq: pattern[step++ % pattern.length] }), 125);
};

// the page holds no port. It wires the node to the speakers, and stops by ending both sides.
node.connect(audio.destination);
stopButton.onclick = () => { composerWorker.terminate(); audio.close(); };

Where you would use it

A real case. A step sequencer runs in a browser tab. The page draws the grid of notes, a worker holds the pattern and sends each note, and an AudioWorkletProcessor makes the sound. When the person presses Play, the page makes one channel and gives one port to the worker and the other to the processor. Later the page is busy for a second, because the person opens a long list of saved patterns. The worker still sends each note and the audio thread still plays it, because the page's only part was to hand out the two ports.

How it works

An AudioWorkletProcessor runs on the audio rendering thread. It has no DOM, no timers and no network. It does have a MessagePort to its node, and it accepts further ports posted through that.

The page makes a channel and gives one end to a worker and the other to the processor. The worker sends a note every 230 ms. The processor plays it and reports back on the same port.

The page is not in that path, so freezing it changes nothing you can hear. The worker even shows its own state, by painting into a canvas it was handed.

A decoder worker that hands sound straight to the speakers

The idea: A decoder worker feeding samples straight to output.

What you are looking at

A worker produces sound a tenth of a second at a time, as a decoder would, and moves each block of samples down a port to the audio thread. The audio thread plays them and reports how far it has got, and the worker uses that to stay about half a second ahead. This page introduced the two and holds nothing. Freeze it for three seconds and the sound carries on without a gap, because no sample ever passes through here.

The code

// the worker: stay half a second ahead of what has been played
port.onmessage = ({ data }) => {
  while (sent - data.played < sampleRate / 2) {
    const block = decodeNext();                       // a Float32Array
    port.postMessage({ block }, [block.buffer]);      // moved to the audio thread
    sent += block.length;
  }
};

Step by step

What each press of Next does in this demo.

  1. Start the decoder. The worker and the audio thread are introduced. Blocks of sound start to flow between them.
  2. Freeze this page for 3 seconds. The page stops. The worker keeps decoding and the audio thread keeps playing.
  3. Stop the sound. The audio is closed.

A level meter drawn by a worker, fed from the audio thread

The idea: Meters and analysers that report from the audio thread to a worker.

What you are looking at

A tone swells and fades. A processor on the audio thread measures how loud it is, twenty times a second, and posts each reading down a port. The other end is held by a worker, which draws the meter into a canvas it was handed. The readings go from the audio thread to the worker to the screen. Freeze this page and the meter keeps moving, in time with what you hear.

The code

// on the audio thread
process([input]) {
  const level = Math.sqrt(input[0].reduce((sum, s) => sum + s * s, 0) / input[0].length);
  meterPort.postMessage({ level });        // the other end is in a worker
  return true;
}

Step by step

What each press of Next does in this demo.

  1. Start the tone and the meter. The audio thread and the meter's worker are given one end each of a channel.
  2. Freeze this page for 3 seconds. The page stops. The meter does not.
  3. Stop the sound. The audio is closed.

Things to try

  • Start the music, then freeze the page and listen.
  • Read the note count after the freeze: about thirteen in three seconds, none lost.

Common mistakes

  • Browsers only start sound after a real press.
  • The audio thread must never wait. Keep its handler tiny.
  • Measured in Chromium 157: the audio thread accepts ports, buffers and streams, and little else.

Measured

Chromium 157: 13 notes played during a 3 second main-thread freeze. Other browsers are being filled in from the lab's results.

Port patterns / Knowing the other side is still there

Which signal notices which ending, and how quickly

What you are looking at

Every way of knowing the far side has gone, side by side, measured in your browser. For each row a fresh far side is made on this site's own origin and given every signal at once: a port that only carries its goodbye, a port it answers pings on every half second, a port it beats on every half second, and a Web Lock it holds. Then it is ended in one way, and the table shows how long each signal took to say so. The last column is the port close event. It was added to the HTML standard in 2024, never switched on in any browser, and taken out again in October 2026.

The code

// the far side holds a lock with a name only it uses, and tells the page the name
const name = "alive-" + crypto.randomUUID();
navigator.locks.request(name, () => new Promise(() => {}));  // never let go

// this page queues for the same lock. It is granted when the holder is destroyed.
await navigator.locks.request(name, () => {});
farSideIsGone();

Using it

// a document editor open in several tabs, and one SharedWorker that keeps the list of tabs
// a tab: take the lock, and send its name to the worker once the lock is held
const { port } = new SharedWorker("/editor-worker.js");
const name = "alive-" + crypto.randomUUID();
navigator.locks.request(name, () => {
  port.postMessage({ name });
  return new Promise(() => {});              // never let go
});

// the worker: queue for each tab's lock. It is granted when that tab is destroyed.
onconnect = ({ ports: [port] }) => port.onmessage = async ({ data: { name } }) => {
  tabs.add(port);
  await navigator.locks.request(name, () => {});
  farSideIsGone(port, name);
};

// the tab closed, crashed or went to another page. Nothing came on its port to say so.
function farSideIsGone(port, name) {
  tabs.delete(port); port.close();
  for (const tab of tabs) tab.postMessage({ left: name });   // the others remove its cursor
}

Where you would use it

A real case. A document editor is open in several tabs of one browser, and one SharedWorker keeps the list of tabs so that each tab can show the others' cursors. Each tab holds a Web Lock with a name of its own and sends that name to the worker on its port. The worker shares the tabs' origin, so it can queue for the same lock, and the browser grants it when the tab is closed, navigated away or crashed. Then the worker closes that tab's port and tells the other tabs to remove its cursor. A tab that is hung still holds its lock, so a worker that must notice a hang needs pings or beats as well.

How it works

There are four signals a page can use today, and each one notices a different set of endings.

The goodbye. A page that is closing, navigating or being removed from its parent fires pagehide, and can post on a port from there. It is the quickest signal, a few milliseconds. It is never sent by a worker, by a process that crashes, or by a page that just calls close().

Pings and beats. They notice everything, including a stuck thread and a crash, and they are the only signal that works across origins for anything other than a page. Their cost is time: the far side is only called gone after several missed intervals. A stuck far side looks the same as a dead one until it recovers.

A Web Lock. The far side requests a lock with a name only it uses and never releases it. The page queues for the same name. The browser grants the page's request the moment the holder is destroyed: frame removed, page navigated, worker terminated, process crashed. It does not fire for a stuck thread, which still holds its lock, or for close() on a port. Locks belong to one origin, and in a frame on another site, to one storage partition, so this only works between contexts that share both.

The port close event. It would have been the quickest of all. It is no longer in the HTML standard and no browser turns it on. The column stays so that a browser that does have it shows its numbers.

Only on this page, the far side for the busy row is a worker. A frame on the same site as the page usually shares its thread, so a busy frame stops the page too, and the page cannot time anything while it waits.

What you could build with it

Already running

  • Choosing the signal for each far side: a goodbye and a lock for pages and workers on your own origin, pings or beats for everything else. See the demo at the top of this page.

Things to try

  • Run every row and compare the goodbye and lock columns with the pings and beats columns.
  • In Chrome, start it with --enable-blink-features=MessagePortCloseEvent and run the table again. The last column fills in.
  • Run it on a phone too, where the timings are different.

Common mistakes

  • A Web Lock used as a liveness signal must have a name nobody else will use. Make it from crypto.randomUUID().
  • A held Web Lock can stop a page entering the back/forward cache in some browsers, and the page's code cannot release it while frozen. Release it in pagehide if you hold one in a page.
  • A lock on another origin has the same name and is a different lock. The page gets it at once and would conclude, wrongly, that the far side is gone.

Measured

Chromium 153, frames on this origin: removing the frame was seen by the goodbye in 3 to 4 ms and by the lock in 4 to 5 ms. Navigating it away, 16 to 31 ms for both. close() was seen only by pings (1.8 s) and beats (1.5 s). A terminated worker's lock was free in 1 ms. A worker busy for 4 seconds was marked silent by pings and beats and alive again afterwards, and kept its lock. With the MessagePortCloseEvent flag on, the close event fired 0 to 1 ms after close(), 2 to 4 ms after removal, 20 to 24 ms after navigation and 1 ms after a worker was terminated, and not for a busy worker. Between two origins, a page was granted the far side's lock name immediately while the far side still held it. Other browsers are being filled in from the lab's results.

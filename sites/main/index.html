What you can do with a MessagePort

Hello, I'm Paul Kinlan. I've been working on the web for a long time, and I think message channels and message ports are massively underserved. Most people don't know what they can do.

You can hand a MessagePort to another window, another origin or a worker, and they can pass it on again. Whoever holds it can talk to the other end, and nothing in between has to stay open.

I made this site while exploring where the web meets AI. It explains how ports work, with demos you can run and code you can copy. I also write about the web at paul.kinlan.me and about the web and AI at aifoc.us.

Experiments

Everything here runs in your browser, across separate origins. The first four use the hub.

  1. Web Intents, with a port at the end

    Working

    A site says what it needs in plain words and you choose which site answers. The picker opens that site, gives each side one end of a channel and closes. The call then runs on your machine, even with the network off. The same tools are offered to WebMCP.

    // a site with something to offer
serve({ name: "Stem and Petal", tools: [{ name: "book_delivery", description, inputSchema, execute }] });

// a site that needs something, and has never heard of the florist
const line = await pick("send flowers to a friend");
await line.call({ bouquet: "ember", recipient: "Ada" });

    Working

    Sites send their tools to your hub (a small server that is yours) each time they load, so the picker can list them without any tab being open. A site you trust can ask for the whole registry and gets a Model Context Protocol connection over one port.

  3. Your agent, on any website

    Working, tested with a stand-in agent

    A site asks for an agent and gets a port that speaks the Agent Client Protocol. You choose the agent by running the bridge next to Claude Code, Gemini CLI or anything else that speaks ACP. The agent gets the registry too, so it can use tools in your open tabs. If you set nothing up you get a built-in agent that has no model and only matches words.

What I've learned so far

  • A hidden hub iframe doesn't work any more. Browsers partition a SharedWorker in a cross-site iframe by the top-level site, so each site would get its own empty hub. The hub has to be a window of its own, which is the old Web Intents picker, and that gives you somewhere to say yes.
  • A port handed over through that window keeps working after the window closes, and with the network off. The hub is only needed for the introduction.
  • A port only lives while both pages do. So the list of who offers what is kept on a server, and the picker opens the tool's page when you choose it.
  • A site keeps its link to your hub in its own storage, which partitioning doesn't touch. The server only accepts it from that site's origin.
  • An agent on a website needs something in the middle. The hub rewrites the session so a site can't pick the agent's folder, give it servers or see another site's session.
  • A stream relayed through an introducer stalls silently when the introducer goes away. A port doesn't. Introduce with a port, then send the stream down it.
  • A port can survive its page reloading. Post it to a SharedWorker made with extendedLifetime as the page unloads and collect it on the next load.
  • Two unrelated tabs can't pass a port. When you pick a tool whose site is already open in a tab, your hub server introduces the two tabs and they open a WebRTC channel. That channel carries JSON only, so no ports or streams.

What you can do with a MessagePort

Hello, I'm Paul Kinlan. I've been working on the web for a long time, and I think message channels and message ports are massively underserved. Most people don't know what they can do.

You can hand a MessagePort to another window, another origin or a worker, and they can pass it on again. Whoever holds it can talk to the other end, and nothing in between has to stay open.

I made this site while exploring where the web meets AI. It explains how ports work, with demos you can run and code you can copy. I also write about the web and AI at aifoc.us.

  9. Web Intents, with a port at the end

    A site says what it needs in plain words and you choose which site answers. The picker opens that site, gives each side one end of a channel and closes. The call then runs on your machine, even with the network off. The same tools are offered to WebMCP (Web Model Context Protocol).

    // a site with something to offer
serve({ name: "Stem and Petal", tools: [{ name: "book_delivery", description, inputSchema, execute }] });

// a site that needs something, and has never heard of the florist
const line = await pick("send flowers to a friend");
await line.call({ bouquet: "ember", recipient: "Ada" });

What I've learned so far

  • A hidden hub iframe doesn't work any more. Browsers partition a SharedWorker in a cross-site iframe by the top-level site, so each site would get its own empty hub. The hub has to be a window of its own, which is the old Web Intents picker, and that gives you somewhere to say yes.
  • The hub is only needed for the introduction. A port handed over through that window keeps working after the window closes, and with the network off.
  • Keep the directory on a server. A port only lives while both pages do, so the list of who offers what is kept on a server, and the picker opens the tool's page when you choose it.
  • Tokens stay in each site's own storage. A site keeps its link to your hub in its own storage, which partitioning doesn't touch. The server only accepts it from that site's origin.
  • An agent on a website needs a gatekeeper in the middle. The hub rewrites the session so a site can't pick the agent's folder, give it servers or see another site's session.
  • Introduce with a port before sending a stream. A stream relayed through an introducer stalls silently when the introducer goes away. A port doesn't.
  • A port can survive its page reloading. Post it to a SharedWorker made with extendedLifetime as the page unloads and collect it on the next load.
  • Unrelated tabs need a WebRTC bridge. Two unrelated tabs can't pass a port directly. When you pick a tool whose site is already open in a tab, your hub server introduces the two tabs and they open a WebRTC channel, which carries JSON only (no ports or streams).

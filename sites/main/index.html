Pass the port.

A MessagePort can be handed to another window, another origin, a worker, and on again. Whoever holds it can talk, and nobody in between has to stay. These are experiments in how far that goes.

Three real origins. Site A and Site B have never met. Press Introduce them, let them talk, then remove the one in the middle.

Experiments

Each one runs here, across separate origins, in your browser. Start with the hub: the other three sit on top of it.

  1. Web Intents, with a port at the end

    Working

    A site says what it needs in plain words. You choose which site answers. The picker opens that site, hands each side one end of a channel, and closes. The call runs on your machine over that port, and it keeps working with the network unplugged. Sites declare tools once and they are offered to WebMCP as well.

    Open the plannerthe floristthe library

    // a site with something to offer
serve({ name: "Stem and Petal", tools: [{ name: "book_delivery", description, inputSchema, execute }] });

// a site that needs something, and has never heard of the florist
const line = await pick("send flowers to a friend");
await line.call({ bouquet: "ember", recipient: "Ada" });

  2. One registry of every site's tools

    Working

    Sites submit their tools to your hub, a small server that is yours, every time they load. So the picker can list everything you have ever added with nothing open, and you never keep a tab around for it. A site you trust can ask for the whole registry and gets a Model Context Protocol connection over a single port.

    Open your hub

  3. Your agent, on any website

    Working, tested with a stand-in agent

    A site asks for an agent and receives a port that speaks the Agent Client Protocol. Which agent is yours to decide. Run the bridge beside Claude Code, Gemini CLI or anything else that speaks ACP, and it connects out to your hub. The agent is handed the registry too, so it can use tools in your open tabs. With nothing set up you get a built-in agent that has no model and only matches words.

What we know so far

  • A hidden hub iframe does not work any more. Browsers partition a SharedWorker in a cross-site iframe by the top-level site, so each site would get its own empty hub. The hub has to be a window of its own, which turns out to be the old Web Intents picker, and gives you somewhere to say yes.
  • A port handed over through that window keeps working after the window closes, and with the network off. The introduction is the only moment the hub is needed.
  • Nothing has to stay open. A port only lives while both pages do, so the list of who offers what lives on a server, and the picker opens the tool's page when you choose it.
  • A site keeps its link to your hub in its own storage, which partitioning does not touch, and the server only accepts it from that site's origin.
  • An agent on a website needs a middle. The hub rewrites the session so a site cannot pick the agent's folder or give it servers, and cannot see another site's session.
  • A stream that is relayed through an introducer stalls, silently, when the introducer goes. A port does not. Introduce with a port, then send the stream down it.
  • A port can survive its page reloading. It cannot be stored, but it can be posted to a SharedWorker made with extendedLifetime as the page unloads and collected on the next load.
  • Two unrelated tabs have no way to pass a port. So when you pick a tool whose site is already open in a tab, your hub server introduces the two tabs and they open a WebRTC channel between themselves. That line carries JSON only: ports and streams cannot ride on it.

AI router: use your own model account on any site

A site asks for an AI model. A window from the router opens and you pick one of your own accounts. The site gets a MessagePort to send prompts on. It never sees your API key, and you can stop it at any time.

Try it on this page

This page is a site like any other. It has no AI account. Press the button, pick one of your accounts, then send a prompt. You need an account in your router first.

Two other sites use the same router. Each has to ask you separately, and each gets its own limit.

    What it is for

    Today a site that wants to use a model has two choices. It can pay for the model itself and run a server that hides its key. Or it can ask you to paste your API key into its page, where its scripts can read it and send it anywhere.

    With the router you give your key to one place that you choose to trust. Every other site asks that place for access and gets a port. A site can use the port, but there is no key in it to copy.

    • You add each key once, at the router's address.
    • A site asks. You see its address, pick an account and a model, and set a limit in requests and days.
    • The site sends prompts and reads answers. It is told the model's name and how many requests are left.
    • The router's page lists every site you allowed and what it has used. Stop takes effect on the site's next request.

    The code a site writes

    
        
    A site can pass its access on. lend() returns a second port into the same grant. Post it to a worker or to an iframe from another site, and wrap it there with fromPort(). With a limit, the port stops after that many requests. A lent port cannot lend again.
    

    // on the page
const port = await ai.lend({ requests: 3 });
worker.postMessage({ job: "summarise" }, [port]);

// in the worker
import { fromPort } from "/router.js";
onmessage = async (event) => {
  const ai = fromPort(event.ports[0]);
  const text = await ai.prompt("Summarise this in one line: ...").text();
};
    
        
    In the shape of the Chat Completions API
    
        
    Much code already speaks the Chat Completions API. A list of messages goes in, and a completion object or a stream of chunks comes out. The router answers in that shape too. The call does not go over HTTP. It goes down the same port, to the same grant, with the same limits.
    

    const answer = await ai.chat.completions.create({
  messages: [
    { role: "system", content: "You write short cards." },
    { role: "user", content: "A card for Ada, who passed her exam" },
  ],
});
output.textContent = answer.choices[0].message.content;

// or a few words at a time
const stream = await ai.chat.completions.create({ messages, stream: true });
for await (const chunk of stream) {
  output.textContent += chunk.choices[0]?.delta?.content ?? "";
}
    
        
      
          
    • The person chose the model, so model in the request is ignored. The answer says which model it was.
      • 
          
    • The router reads messages, stream, stream_options.include_usage, max_completion_tokens or max_tokens, temperature, top_p and stop. The browser's built-in model takes no notice of the last three.
      • 
          
    • Messages are text. A request with tools, images, a response_format other than text, or any setting the router does not pass on is refused, and the error names the field. The router does not drop a setting and answer anyway.
      • 
          
    • The token limit can be up to 4,000. With no limit in the request, the router asks for 600.
      • 
          
    • An error has the fields an OpenAI client puts on its errors: status, code, type and param. A site with no grant gets 401. A site that has used its requests gets 429.
      • 
          
    • Pass { signal } as the second argument to stop a request.
      • 
          
    • finish_reason is always "stop". The router is not told when an answer was cut short by the token limit.
      • 
        
    
        
    The calls are carried by Hawser, the remote-object library from this site. The first call to create() asks the router's worker for one more port. On that port the worker answers chat.completions.create and nothing else. A port from lend() can do the same, inside its own limit.
    
      
    

      
    
        
    How it works
    
        
    This is the whole pattern, one step at a time. It is written about an AI model, but nothing in it is about AI. It is a way for a service at one address to keep something for you, and let any site use it without ever holding it.
    

        
    Why it takes a frame and a window
    
        
    The router keeps your accounts in your browser, in the storage for the router's own address. A site that wants to use one puts a hidden frame from the router in its page. You would expect that frame to read your accounts. It cannot.
    
        
    A browser keeps a frame's storage under two things: the address of the frame, and the site the frame is inside. This is called storage partitioning. The router frame inside a florist's page has storage of its own, and it is empty. The frame inside a library's page has another. Neither is the storage you filled at the router's own address. Browsers do this so that a frame cannot follow you from site to site.
    
        
      
          
    • A router window, open in its own right, can read your accounts. It cannot stay open for ever, and a site cannot reach inside it.
      • 
          
    • A router frame, inside the site, can stay for as long as the page does, and the site can talk to it. It knows nothing about you.
      • 
        
    
        
    So the pattern uses both. The window is where you decide. The frame is what the site talks to afterwards. The rest is how a decision gets from the window to the frame without passing through the site.
    

        
    The usual way: a hidden frame
    
        
        
    
          
    When the site's page loads
    
          
      
            
    1. The site's script adds a hidden iframe from the router's address and posts it one end of a MessageChannel. The site keeps the other end. That end is the site's port.
      2. 
            
    2. The frame starts a worker and passes the port on to it. From here the site's page talks to the worker directly.
      3. 
          
    
          
    When you choose
    
          
      
            
    1. You click a button on the site, and the site opens the router window. It is a normal top-level window at the router's address, so it can read the accounts you saved there.
      2. 
            
    2. The window has to find the router frame inside the page that opened it. It posts a port to each of that page's frames, and names the router's address as the only address allowed to receive it. The browser drops the message for every frame that is not a router page. The site cannot take the port and cannot listen in.
      3. 
            
    3. The frame answers on that port with the address of the site it is inside. It learned that from the browser when the site said hello, not from anything the site wrote. The window shows you that address.
      4. 
            
    4. You choose an account, a model and a limit. The window sends your choice to the router's server.
      5. 
            
    5. The server records the grant and returns an unlock key. It keeps a copy of the unlock key. It is never sent your API key.
      6. 
            
    6. The window encrypts your API key with the unlock key.
      7. 
            
    7. The window posts the grant and the encrypted key to the frame, over the private port. The frame keeps them in its storage for this site.
      8. 
            
    8. The window closes. Nothing of the router is on screen from here on.
      9. 
          
    
          
    Every prompt
    
          
      
            
    1. The site posts a prompt on its port, with a new port for the answer. It arrives in the worker.
      2. 
            
    2. The worker asks the router's server whether the grant is still good.
      3. 
            
    3. The server counts the request and returns the unlock key. If you pressed Stop, or the limit is used up, it refuses. Then the encrypted key in the frame can no longer be opened.
      4. 
            
    4. The worker posts the prompt, the encrypted key and the unlock key to the call page. That is a second hidden iframe inside the frame. It is served with a rule that lets it connect to the provider you chose and to nothing else.
      5. 
            
    5. The call page decrypts the API key in memory and sends the prompt to the provider, straight from your browser.
      6. 
            
    6. The answer comes back the same way, a few words at a time: from the provider to the call page, to the worker, and down the reply port to the site.
      7. 
          
    
        
    

        
    When a site cannot have the frame
    
        
    Some sites cannot put a frame from another address in their pages. Their own Content-Security-Policy forbids it. For those, the router window does the frame's job, and it has to stay open. The frame is better when a site can have it: nothing has to stay open, and a reload needs no click. The chat app can be switched to either way, so you can see both.
    
        
        
    
          
    When the site's page loads
    
          
      
            
    1. The site's script adds the router frame, and the browser refuses to load it. connect() hears of it from the browser's own report, or from the frame never answering, and sets ai.mode to "window".
      2. 
          
    
          
    When you connect
    
          
      
            
    1. You click a button on the site, and the site opens the router window.
      2. 
            
    2. The window tells the page that opened it that it is ready. The message carries nothing.
      3. 
            
    3. The site posts the window one end of a MessageChannel, and names the router's address as the only address allowed to receive it. The site keeps the other end.
      4. 
            
    4. The window starts the same worker the frame would have, and passes the port on to it. The window knows which site this is, because the browser says where the port came from.
      5. 
            
    5. You choose an account, a model and a limit. The window sends your choice to the router's server.
      6. 
            
    6. The server records the grant and returns an unlock key.
      7. 
            
    7. The window encrypts your API key and keeps the grant itself, in the router's own storage. It does not close.
      8. 
          
    
          
    Every prompt
    
          
      
            
    1. The site posts a prompt on its port. It arrives in the worker, inside the window.
      2. 
            
    2. The worker asks the router's server whether the grant is still good.
      3. 
            
    3. The server counts the request and returns the unlock key, or refuses.
      4. 
            
    4. The worker passes the prompt, the encrypted key and the unlock key to the call page, inside the window.
      5. 
            
    5. The call page decrypts the API key in memory and sends the prompt to the provider.
      6. 
            
    6. The answer comes back the same way, and down the reply port to the site.
      7. 
          
    
          
    When the window closes
    
          
      
            
    1. The site is disconnected. A request that was waiting fails with an error the site can read. The grant is still in the router's storage, so the next time the site opens the window it connects at once, with nothing to choose.
      2. 
          
    
        
    

        
    What each check is for
    
        
    The site is not trusted, and it sits between you and the router the whole time. Each of these stops one thing a site could try.
    
        
    
          
    The checkWho makes itWhat it stops
    
          
            
    The window posts its port with the router's address as the only allowed receiverThe browser, for the windowA site putting a frame of its own where the router frame should be, and being handed the grant
    
            
    The site never makes the line between the window and the frameThe designA site keeping one end of that line and reading what crosses it
    
            
    The frame takes a grant only from a page at the router's addressThe frame, from event.originA site handing the frame a grant it wrote itself
    
            
    The frame takes its hello only from the page it is inside, and reads that page's address from the browserThe frame, from event.source and event.originA site claiming to be another site, to use that site's grant
    
            
    The window shows you that address before you chooseYouAllowing a site you did not mean to
    
            
    The key in the frame is encrypted, and the server holds what opens itThe server, on every requestA grant that cannot be stopped. Stop works from any tab, though the frame's storage cannot be reached from outside the site
    
            
    The call page may connect to one provider. Every other router page may connect only to the routerThe browser, from a Content-Security-Policy headerA changed or injected router script sending your key or your prompt somewhere else

    The messages
    
        
    There are few of them, so that the whole of it can be read. A message between windows is found by its router field. A message on a port is found by its t field.
    
        
    
          
    From, toThe messageWhat it is for
    
          
            
    Site to frame{ router: "hello" } and a portThe site's port. Sent with the router's address as the target
    
            
    Frame to site{ router: "frame-ready" }The frame loaded. A site that hears nothing uses the window
    
            
    Window to each frame of the site{ router: "picker" } and a portFinds the router frame. Only a router page receives it
    
            
    Frame to window, on that port{ t: "site", site, current }Which site this is, and what it uses now
    
            
    Window to frame, on that port{ t: "grant", grant, info }The grant and the encrypted key. The frame answers { t: "stored" }
    
            
    Window to site{ router: "picker-ready" }With no frame: the window is ready for a port
    
            
    Site to window{ router: "hello" } and a portWith no frame: the site's port, sent to the window
    
            
    Window to site{ router: "picked", ok }, { router: "closing" }With no frame: you chose, or the window is going
    
            
    Site to window{ router: "choose" }, { router: "bye" }With no frame: ask you to choose again, or the site's page is going
    
            
    Site to worker, on its port{ t: "prompt", system, messages, maxTokens } and a reply portOne request
    
            
    Worker to site, on the reply port{ t: "text", text }, then { t: "done", usage, left } or { t: "error", code, message }The answer, in pieces. The site can post { t: "cancel" } to stop it
    
            
    Worker to site, on its port{ t: "state", ready, model, left, expires }Sent whenever the grant changes, and when asked with { t: "state" }
    
            
    Site to worker, on its port{ t: "lend", n, requests }Another port into the same grant, with a limit. Answered with { t: "lent", n } and the port
    
            
    Site to worker, on its port{ t: "api", n }A port that speaks the Chat Completions API. Answered with { t: "api", n } and the port
    
            
    Site to worker, on its port{ t: "forget" }Drop this site's grant from this browser
    
              
        
    

        
    Where the ports end up
    
        
    Every port leads to the same worker. The site's page holds one. A worker the site starts can hold another, and so can an iframe from a third site that the page chooses to lend to. None of them can open the router window, and none holds a key. The browser's built-in model cannot be used from a worker, so for that one the frame lends the worker a port and answers on it.
    
        
    Changing the model
    
        
    A site can open the router window again at any time, and it is the same steps. The window shows what the site uses now. You can pick another account or model, or add a new account there and then. The new grant replaces the old one in the frame.
    
        
    If the new model is with a different provider, the frame closes the call page for the old provider and opens one for the new. The address of the call page names the provider, as in /call.html?provider=openai, and the server sends that page with a rule that allows that one provider. So after a change, nothing in the page can reach the old provider. The rule is about the provider's address, not about which of its models is asked for. The model is set by the router's worker from the grant, and a site cannot change it.
    
        
    After a reload
    
        
    The frame stored the grant under the site's address, so the site has its model again with no window. If you pressed Stop in the router, the server has deleted the unlock key. The encrypted key left inside that site can no longer be opened, and the frame deletes it the next time it checks. A site that uses the window has to open it again, and that takes a click.
    

        
    Using the pattern for something else
    
        
    The same parts fit any service that keeps something for a person and lets sites use it without holding it: a signing key, a wallet, an address book, a way to pay. These are the parts.
    
        
      
          
    1. A page at the service's own address, where the person keeps the thing. Here it is the list of accounts.
      2. 
          
    2. A hidden frame that a site embeds. It keeps one grant, for that one site, and nothing else about the person.
      3. 
          
    3. A window, opened by a click, where the person decides. It finds the frame by naming the service's address as the target, and hands the grant to the frame directly.
      4. 
          
    4. A port from the site to a worker inside the frame. Everything the site may do is a message on that port, and no message returns the thing itself.
      5. 
          
    5. A record of each grant on a server, with something the grant needs on every use. That is what lets a person stop a site from anywhere.
      6. 
          
    6. The window as the way through, for a site that cannot have the frame.
      7. 
        
    
        
    It is built from port patterns described elsewhere on this site: introducing two parties and stepping away, and handing on a port that can do less. The code is short enough to read: router.js is what a site loads, host.js is the job the frame and the window both do, and pick.js is the window.

    What does not work yet, and what to know
    
        
      
          
    • You are trusting the router's code. The frame and the picker are pages from the router's address, and they handle your key. A site is kept away from the key by the browser's rule that a page cannot read a frame from another origin.
      • 
          
    • The router's pages and its worker are served with a Content-Security-Policy. They can run only the router's own scripts. The call page, the only one that holds your key in the clear, can connect only to the provider named in its address. That is the provider you chose for that site. Every other router page, and the worker, can connect only to the router's own server. So if you chose Anthropic, nothing in the router can reach OpenAI or any other address, and a changed or injected script could not either. Your browser enforces this, not the router's code.
      • 
          
    • That rule has edges. It does not stop the router's code sending something to the router's own server. The code sends it no prompts and no keys, but you are trusting the code for that. It limits the connections a script makes. It does not stop a page going to another address.
      • 
          
    • There is one small server, and it exists because browsers give a frame separate storage inside each site. The list of grants is the only thing that has to be seen from everywhere, so that Stop works and the router page can show usage. It holds no keys and sees no prompts or answers.
      • 
          
    • It only works for providers that accept calls from a browser. Anthropic does when the request carries the anthropic-dangerous-direct-browser-access header. A provider that sends no CORS headers cannot be used.
      • 
          
    • Your key is visible in your own browser's network tools when the call page calls the provider. Other sites still can't see it.
      • 
          
    • Limits are counted in requests and days, not money. A site with 20 requests can still send 20 long prompts.
      • 
          
    • The site sees every answer. The router controls who pays and how much. It does not control what the site does with the text.
      • 
          
    • The Anthropic path was tested against a stand-in server, not with a real key. The OpenAI, OpenRouter, Gemini and Ollama paths have not been run at all yet. Only Chromium has been tested.
      • 
          
    • There is no tool calling and no images yet. Prompts and answers are text.

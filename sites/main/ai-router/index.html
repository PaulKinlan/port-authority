AI router: use your own model account on any site

A site asks for an AI model. A window from the router opens and you pick one of your own accounts. The site gets a MessagePort to send prompts on. It never sees your API key, and you can stop it at any time.

Try it on this page

This page is a site like any other. It has no AI account. Press the button, pick one of your accounts, then send a prompt. You need an account in your router first.

Two other sites use the same router. Each has to ask you separately, and each gets its own limit.

    What it is for

    Today a site that wants to use a model has two choices. It can pay for the model itself and run a server that hides its key. Or it can ask you to paste your API key into its page, where its scripts can read it and send it anywhere.

    With the router you give your key to one place that you choose to trust. Every other site asks that place for access and gets a port. A site can use the port, but there is no key in it to copy.

    • You add each key once, at the router's address.
    • A site asks. You see its address, pick an account and a model, and set a limit in requests and days.
    • The site sends prompts and reads answers. It is told the model's name and how many requests are left.
    • The router's page lists every site you allowed and what it has used. Stop takes effect on the site's next request.

    The code a site writes

    
        
    A site can pass its access on. lend() returns a second port into the same grant. Post it to a worker or to an iframe from another site, and wrap it there with fromPort(). With a limit, the port stops after that many requests. A lent port cannot lend again.
    

    // on the page
const port = await ai.lend({ requests: 3 });
worker.postMessage({ job: "summarise" }, [port]);

// in the worker
import { fromPort } from "/router.js";
onmessage = async (event) => {
  const ai = fromPort(event.ports[0]);
  const text = await ai.prompt("Summarise this in one line: ...").text();
};
    
        
    In the shape of the Chat Completions API
    
        
    Much code already speaks the Chat Completions API. A list of messages goes in, and a completion object or a stream of chunks comes out. The router answers in that shape too. The call does not go over HTTP. It goes down the same port, to the same grant, with the same limits.
    

    const answer = await ai.chat.completions.create({
  messages: [
    { role: "system", content: "You write short cards." },
    { role: "user", content: "A card for Ada, who passed her exam" },
  ],
});
output.textContent = answer.choices[0].message.content;

// or a few words at a time
const stream = await ai.chat.completions.create({ messages, stream: true });
for await (const chunk of stream) {
  output.textContent += chunk.choices[0]?.delta?.content ?? "";
}
    
        
      
          
    • The person chose the model, so model in the request is ignored. The answer says which model it was.
      • 
          
    • The router reads messages, stream, stream_options.include_usage, max_completion_tokens or max_tokens, temperature, top_p, stop, tools, tool_choice and parallel_tool_calls. The browser's built-in model takes no notice of temperature, top_p or stop.
      • 
          
    • A response_format other than text, or any setting the router does not pass on, is refused, and the error names the field. The router does not drop a setting and answer anyway.
      • 
          
    • The token limit can be up to 4,000. With no limit in the request, the router asks for 600.
      • 
          
    • An error has the fields an OpenAI client puts on its errors: status, code, type and param. A site with no grant gets 401. A site that has used its requests gets 429.
      • 
          
    • Pass { signal } as the second argument to stop a request.
      • 
          
    • finish_reason is "stop", or "length" when the answer ran out of tokens, or "tool_calls" when the model is waiting for tools to be run.
      • 
        
    
        
    Images
    
        
    A user message can carry images beside its words. Each is an image_url part, with an https: address or a data: address of a PNG, JPEG, GIF or WebP. The router sends them on in the shape each provider takes. An image can be up to 8 MB, and a request can carry 20.
    

    const answer = await ai.chat.completions.create({
  messages: [{
    role: "user",
    content: [
      { type: "text", text: "What plant is this?" },
      { type: "image_url", image_url: { url: photoAsDataUrl } },
    ],
  }],
});
    
        
    Tools
    
        
    A request can list tools: functions your site has, each with a name, a description and a JSON Schema for its arguments. If the model wants one run, the answer says so in tool_calls, and finish_reason is "tool_calls". The router never runs a tool. Your site decides whether to, and sends what came of it back as a tool message.
    

    const tools = [{
  type: "function",
  function: {
    name: "stock_of",
    description: "How many of a flower are in the shop today.",
    parameters: { type: "object", properties: { flower: { type: "string" } }, required: ["flower"] },
  },
}];
const messages = [{ role: "user", content: "Do you have tulips?" }];

let answer = await ai.chat.completions.create({ messages, tools });
while (answer.choices[0].finish_reason === "tool_calls") {
  messages.push(answer.choices[0].message);              // what the model asked for
  for (const call of answer.choices[0].message.tool_calls) {
    const result = await stockOf(JSON.parse(call.function.arguments));   // your code runs it
    messages.push({ role: "tool", tool_call_id: call.id, content: JSON.stringify(result) });
  }
  answer = await ai.chat.completions.create({ messages, tools });
}
output.textContent = answer.choices[0].message.content;
    
        
      
          
    • tool_choice can be "auto", "none", "required", or one function by name. parallel_tool_calls: false asks for one call at a time.
      • 
          
    • In a stream, a call arrives as its name first, and then its arguments in pieces of JSON text, as the Chat Completions API sends them.
      • 
          
    • Every call to create() is one request against the site's limit. So a question that needs a tool costs two: one to be asked for the tool, and one to answer with its result.
      • 
          
    • Only functions are passed on. strict is refused, because not every provider can promise it.
      • 
          
    • The browser's built-in model is given text only. With that model chosen, a request with images or tools is refused, and the error says so.
      • 
        
    
        
    The calls are carried by Hawser, the remote-object library from this site. The first call to create() asks the router's worker for one more port. On that port the worker answers chat.completions.create and nothing else. A port from lend() can do the same, inside its own limit.
    
      
    

      
    
        
    How it works
    
        
    This is the whole pattern, one step at a time. It is written about an AI model, but nothing in it is about AI. It is a way for a service at one address to keep something for you, and let any site use it without ever holding it.
    

        
    Why it takes a frame and a window
    
        
    The router keeps your accounts in your browser, in the storage for the router's own address. A site that wants to use one puts a hidden frame from the router in its page. You would expect that frame to read your accounts. It cannot.
    
        
    A browser keeps a frame's storage under two things: the address of the frame, and the site the frame is inside. This is called storage partitioning. The router frame inside a florist's page has storage of its own, and it is empty. The frame inside a library's page has another. Neither is the storage you filled at the router's own address. Browsers do this so that a frame cannot follow you from site to site.
    
        
      
          
    • A router window, open in its own right, can read your accounts. It cannot stay open for ever, and a site cannot reach inside it.
      • 
          
    • A router frame, inside the site, can stay for as long as the page does, and the site can talk to it. It knows nothing about you.
      • 
        
    
        
    So the pattern uses both. The window is where you decide. The frame is what the site talks to afterwards. The rest is how a decision gets from the window to the frame without passing through the site.
    

        
    Why the key is handed over on a port
    
        
    The window has your key and the frame needs it. The window sends it on a MessagePort that it opens straight to the frame. There are two reasons.
    
        
      
          
    1. The site must never see it. The frame is inside the site's page, but a site cannot read into a frame from another address, and it cannot listen to a port it does not hold. The window makes the channel itself. It posts one end to the frame, and names the router's address as the only address allowed to receive it. The site embedded the frame and opened the window, and that is all it did. It never holds either end. What happens when a site tries to get in between is further down.
      2. 
          
    2. There is nowhere shared to leave it. You might expect the window to save the key and the frame to read it. Storage partitioning rules that out. For a frame inside another site, localStorage, IndexedDB, the Cache API, a SharedWorker and a BroadcastChannel are all kept apart by the site the frame is inside. Chrome has done this since version 115, and Firefox and Safari partition storage too. It is sometimes called double-keying, because the storage is found by two keys: the frame's own address, and the site at the top of the page. A message is not storage, so it is not partitioned. A window can still post to a frame of its own address inside another site, and a port gives the two a private line.
      3. 
        
    
        
    What crosses is not the key in the clear. The window encrypts it first, with an unlock key that the router's server keeps. The copy the frame keeps is in the part of the browser's storage set aside for that site, where the router's own pages cannot reach it to delete it. So it is made useless by itself. It opens only while the server agrees, and Stop ends that from anywhere. The server keeps the unlock key and a record of the grant. It is never sent your API key, in the clear or encrypted.
    
        
    So there are two channels, made by two different parties.
    
        
      
          
    • The site makes one and gives one end to the frame. Prompts and answers travel on it. These are steps 1 and 2 below.
      • 
          
    • The window makes the other and gives one end to the frame. The grant and the encrypted key travel on it, once. These are steps 4, 5 and 9.
      • 
        
    
        
    The site does not join the two, and nothing links them. The site's part in the second is to open the window. When a site cannot have the frame, there is only the first channel, and the site gives its end to the window.
    
        
    There is one other way round partitioning, and the router does not use it. A frame can ask the browser for the storage it would have in a window of its own, with document.requestStorageAccess(). Chrome can hand over localStorage that way. It needs a click inside the frame and usually a permission prompt, and this frame is hidden. It works differently in each browser. And it would put every one of your keys inside every site's frame, where the port puts one grant for one site.
    

        
    The usual way: a hidden frame
    
        
        
    
          
    When the site's page loads
    
          
      
            
    1. The site's script adds a hidden iframe from the router's address and posts it one end of a MessageChannel. The site keeps the other end. That end is the site's port.
      2. 
            
    2. The frame starts a worker and passes the port on to it. From here the site's page talks to the worker directly.
      3. 
          
    
          
    When you choose
    
          
      
            
    1. You click a button on the site, and the site opens the router window. It is a normal top-level window at the router's address, so it can read the accounts you saved there.
      2. 
            
    2. The window has to find the router frame inside the page that opened it. It posts a port to each of that page's frames, and names the router's address as the only address allowed to receive it. The browser drops the message for every frame that is not a router page. The site cannot take the port and cannot listen in.
      3. 
            
    3. The frame answers on that port with the address of the site it is inside. It learned that from the browser when the site said hello, not from anything the site wrote. The window shows you that address.
      4. 
            
    4. You choose an account, a model and a limit. The window sends your choice to the router's server.
      5. 
            
    5. The server records the grant and returns an unlock key. It keeps a copy of the unlock key. It is never sent your API key.
      6. 
            
    6. The window encrypts your API key with the unlock key.
      7. 
            
    7. The window posts the grant and the encrypted key to the frame, over the private port. The frame keeps them in your browser, in its storage for this site.
      8. 
            
    8. The window closes. Nothing of the router is on screen from here on.
      9. 
          
    
          
    Every prompt
    
          
      
            
    1. The site posts a prompt on its port, with a new port for the answer. It arrives in the worker.
      2. 
            
    2. The worker asks the router's server whether the grant is still good.
      3. 
            
    3. The server counts the request and returns the unlock key. If you pressed Stop, or the limit is used up, it refuses. Then the encrypted key in the frame can no longer be opened.
      4. 
            
    4. The worker posts the prompt, the encrypted key and the unlock key to the call page. That is a second hidden iframe inside the frame. It is served with a rule that lets it connect to the provider you chose and to nothing else.
      5. 
            
    5. The call page decrypts the API key in memory and sends the prompt to the provider, straight from your browser.
      6. 
            
    6. The answer comes back the same way, a few words at a time: from the provider to the call page, to the worker, and down the reply port to the site.
      7. 
          
    
        
    
        
    Step 4 is the odd one. A window posts into a page it cannot read, and reaches a frame it cannot see. How the window finds the frame says why a browser allows it, and why the site cannot get in the way.
    

        
    When a site cannot have the frame
    
        
    Some sites cannot put a frame from another address in their pages. Their own Content-Security-Policy forbids it, or they are sent with a Cross-Origin-Embedder-Policy and the browser refuses the frame. For those, the router window does the frame's job, and it has to stay open. The frame is better when a site can have it: nothing has to stay open, and a reload needs no click. The chat app can be switched to either way, so you can see both.
    
        
        
    
          
    When the site's page loads
    
          
      
            
    1. The site's script adds the router frame, and the browser refuses to load it. connect() hears of it from the browser's own report, or from the frame never answering, and sets ai.mode to "window".
      2. 
          
    
          
    When you connect
    
          
      
            
    1. You click a button on the site, and the site opens the router window.
      2. 
            
    2. The window tells the page that opened it that it is ready. The message carries nothing.
      3. 
            
    3. The site posts the window one end of a MessageChannel, and names the router's address as the only address allowed to receive it. The site keeps the other end.
      4. 
            
    4. The window starts the same worker the frame would have, and passes the port on to it. The window knows which site this is, because the browser says where the port came from.
      5. 
            
    5. You choose an account, a model and a limit. The window sends your choice to the router's server.
      6. 
            
    6. The server records the grant and returns an unlock key.
      7. 
            
    7. The window encrypts your API key and keeps the grant itself. That is in your browser too, in the router's own storage. It does not close.
      8. 
          
    
          
    Every prompt
    
          
      
            
    1. The site posts a prompt on its port. It arrives in the worker, inside the window.
      2. 
            
    2. The worker asks the router's server whether the grant is still good.
      3. 
            
    3. The server counts the request and returns the unlock key, or refuses.
      4. 
            
    4. The worker passes the prompt, the encrypted key and the unlock key to the call page, inside the window.
      5. 
            
    5. The call page decrypts the API key in memory and sends the prompt to the provider.
      6. 
            
    6. The answer comes back the same way, and down the reply port to the site.
      7. 
          
    
          
    When the window closes
    
          
      
            
    1. The site is disconnected. A request that was waiting fails with an error the site can read. The grant is still in your browser, so the next time the site opens the window it connects at once, with nothing to choose.
      2. 
          
    
        
    

        
    The rule on the call page
    
        
    The call page is the only place your key is ever in the clear. So it is sent with the strictest rule of any page here. The rule is a Content-Security-Policy header from the router's server, and your browser enforces it. This is the whole of it, for /call/anthropic.
    

    default-src 'none'; script-src 'self'; connect-src https://api.anthropic.com/v1/messages; base-uri 'none'; form-action 'none'
    
        
    
          
    The lineWhat it meansWhat it stops
    
          
            
    connect-src, with one addressThe page can send a request to the address where the provider takes prompts, and to no other. That covers fetch, XMLHttpRequest, WebSocket, EventSource and sendBeaconYour key or your prompt being sent to another site, to another provider, to anywhere else at this provider, or to the router's own server
    
            
    script-src 'self'Only script files from the router's own address run. No script written into the page, no eval, no script from anywhere elseThe page being talked into running someone else's code. Nothing a site sends and nothing a model answers can become code here
    
            
    default-src 'none'Nothing else may be loaded: no image, style, font, frame, sound or videoA key carried out in the address of an image or a style sheet
    
            
    form-action 'none', base-uri 'none'No form can be sent, and the page's addresses cannot be pointed somewhere elseThe two old ways round the lines above
    
              
        
    
        
    The rule is not the only thing in the way. The call page takes a port only from the router page it is inside, so a site cannot put the call page in a frame of its own and ask it for anything. It refuses a request for any provider but the one in its own address. And it has no message that gives the key back: what comes out of it is the model's answer, as text.
    
        
    The frame around it is sent with almost as little. It may run the router's scripts, start its worker, hold the call page, and connect to the router's server. It may not hold a frame from anywhere else, so the call page cannot be sent off to another site either.
    

        
    What each check is for
    
        
    The site is not trusted, and it sits between you and the router the whole time. Each of these stops one thing a site could try. The longer account, with what is still open, is in Security: the site is in the middle.
    
        
    
          
    The checkWho makes itWhat it stops
    
          
            
    The window posts its port with the router's address as the only allowed receiverThe browser, for the windowA site putting a frame of its own where the router frame should be, and being handed the grant
    
            
    The site never makes the line between the window and the frameThe designA site keeping one end of that line and reading what crosses it
    
            
    The frame takes a grant only from a page at the router's addressThe frame, from event.originA site handing the frame a grant it wrote itself
    
            
    The frame takes its hello only from the page it is inside, and reads that page's address from the browserThe frame, from event.source and event.originA site claiming to be another site, to use that site's grant
    
            
    The window shows you that address before you chooseYouAllowing a site you did not mean to
    
            
    The frame answers only the page in the tab itself, and the window refuses a page that is inside another pageThe frame and the windowA hostile page showing a site you trust inside itself, so that you approve it by the trusted name
    
            
    A key is typed at the router's own page and nowhere else. The window a site opens never asks for oneThe designA site opening a look-alike window that asks for your key. The real one never does
    
            
    The window cannot be put inside any pageThe browser, from frame-ancestors 'none'A site drawing over the window to trick you into pressing Allow
    
            
    The key in the frame is encrypted, and the server holds what opens itThe server, on every requestA grant that cannot be stopped. Stop works from any tab, though the frame's storage cannot be reached from outside the site

    The messages
    
        
    There are few of them, so that the whole of it can be read. A message between windows is found by its router field. A message on a port is found by its t field.

    Where the ports end up
    
        
    Every port leads to the same worker. The site's page holds one. A worker the site starts can hold another, and so can an iframe from a third site that the page chooses to lend to. None of them can open the router window, and none holds a key. The browser's built-in model cannot be used from a worker, so for that one the frame lends the worker a port and answers on it.
    
        
    Changing the model
    
        
    A site can open the router window again at any time, and it is the same steps. The window shows what the site uses now. You can pick another account or model. To add an account, the window sends you to the router's own page. The new grant replaces the old one in the frame.
    
        
    If the new model is with a different provider, the frame closes the call page for the old provider and opens one for the new. The address of the call page names the provider, as in /call/openai. The server sends that page with a rule that allows one address and no other: the one where that provider takes prompts. For /call/anthropic that is https://api.anthropic.com/v1/messages. So after a change, nothing in the page can reach the old provider, and the call page cannot reach anything else at the new one either. The rule is about an address, not about which model is asked for there. A browser's rule can name where a page may connect, but not what it sends. The model is set by the router's worker from the grant, and a site cannot change it.
    
        
    After a reload
    
        
    The frame stored the grant under the site's address, so the site has its model again with no window. If you pressed Stop in the router, the server has deleted the unlock key. The encrypted key left inside that site can no longer be opened, and the frame deletes it the next time it checks. A site that uses the window has to open it again, and that takes a click.
    

        
    Using the pattern for something else
    
        
    The same parts fit any service that keeps something for a person and lets sites use it without holding it: a signing key, a wallet, an address book, a way to pay. These are the parts.
    
        
      
          
    1. A page at the service's own address, where the person keeps the thing. Here it is the list of accounts.
      2. 
          
    2. A hidden frame that a site embeds. It keeps one grant, for that one site, and nothing else about the person.
      3. 
          
    3. A window, opened by a click, where the person decides. It finds the frame by naming the service's address as the target, and hands the grant to the frame directly.
      4. 
          
    4. A port from the site to a worker inside the frame. Everything the site may do is a message on that port, and no message returns the thing itself.
      5. 
          
    5. A record of each grant on a server, with something the grant needs on every use. That is what lets a person stop a site from anywhere.
      6. 
          
    6. The window as the way through, for a site that cannot have the frame.
      7. 
        
    
        
    It is built from port patterns described elsewhere on this site: introducing two parties and stepping away, and handing on a port that can do less. The code is short enough to read: router.js is what a site loads, host.js is the job the frame and the window both do, and pick.js is the window.
    
      
    

      
    
        
    Security: the site is in the middle
    
        
    The hard part of this pattern is not the model. It is the page in the middle. The site embeds the router's frame. The site opens the router's window. The site writes the script that does both, and it does not have to use the router's script to do it. So the router assumes the site is hostile, and that it will try everything a page can try.
    
        
    These are the things a hostile site wants, most wanted first.
    
        
      
          
    1. Your API key.
      2. 
          
    2. To read or change what passes between the window and the frame.
      3. 
          
    3. To be allowed under another site's name.
      4. 
          
    4. To use more than you allowed, or to go on after you press Stop.
      5. 
        
    
        
    This section says how each is stopped, which part is the browser's work and which is the router's, and what is still open.
    

        
    The relay a hostile site would try
    
        
    The window and the frame have to talk, and the site stands between them. So this is the obvious attack. The site makes a MessageChannel and gives one end to the window. It makes another and gives one end to the frame. It keeps the other two ends, passes each message across, and reads every one. The window and the frame each think they are talking to the other.
    
        
    That is a relay, or a man in the middle. It looks like the Two Generals problem, and it is not. Two Generals is about messages that are lost. This is about messages that are read.
    
        
    The site can do the first half. It can make both channels, and it can offer both ports. But a port from a site is taken as a port from a site. Nothing secret is ever put on a port that a site supplied. The key travels on a third line, and the site did not make it.
    
        
    
          
    The lineWho makes itWho holds the endsWhat travels on it
    
          
            
    A. Site to frameThe siteThe site, and the router's worker inside the framePrompts and answers
    
            
    B. Site to windowThe siteThe site, and the router's worker inside the windowPrompts and answers. Only when the site has no frame. When there is a frame, the window takes no port from the site at all
    
            
    C. Window to frameThe windowThe window and the frameThe grant and the encrypted key, once
    
              
        
    
        
        
    To relay, the site would have to get the window to send the key on one of the site's ports, or get the frame to accept one. Neither happens.
    
        
      
          
    • The window uses only the port it made. It never takes the key line from the page that opened it.
      • 
          
    • The frame takes that port only from a page at the router's address. The site can post the frame the same message with a port of its own. The browser marks that message with the site's address, and the frame ignores it. A page cannot choose the address its messages are marked with.
      • 
        
    

        
    How the window finds the frame, across a page it does not trust
    
        
    The window is at the router's address. The page that opened it is not. You would expect the window to be able to do nothing with that page. It can do a few things. A browser allows a short, fixed list of things on a window from another address, and the list is the same in every browser.
    
        
    
          
    Allowed on a window from another addressNot allowed
    
          
            
    w.postMessage()w.document, and anything on the page
    
            
    w.length: how many frames it hasw.localStorage, and any other storage
    
            
    w[0], w[1]: a handle to each of those framesReading w.location.href
    
            
    w.opener, w.parent, w.topListening for the messages it receives
    
            
    w.closed, w.close(), w.focus()Any variable or function in it
    
              
        
    
        
    The window uses three of them. opener is its handle to the site's page. opener.length is how many frames that page has. opener[i] is a handle to each one. The window does not know which frame is the router's, or whether any is, and it does not try to work that out. It makes a new channel for every frame, posts one end to each, and names the router's address as the only address that may receive it.
    

    // in the router window
for (let i = 0; i < opener.length; i++) {
  const line = new MessageChannel();
  line.port1.onmessage = (event) => { /* a router frame answered. This is the line. */ };
  opener[i].postMessage({ router: "picker" }, location.origin, [line.port2]);
}
    
        
    The browser does the sorting.
    
        
      
          
    • A frame that is not a router page gets nothing. That is an advert, a video, or a frame the site planted. The browser drops the message, because the address does not match. The frame never sees the message or the port.
      • 
          
    • The router frame gets the message. It checks that the sender is a router page, and answers on the port with the address of the site it is inside. Now the window knows which line reached the real frame.
      • 
          
    • If nothing answers in two and a half seconds, the window decides there is no frame. It does the frame's job itself, and the key never leaves the window.
      • 
        
    
        
    The message goes from the window to the frame. The frame is inside the site's page, but the message does not pass through the site's script. A page cannot listen for messages sent to a frame from another address.
    
        
    The site can change the frames, and it does not help it.
    
        
      
          
    • It can add frames, or put its own first. Position does not matter. Each frame gets its own line, and only a router page can answer on one.
      • 
          
    • It can embed the router frame twice. Both are the router's real code, with the same storage. A router frame that the site has not said hello to closes the port without a word.
      • 
          
    • It can put the router frame inside another frame. The window reaches only the page's own frames, and the frame refuses to work unless the page it is in is the page in the tab.
      • 
          
    • It can leave the frame out. Then the window keeps the key, as above.
      • 
        
    

        
    Why the address is checked once
    
        
    A message between windows is marked with the address it came from. The receiver reads it in event.origin. A message on a port is not marked. There, event.origin is an empty string. So nothing can be checked once the two are talking on the port. The check is made once, on the message that delivers the port. After that, holding the port is the proof.
    
        
    That is safe because a port cannot be copied. Posting a port moves it, and the sender no longer has it. A channel has two ends and never a third. One end never left the window. The browser put the other in a router page, and nowhere else. And that page checked that it came from a router page.
    

        
    What a hostile site can still do
    
        
      
          
    • Stop it working. It can remove the frame or send it to another address. Nothing is delivered to a frame that is no longer a router page.
      • 
          
    • Use what you allowed, for anything. It can send any prompt. It can pass your model on to other people through its own server. That lasts until the limit runs out or you press Stop. The limit is in requests and days, not money.
      • 
          
    • Read every answer. It asked for them.
      • 
          
    • Send the window somewhere else. The site opened the window, so it can point it at a page of its own that looks the same. The address bar is the only thing that tells you. That is why the real window never asks for a key: a window that does is not the router.
      • 
          
    • Say anything on its own page. The router cannot stop a site telling you to paste a key into it.
      •

    The server learns about youIt is sent no keys, no prompts and no answers. You have no login and it has no name or email for you.     How it is tested
    
        
    There is a test that plays the hostile site. It is test/hostile.mjs. Its page does these things.
    
        
      
          
    • It records every message its window receives, every port it ever sees, and every message on those ports. It replaces MessageChannel and postMessage in its own page to do it.
      • 
          
    • It plants three frames of its own where the window will look: one at its own address, one with no address, and the router frame's address inside a sandbox.
      • 
          
    • It tries to read the real frame's page and storage, to listen on its window, and to replace its postMessage. It tries to read the router window's page and storage too.
      • 
          
    • It posts the frame a forged message from "the window", with a port of its own, and a grant it wrote.
      • 
          
    • It says hello to the frame a second time, for a second line in.
      • 
          
    • It posts forged messages and a port at the window while you choose.
      • 
        
    
        
    Then a person allows it, and it sends a prompt and gets its answer. At the end, everything it collected is searched for the API key, the encrypted key, and the grant's id and secret. None of them is there. It saw no message between the window and the frame. Its planted frames were sent nothing. The frame did not answer the forged window or take the forged grant. The browser refused every reach into the frame and the window.
    
        
    It is one test, in Chrome, on one computer, against a stand-in for the provider. Storage partitioning is on, as it is in your browser. Firefox and Safari have not been tried.
    
        
    A second test, test/site-headers.mjs, serves a site under each of the headers that change what a page may embed or open, and has a person try to choose. Its results are the list of where it works, and where it does not.
    

        
    What all of it rests on
    
        
    Two things.
    
        
      
          
    • The browser's rules about addresses. A page cannot read a window or a frame from another address. A message goes only to the address the sender named. A message is marked with the address it really came from. A port cannot be copied. If a browser got one of these wrong, this would fail. So would much else: the same rules keep one site from reading your mail in another tab.
      • 
          
    • The router's own code. The frame, the window and the call page handle your key. You are trusting them, and the server that sends them.
      • 
        
    
        
    These would make it harder still, and are not built.
    
        
      
          
    • A limit on how often the server can be asked.
      • 
          
    • Requests to the server signed with a key that cannot be copied out of the browser, so that a grant's id and secret are no use to a program.
      • 
          
    • Keys encrypted where they are kept, at the router's address.
      • 
          
    • A server that is told less: an id, the counts and the unlock key, with the names kept in your browser.
      •

    What does not work yet, and what to know
    
        
      
          
    • You are trusting the router's code. The frame and the picker are pages from the router's address, and they handle your key. A site is kept away from the key by the browser's rule that a page cannot read a frame from another origin.
      • 
          
    • The router's pages and its worker are served with a Content-Security-Policy. They can run only the router's own scripts. The call page, the only one that holds your key in the clear, can connect to one address: the one where the provider named in its own address takes prompts. That is the provider you chose for that site. Every other router page, and the worker, can connect only to the router's own server. So if you chose Anthropic, nothing in the router can reach OpenAI or any other address, and a changed or injected script could not either. Your browser enforces this, not the router's code.
      • 
          
    • That rule has edges. It does not stop the router's code sending something to the router's own server. The code sends it no prompts and no keys, but you are trusting the code for that. It limits the connections a script makes. It does not stop a page going to another address.
      • 
          
    • There is one small server, and it exists because browsers give a frame separate storage inside each site. The list of grants is the only thing that has to be seen from everywhere, so that Stop works and the router page can show usage. It holds no keys and sees no prompts or answers.
      • 
          
    • It only works for providers that accept calls from a browser. Anthropic does when the request carries the anthropic-dangerous-direct-browser-access header. A provider that sends no CORS headers cannot be used.
      • 
          
    • Your key is visible in your own browser's network tools when the call page calls the provider. Other sites still can't see it.
      • 
          
    • Limits are counted in requests and days, not money. A site with 20 requests can still send 20 long prompts.
      • 
          
    • The site sees every answer. The router controls who pays and how much. It does not control what the site does with the text.
      • 
          
    • The Anthropic and OpenAI paths were tested against stand-in servers, not with real keys. That includes images and tool calls. OpenRouter, Gemini and Ollama use the same code as OpenAI, and have not been run at all yet. Only Chromium has been tested.
      • 
          
    • Images and tool calls are passed on, and nothing else yet. There is no sound and no file going in, no image coming out, and no promise that an answer is JSON that fits a schema.
      • 
        
    

        
    Where it works, and where it does not
    
        
    A site's own headers decide two things: whether its page may hold the router's frame, and whether a window it opens can still reach it. The router needs the second. With the first it works better. The rows marked tried were run in Chrome by a test, test/site-headers.mjs, which serves one small site under each set of headers and has a person try to choose a model.
    
        
    
          
    The site, or the browserWhat happensHow it is known

    Firefox and SafariNot knownNot tried
    
            
    A phoneNot known. Where the window has to stay open, it is a second tab, and a phone may stop a tab that is not in frontNot tried
    
            
    A private windowNot known. Accounts added in one should be gone when it closesNot tried
    
            
    A browser set to keep no data for the router's addressNot known. The router would have nowhere to keep your accounts or a grantNot tried
    
            
    A browser inside an app, that cannot open a second windowNot known. Without the window there is nowhere to chooseNot tried
    
              
        
    
        
    The first of the failures has no way round that keeps the site out of the middle. The window finds the frame through its handle to the page that opened it. Without that handle, the window and the frame could only meet through something the site passes along, such as an address for the window to open. Then the site could put itself between them, and that is the relay the design is there to stop. Asking the browser for storage access, as described under why the key is handed over on a port, might be a way round. It has not been tried.

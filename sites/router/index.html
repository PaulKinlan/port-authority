      About

      A site that wants to use an AI model has had two choices. It can pay for the model itself and run a server that hides its key. Or it can ask you to paste your API key into its page, where its scripts can read it and send it anywhere.

      This router is a third way. You give your key to one place that you choose to trust. Every other site asks that place for access and gets a port: something it can send prompts down and read answers from. There is no key in a port to copy.

      • You use the accounts you already have. There is nothing to sign up for here and nothing to buy. Your prompts go from your browser to your provider, on your own account.
      • You decide, one site at a time. When a site asks, you see its address, pick an account and a model, and set a limit in requests and days.
      • You can see it and stop it. This page lists every site you allowed and what it has used. Stop takes effect on that site's next request.
      • Any site can ask. A site adds one script to its page. It needs no account with the router and no key of its own. A site that already speaks the Chat Completions API can call the router in that shape.

      The router is an experiment by Paul Kinlan, and part of Port Authority, a site about what the web can do when pages hand each other message ports.

      How it works

      When a site asks for a model

      1. The site adds a hidden frame from this address to its page and gives it one end of a MessageChannel. The site keeps the other end. That end is its port.
      2. When you press the site's button, a small window from this address opens. Only pages from this address can read the accounts you saved here, so the window can list them and the site cannot.
      3. The frame tells the window which site it is inside. It learned that from the browser, not from anything the site wrote, and the window shows you that address.
      4. You choose an account, a model and a limit. You can add an account in that window if you have none, or want another. The window records your choice on the router's server and gets back an unlock key. It encrypts your API key with that, gives the encrypted copy to the frame, and closes.

      When the site sends a prompt

      1. The prompt goes down the site's port to a worker inside the frame.
      2. The worker asks the router's server whether your permission still stands. The server counts the request and returns the unlock key, or refuses.
      3. The worker hands the prompt, the encrypted key and the unlock key to one more hidden page inside the frame. That page is served with a rule that lets it connect to the provider you chose and to nothing else, not even the router.
      4. That page decrypts your API key in memory and calls the provider straight from your browser. The answer comes back down the port a few words at a time.

      When a site cannot have the frame

      A site whose own rules forbid frames from other addresses passes its port to the window instead. The window then does the frame's job, and stays open while the site uses the model. Closing it disconnects the site.

      When you press Stop

      The server deletes the unlock key. The encrypted copy of your API key that was left with that site can no longer be opened, and the frame deletes it the next time it checks.

      Who can see what

      • The site sees your prompts and the answers, because it wrote the first and asked for the second. It never sees your API key.
      • The router's server keeps one record for each site you allowed: the site's address, the names of the account and the model, counts of requests and tokens, and the unlock key. It holds no API keys and sees no prompts or answers.
      • Your provider sees your prompts and answers, and the API key it issued to you.
      • This browser holds your accounts, in its storage for this address.

      What you are trusting

      • You are trusting the router's code. The frame and the window are pages from this address, and they handle your API key. A site is kept away from the key by the browser's rule that a page cannot read a frame from another origin.
      • The router's pages can run only the router's own scripts. The page that holds your key in the clear can connect to one address: the one where the provider you chose for that site takes prompts. Every other router page can connect only to the router's own server. If you chose Anthropic, no router page can reach OpenAI, or any other address. The rule is a Content-Security-Policy header, and your browser enforces it, not the router's code.
      • That rule does not cover the router's own server. The router's code sends it no prompts and no keys, and you are trusting the code for that.
      • Limits are counted in requests and days, not money. A site with 20 requests can still send 20 long prompts.
